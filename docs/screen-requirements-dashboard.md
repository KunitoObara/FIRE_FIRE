# 画面要件定義書:ダッシュボード・データ管理系画面(B1〜B4、B11)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.2節のダッシュボード・データ管理系画面(B1〜B4、B11)について、画面ごとの要件を詳細化したものである。機能全体の方針は [FIRE-FIRE 要件定義書](./fire-asset-management-requirements.md) 4.2〜4.4節および4.8節を参照。

## B1. ダッシュボード画面

- **画面目的**: ログイン後のトップ画面。資産状況・FIRE達成度・収支状況を俯瞰する

| 区分 | 項目 |
|---|---|
| 表示項目 | 資産推移グラフ(資産種別の積み上げ。分類軸が対象にする不動産を1本の帯として積み、負債の反映を切替)、分類別内訳(円グラフ)、FIRE達成度ゲージ/到達予測日/現在資産額(その対象分類名を併記)、収支サマリ(選択した年月の収支・費目別支出の円グラフ)、負債サマリ(負債合計・項目別の残債)、直近CSV取込日時、(A8経由のログイン時のみ)Googleアカウント連携の失敗通知 |
| 入力項目 | 分類軸切替セレクタ([B4](#b4-資産分類マスタ設定画面)で登録した分類から選択)、表示期間切替(例:1年/3年/5年/全期間)、資産推移グラフの負債反映切替(ON/OFF)、収支サマリの年月選択 |
| 主な操作 | 分類軸切替、表示期間切替、資産推移グラフの負債反映切替、収支サマリの年月選択、「CSVを取り込む」ボタン、各ウィジェットからの詳細画面遷移 |

**分類軸の切り替えが及ぶ範囲**

分類軸切替セレクタは、**資産推移グラフと分類別内訳の両方**に反映する。分類軸は「総資産ポートフォリオに加えて切り替えられるポートフォリオの単位」であり([要件定義書](./fire-asset-management-requirements.md) 4.3)、内訳だけが切り替わって推移が総資産のまま残ると、同じ画面の2つのグラフが別の対象を指すことになるため。

- 資産推移グラフの見出しには選択中の分類軸名を添える(例:「資産推移(投資性資産)」)。「総資産推移」と固定で名乗ると、総資産以外を選んだときに中身と食い違う
- 収支サマリはこのセレクタの影響を受けない。入出金明細の集計であり、資産の分類軸とは別の軸のため。収支サマリは代わりにカードの中に**年月選択**を持つ(後述「収支サマリ」)
- 負債サマリもこのセレクタの影響を受けない。**登録済みの負債をそのまま並べる**カードであり、分類軸で絞ると「登録したのに出てこない負債」が生まれるため(後述「負債サマリ」)
- FIRE達成度ゲージも**このセレクタの影響を受けない**。ゲージの現在資産額は分類軸で集計するが、どの分類軸で見るかは目標とセットで **B8 FIRE目標設定画面** に持つ(次項)。B1のセレクタに追従させると、同じ目標に対する達成率が画面上の切替ひとつで別の値になり、「目標に対してどこまで来たか」として読めなくなる

**資産推移グラフの負債反映切替(ON / OFF)**

資産推移グラフは**常に資産種別の積み上げ面グラフ**とし、カードの中の切替では**対象の負債を反映するかどうか**だけを行き来する。**既定は反映ON**。

| 切替 | 描くもの |
|---|---|
| 負債反映 ON(既定) | 対象の資産種別の帯に加え、**対象の負債を0より下の1本の帯として積む**。正の帯の合計と負の帯の合計の差がその時点の純資産になる |
| 負債反映 OFF | 対象の資産種別の帯だけを積む。負債は描かない(負債を集計対象にする前の見え方) |

- 切替が動かすのは**負債の有無だけ**で、積み上げそのものは切り替えない。**合計を1本の線で描く表示は持たない**
  - 以前この切替は「積み上げ / 純資産」で、純資産側だけが差引後の1本の線だった。負債を見るたびに資産の内訳を捨てることになり、「何をどれだけ持っていて、そこから何を引くか」を1枚で読めないため、**負債の反映有無を切り替える形へ改めた**(PO判断、[B1-15](https://trello.com/c/9PoKqOdR))
  - この決定は、[B1-12](https://trello.com/c/241QPnVT) で決めた「**負債を0より下の帯として積む案は採らない**」を意図的に覆すもの。負債を含む分類軸ではY軸がマイナス側まで伸び、資産側の帯が縦に圧縮されて内訳が読みにくくなるという難点は残るが、内訳と差引を同時に読めることを優先する。読みにくいときに戻る先が切替のOFF側になる
  - 純資産の額を1つの数字として読む場所は、**ツールチップの合計**(後述「積み上げ表示」)と、同じ画面のFIRE達成度ゲージの現在資産額・分類別内訳カードの純額併記になる
- 見た目は分類軸・表示期間と同じ**2択の切替(タブ)**とし、ラベルは「**負債反映**」「**資産のみ**」にする。ON/OFFのスイッチ1つ(ラベルは「負債反映」)にしない理由は、スイッチだとOFF側が何を描く状態なのかがラベルから読めず、同じカードに並ぶ表示期間の切替とも操作の形が変わるため
- **既定を反映ONにする。** 分類軸に負債を選んでいること自体が「この軸では負債を差し引いて見たい」という設定であり(B4「集計対象に負債を含める」)、既定OFFだとB4でチェックした結果が初期表示に出ない。負債を1件も選んでいない分類軸ではONでも描くものが増えないので、既定の違いはそもそも現れない
- **切替を出すのは、表示中の期間のどこかで負債の帯が0でないときだけ**とする。押しても何も変わらない切替は、負債を反映していないのか負債を設定していないのかの区別を却って曖昧にする(資産残高が1件も無いときに切替を出さないのと同じ考え方)
  - 判定を「対象の負債の**件数**」で行わない。B11は完済した負債を残債0円のまま残せるので(B11「入力項目の補足」)、0円の負債だけを参照している分類軸では帯の高さが常に0になり、押しても何も変わらない切替が出る
  - 判定を「**いまの**残債の合計」でも行わない(円グラフの負債スライスや後述の注記が使っている条件)。完済した負債は現在の残債が0でも**過去の期間には帯が出る**ため、この条件だと帯を消す手段だけが画面から無くなる。円グラフが直近1日しか描かないのに対し、推移グラフは期間全体を描くという違いがそのまま条件の違いになる
  - 表示期間(1年/3年/5年/全期間)を切り替えると、この判定も切り替え後の期間で行われる。完済からの経過が長い負債は、期間を狭めると切替ごと消えることになるが、その期間には帯が1つも無いので消えて正しい
  - 反映OFFのときに出す注記(後述「積み上げ表示」)も同じ条件に従う。切替が出ていないのに「反映していません」とだけ告げる状態を作らないため
- 選択した状態は**URLのクエリに載せる**。分類軸・表示期間と同じ扱いで、リロードやリンク共有で同じ表示を再現できる([CODING_STANDARDS.md](../src/frontend/docs/CODING_STANDARDS.md) 2章)。未指定・不正な値は既定(反映ON)として解釈する(分類軸・表示期間の解決と同じ)
- **FIRE達成度ゲージの現在資産額と一致するのは、反映ONのときのツールチップの合計の最新点**(後述「FIRE達成度の現在資産額(対象分類)」)。面の上端は正の帯だけの合計なので、この一致は上端には無い
- 見出しに選択中の分類軸名を添える扱いは切替によらず変えない(「資産推移(投資性資産)」)
- 分類軸切替・表示期間切替はどちらの状態にも効く。切替そのものが分類軸や期間の選択を変えることはない

**積み上げ表示**

- 帯は**対象の資産種別**で分ける。加えて**対象の物件を「不動産」1本の帯として積み**(後述「不動産を含む分類軸の集計」。負債反映の切替の影響を受けない)、**負債反映ONのときだけ、対象の負債を1本の帯として積む**
  - 負債の帯は**項目ごとに分けず「負債」1つにまとめる**(円グラフの負債スライスと同じ理由。項目別の残債は負債サマリとB11で見られる)
  - 負債の帯の額は**その時点の残債に -1 を掛けた値**とし、`stackOffset="sign"` によって0より下に積まれる。差し引くのではなく負の帯として積むので、面の上端(正の帯の合計)は負債の有無で動かない
  - 色は資産分類カラーのスロット(`--chart-1`〜`--chart-8`)を使わず、**円グラフの負債スライスと同じ負債専用の固定色**にする([DESIGN.md](../DESIGN.md) 3章)。同じ画面の2つのグラフで負債の色が違うと見比べられないうえ、資産のスロットを負債が奪うと実際に持っている資産の分類が「その他」へ押し出される
  - 負債の帯も円グラフのスライスと同じく**擬似的な分類ID**で表し、表示名「負債」との一致で判定しない(資産種別の名前はCSVの列名そのものなので「負債」という名前の資産種別が現れうる)
  - 帯の並びは資産種別のスロット順の**後ろ**に固定する。負の値なので描かれる位置は0より下だが、凡例の並びは常に「資産種別 → 負債」になる
- **色は分類別内訳(円グラフ)と同じスロット割り当てをそのまま使う**([DESIGN.md](../DESIGN.md) 3章)。同じ画面に並ぶ2つのグラフで同じ資産種別が違う色になると、内訳と推移を見比べられない
  - 割り当ての基準も円グラフと同じにする。**直近1日の資産残高に現れる資産種別**を名前順に並べ、8スロット + 「その他」に収める
  - **基準に採るのは符号を問わず直近1日に現れる資産種別すべて**で、円グラフが構成比を出すときに掛けている「0円以下の資産種別を除く」フィルタは色の割り当てには掛けない。マイナス残高の資産種別も固有の色と凡例を持つ。掛けてしまうと、負の帯だけが常に「その他」の色に丸められ、凡例で識別できるようにした意味が無くなる
  - そのため**すでに全て売却した資産種別は、過去の区間で「その他」に溶ける**。これは許容する。過去に存在した種別まで基準に含めると、表示期間(1年/3年/5年/全期間)を切り替えるたびにスロットの並びが変わって同じ資産種別の色が入れ替わり、「分類軸や期間を切り替えても同じ分類は同じ色」というDESIGN.md 3章の約束を推移グラフだけが破る
  - 「その他」に溶けた分も帯としては積まれるので、**過去の合計が欠けることはない**
- **マイナス残高の資産種別は0で止めず、負のまま積む。** 積み方は**正を0より上・負を0より下に分けて積む**(Rechartsの `stackOffset="sign"`)。0に丸めると、その種別を保有していること自体が画面から消える
  - 順にそのまま累積する既定(`stackOffset="none"`)は採らない。マイナスの帯が直前の帯に重なって下向きに描かれ、どの帯がどこまでなのかが読めなくなる
  - この積み方では**面の上端は「正の資産種別だけの合計」**であり、対象の資産種別の合計でも純資産でもない。合計を読む場所はツールチップの合計であって、面の上端ではない
- 帯の並び順は円グラフと同じくスロット順に固定する。金額順にすると月ごとに順位が入れ替わって帯が交差し、同じ種別の帯を横に追えない
- **凡例を出す。** 1本の線だったこれまでと違い、色以外に資産種別を識別する手掛かりが無くなるため(色だけに意味を持たせない。DESIGN.md 1章・3章)。負債の帯を積んでいるあいだは凡例にも「負債」を出す
- ツールチップにはその月の**資産種別ごとの額と合計**を出す。積み上げでは各帯の額を目盛りから読めない(帯の下端が0ではないため)
  - **「合計」は行に並べた額の総和**とし、負の資産種別も符号のまま加える。行を足しても合わない合計を並べないため。したがって**面の上端(正の帯だけの合計)とは一致しないことがある**
  - **負債反映ONのときは負債の行も出し、合計にも含める。** このとき合計はその時点の純資産そのものになり、FIRE達成度ゲージの現在資産額と突き合わせられる(最新点の場合)
  - 負債の行の額は**マイナスの符号を付けて出す**(帯が0より下にあることと符号を一致させる)。負債サマリ・円グラフが正の値で残債を並べるのとは符号の向きが違うが、こちらは「合計に足すと純資産になる値」であり、符号を落とすと行を足しても合計に合わなくなる
  - **負債反映OFFのときは負債の行を出さない。** 描いていないものをツールチップだけが差し引くと、同じカードの中で2つの合計が並ぶ
- **負債反映OFFのあいだは、対象の負債を反映していない旨を添える。** 隣の円グラフは負債のスライスと差引後の純額を出しているので、注記が無いと同じ画面の2つのグラフが同じ分類軸について違う合計を示しているように見える。出す条件は切替と同じ「表示中の期間のどこかで負債の帯が0でない」で揃える(切替が出ていないのに注記だけが残る状態を作らない)
- 資産残高が1件も無いときの空状態は切替によらず同じとする(切替を出す前に空状態を出す)

**実装時に直すもの**(切替を「積み上げ / 純資産」から「負債反映 ON / OFF」へ改める分。[PR #144](https://github.com/KunitoObara/FIRE_FIRE/pull/144) で実装済み):

- `NetWorthPoint` は**その時点の残債を別に持つ**。現状は差引後の `amount` と資産種別ごとの `byType` しか無く、負債の帯の高さは `byType` の総和と `amount` の差からしか求められない。逆算はフィルタの有無に依存する脆い読み方になるため、集計側(`src/frontend/src/lib/dashboard/aggregation.ts` の `buildAxisNetWorthSeries`)で明示的に持たせる。**`amount` は残す** — `resolveAxisNetAmount` とFIRE達成度ゲージの一致の約束がこの値に乗っている
- 1本の線を描く `src/frontend/src/components/dashboard/NetWorthTrendChart.tsx` は使わなくなる。合計を線で読む表示が無くなるため、コンポーネントごと畳む(残すと参照されない実装が2つ目のグラフとして残る)
- `src/frontend/src/constants/dashboard.ts` の `NET_WORTH_TREND_MODES` / `DEFAULT_NET_WORTH_TREND_MODE_ID` / `DASHBOARD_TREND_PARAM` と、`src/frontend/src/types/dashboard.d.ts` の `NetWorthTrendModeId`(`"stacked" | "net"`)を、負債反映のON/OFFへ置き換える。URLのクエリも同時に変わるので、`src/frontend/src/lib/dashboard/filters.ts` の `resolveTrendModeId` と href の組み立てを合わせる
- `STACKED_DEBT_NOT_DEDUCTED_NOTICE` の文面は「純資産で見られます」と旧切替の名前を指しているため、反映OFF側の案内として書き直す
- 切替と注記を出すかどうかの判定を、**表示期間で絞ったあとの推移**から求める。`NetWorthTrendCard` が受け取っている `debtTotal` は直近1日の残債(円グラフと共有している値)なので、この判定には使えない(完済した負債の過去の帯を消せなくなる)
- `buildNetWorthSeriesKey` の署名に**負債反映の状態と残債**を含める。負債の帯が出入りしただけではデータの署名が変わらず、アニメーションの再生が漏れる(DESIGN.md 9章)
- `src/frontend/src/lib/dashboard/category-color.ts` の `buildStackedTrend` は資産種別の帯しか組み立てない。負債の帯(専用色・スロットを消費しない・並びは末尾)を足す
- **帯・凡例・ツールチップを実際に描く `src/frontend/src/components/dashboard/NetWorthStackedChart.tsx` が、この改定でいちばん手の入るファイルになる。** `buildStackedTrend` を直しただけでは表示は変わらないので、次の3点を漏らさない
  - docstringの「負債は帯にせず、差し引いた推移は純資産表示が描く」は、廃止する旧切替を前提にした説明になっている
  - ツールチップの合計を組み立てている箇所のコメント「負債は含まない(積み上げが差し引いていないものをツールチップだけが差し引くと…)」は、**反映ONでは負債の行を出して合計にも含める**という本改定と正面から食い違う
  - `bands` から組み立てている系列と凡例に負債の帯が入っていない(ハッチングの描き分けもここに要る。[DESIGN.md](../DESIGN.md) 3章)

**FIRE達成度の現在資産額(対象分類)**

FIRE達成度ゲージの現在資産額は、[B8 FIRE目標設定画面](./screen-requirements-fire-goal.md) で設定した**達成度の対象分類**の分類軸で集計する。目標資産額は「どの資産がいくらになったらFIREできるか」の目標であり、居住用不動産のように取り崩せない資産まで含めた総資産と比べると達成率が実態より高く出るため、比較する資産の範囲をユーザーが決められるようにする。

- 既定は**「総資産(マネーフォワードの合計)」**で、これは分類軸を1つも選んでいない状態を指す。B8で対象分類を設定していない既存ユーザーは、これまでどおりの値のままになる
- 対象分類として分類軸を選んだ場合、集計は資産推移グラフ・分類別内訳と同じ「対象の資産種別の足し合わせ」で行う。同じ分類軸をB1のセレクタで選んだときに、**資産推移グラフの最新点のツールチップの合計(負債反映ON)**とゲージの現在資産額が一致する(面の上端は正の帯だけの合計なので一致しない。前述「資産推移グラフの負債反映切替」)
- 既定(総資産)のときだけはCSVの「合計(円)」列をそのまま採る。**そのため、集計対象を空にした「総資産」相当の分類軸を対象分類に選ぶと、既定の場合とわずかにずれることがある。** ずれるのはマネーフォワードの合計に資産種別の列として現れない額が含まれる場合だけで、そのときはCSVの合計側が正しい(既存の扱いと同じ)
- ゲージのカードには**対象分類名を併記する**(例:「現在資産額 49,600,000円(投資性資産)」)。併記しないと、B1のセレクタが別の分類軸を指しているときにゲージの数字がどちらのものか判別できない
- 対象分類に設定した分類軸がB4で削除されていた場合は、**既定(総資産)で計算したうえで、カード内にその旨とB8への導線を出す**。ゲージを消したり0円として達成率0%を出したりしない。計算できなくなったのではなく比較対象が失われただけであり、黙って基準を変えると気付かないまま別の達成率を見続けることになるため
- この参照を理由にB4側の削除を禁止はしない。B4の削除禁止は資産データが紐づく分類軸に対する制約であり、設定から参照されているだけの分類軸まで削除できなくすると、分類の整理ができなくなるため
- CSV未取込、または対象分類に該当する資産が無い場合は0円(達成率0%)として扱う。未取込であることは同じ画面の「直近CSV取込」が示す
- 到達予測日も同じ対象分類の推移から算出する(算出そのものは想定利回り(B9)を前提とするためPhase 4)

**実装時に直すもの**: `src/frontend/src/lib/dashboard/fire-progress.ts` の `buildFireProgress` には「現在資産額は分類軸の影響を受けない(docs/screen-requirements-dashboard.md B1)」というコメントがあり、本項を根拠にしている。本項の追加でこの記述は誤りになるため、実装時に「B1のセレクタには追従しないが、B8で設定した対象分類には従う」旨へ直す。値だけ変えるとコメントと参照先が正面から食い違う。

**負債を含む分類軸の集計**

[B4](#b4-資産分類マスタ設定画面) の分類軸は、集計対象として資産種別に加えて [B11 負債入力画面](#b11-負債入力画面) の負債を選べる(要件定義書 4.3 / 4.8)。負債を含む分類軸の集計は「**対象の資産種別の合計 - 対象の負債の残債**」になり、資産推移グラフ・分類別内訳・(B8で対象分類に選ばれていれば)FIRE達成度ゲージに効く。

- 資産推移グラフは、**各時点で「その時点以前で最も新しい残債」を反映する**(負債反映ONのとき)。残債は手動更新だが、B11が保存のたびにその日の残債を履歴として残すため(B11「残債の履歴」)、過去の点も当時の残債で引ける
  - **負債を反映し始める起点は、B11の発生年月**(後述「発生年月からの反映」)。発生年月が未入力の負債は、これまでどおり最初に残債を記録した日が起点になる
  - **起点より前の期間は差し引かない。** 残債が分からない期間に現在の値を当てると、実際には無かった負債を過去に作ることになる。起点の月に段差が出るが、これは「そこから負債を負った」という事実の表示であり、隠さない
  - 現在の残債を全期間に一律で差し引く案は採らない。実装は最も簡単だが、当時の残債は今より多いのが普通なので、過去の純資産が実態より良く見える
  - 推移グラフに反映しない案も採らない。同じ分類軸を選んだときに推移グラフの最新点とFIRE達成度ゲージの現在資産額が一致するという前項の約束が崩れる
- **「いま」を表す表示は、履歴ではなく現在の残債(B11で最後に保存した残債)を使う。** 対象は**推移グラフの最新点・分類別内訳の負債スライスと純額の併記・FIRE達成度ゲージの現在資産額**の3つで、履歴に従うのは過去の点だけとする
  - こうしないと、**負債を登録した直後に負債がB1のどこにも現れない**。残債の履歴に付く日付は保存した日だが、資産残高の最新の日付はマネーフォワードのCSVを最後に取り込んだ日で、後者が前者より古いのが普通の状態(CSVは日次で増えるものではない)。「その時点以前で最も新しい記録」を最新点にも当てると全ての点で記録が見つからず、残債が0として扱われる
  - 実際にこの状態が起きている(2026-08-11時点のSTG:資産残高の最新は2026-08-09、負債の履歴は2026-08-10の1件のみ)。**グラフだけでなく円グラフの負債スライス・純額の併記・ゲージの現在資産額まで一斉に「負債なし」と同じ表示になる**ため、設定を間違えたのか反映されていないのかを画面から切り分けられない([B1-15](https://trello.com/c/9PoKqOdR) の起票理由)
  - 最新点だけ扱いが違うことで、**最後の点に段差が出ることがある**(資産残高の日付より後に負債を登録した場合)。これは「そこから負債を管理し始めた」段差が右端に寄っただけで、隠す対象ではない
  - 「いま」の額として現在の残債を採るのは、円グラフ・ゲージ・負債サマリが揃って「いま何をどれだけ持っている/返済中か」を表す表示だから。負債サマリは元から現在の残債を出しており、**同じ画面の負債合計とグラフが差し引く額が食い違わない**という利点もある
- 分類別内訳(円グラフ)では、**負債を1つのスライスとして描く**。金額は対象の負債の残債合計で、面積は絶対値で取る
  - 負債は項目ごとに分けず「負債」1つにまとめる。項目別の残債は負債サマリとB11で見られる
  - 色は資産分類カラーのスロット(`--chart-1`〜`--chart-8`)を使わず、負債専用の固定色にする([DESIGN.md](../DESIGN.md) 3章)。資産のスロットを負債が奪うと、実際に持っている資産の分類が「その他」へ押し出される
  - 負債のスライスは、色スロットに収まらない分類をまとめる「その他」(`__other__`)と同じく**擬似的な分類IDで表す**。表示名「負債」との一致で判定しない — 資産種別の名前はCSVの列名そのもの(要件定義書 4.3)なので「負債」という名前の資産種別が現れうるし、名前による分岐は分類軸をハードコードしない方針にも反する
  - **構成比の分母は「対象の資産合計 + 対象の負債合計」**になる。円グラフは正の面積でしか比を表せず、負債のスライスを置いた時点で分母は純額ではなくなる。カードには**差引後の純額を数字で併記**し、%が純資産に対する割合ではないことが分かるようにする(不動産を含む分類軸では、分母にも純額にも対象の物件の額が加わる。後述「不動産を含む分類軸の集計」)
  - 対象の負債の残債合計が0円のときはスライスを出さない(0円以下の資産種別を除いているのと同じ理由。0円のスライスは凡例を埋めるだけになる)
- FIRE達成度ゲージの現在資産額は、B8の対象分類が負債を含む分類軸であれば負債控除後の額になる。**カードのラベル(「現在資産額」)は分類軸によって出し分けない** — 同じ位置にある数字の呼び名が設定で変わると、B8の参考表示との突き合わせがしづらくなる。何を数えた額かは併記する対象分類名で判別する
  - **負債が資産を上回り、現在資産額がマイナスになることがある。** 負債を差し引くまで現在資産額は常に0円以上だったため、この状態は負債の導入で初めて起こる
  - このとき**達成率は0%に丸め、リングの塗りと中央の%の両方に同じ0%を使う**。リングだけを0で止めて数値に負の達成率を出すと、同じ瞬間に2つの違う達成率が画面に出ることになり、[DESIGN.md](../DESIGN.md) 9章の「リングと中央の%は同じ進捗値から描く」に反する。負の達成率を数値で見せる価値は「目標からどれだけ遠いか」だが、それは併記する現在資産額そのものが示す
  - **現在資産額の金額はマイナスのまま表示する。** ここまで0に丸めると、負債が資産を上回っている事実が画面のどこにも出なくなる。丸めるのは「目標に対してどこまで来たか」を表す達成率だけで、実額は実額のまま出す
  - あわせて**カード内に負債が資産を上回っている旨を出す**。0%は「まだ何も貯まっていない」状態でも出る値なので、注記が無いと達成率だけでは両者を区別できない
  - B8の参考表示も同じ扱いにする([screen-requirements-fire-goal.md](./screen-requirements-fire-goal.md) B8)。同じ設定に対して画面ごとに違う達成率が出ないようにするため
- **負債だけを集計対象にした分類軸は作れない。** 資産種別を1件も選ばない状態は「すべての資産種別が対象」を意味する既存の約束があるため(B4)、負債だけを選ぶと「全資産 - その負債」になる。負債だけを見たい場合は負債サマリかB11を見る。この約束はB4の画面上にも明示する(B4「集計対象に負債を含める」)
- 分類軸が参照している負債がB11で削除されていた場合は、その負債を集計対象から外して計算する。グラフやゲージを出さない扱いにはしない(存在しない資産種別が`byType`に無いときと同じ)

**実装時に直すもの**(「いま」を表す表示に現在の残債を使う分。[PR #142](https://github.com/KunitoObara/FIRE_FIRE/pull/142) で実装済み):

- `src/frontend/src/lib/dashboard/aggregation.ts` の `resolveDebtBalanceAt` は「その時点以前で最も新しい記録が無ければ0」を返す。**過去の点についてはこのままが正しい**ので関数は変えず、「いま」を表す3か所の呼び出し側を現在の残債(`Debt.balance`)へ切り替える
  - `buildAxisNetWorthSeries` — 最新点(末尾)だけ現在の残債を使う
  - `src/frontend/src/lib/dashboard/dashboard-data.ts` の `debtTotal` — `sumDebtBalanceAt(axisDebts, latest.date)` から、対象の負債の現在の残債の合計へ
  - `src/frontend/src/lib/dashboard/fire-progress.ts` の `buildFireProgress` — `sumAxisAmount` が引く残債も同じ扱いにする(推移グラフの最新点と一致し続ける必要がある)
- `sumAxisAmount` は推移の各点(過去)と現在資産額(いま)の両方から呼ばれており、**このままだと2つの意味を1つの関数が担ったままになる**。引く残債を引数で受け取る形にするなど、「いつ時点の残債を引くか」を呼び出し側が決められるようにする
- テストは**資産残高の最新日 < 負債の最初の履歴日**という並びを必ず含める。今回の不具合はこの並びでしか出ず、履歴の日付が資産残高の範囲に収まっているテストデータでは全て通ってしまう

**発生年月からの反映**

[B11](#b11-負債入力画面) の**発生年月**が入力されている負債は、資産推移グラフが**その月以降の点で差し引く**。入力されていない負債はこれまでどおり、最初に残債を記録した日から差し引く。

- 発生年月を置くのは、**段差が「借りた月」ではなく「アプリに登録した月」に出続けるため**。残債の履歴はB11で保存したときにしか積まれないので、何年も前に借りた住宅ローンでも履歴は登録した月から始まる。結果として推移グラフは長い期間を負債ゼロで描いたあと右端で崖のように落ち、資産だけの推移と純資産の推移が最後の1点でしか違わない([B11-7](https://trello.com/c/zNKoKCOn) の起票理由)
- **発生年月から最初の記録までの期間は、最も古い記録の残債を遡って当てる。** その期間の実際の残債はアプリが知りえないため、**知っている中でいちばん古い値**を置く
  - **この期間は実態より残債が少なく出る。** 返済が進む前の残債は今より多いのが普通で、その分だけ過去の純資産は実態より良く見える。全期間に現在の残債を当てる案を退けた理由(前掲)と同じ性質の誤差が、発生年月以降に限って残る。**承知のうえで採る** — 起点が「登録した月」のままである状態のほうが、グラフの読み違いとしては大きいため
  - 当初借入額を別に入力させて直線で補間する案は採らない。入力が1つ増えるうえ、元利均等返済の残高は直線ではない(序盤は利息の割合が高く減りが遅い)ので、補間もまた近似にとどまる
  - 金利と残りの返済期間から残債を逆算する案も採らない。**「自動計算は行わない」**という負債管理の方針([要件定義書](./fire-asset-management-requirements.md) 4.8)と正面から衝突する。金利・返済期間はどちらも任意入力で未登録がありうるうえ、繰上返済があると実際の残債と合わない
  - 遡りは**発生年月で止める**。それより前の点は差し引かない
- **最新点が現在の残債であることは変えない**(前掲「いま」の扱い)。発生年月は起点を動かすだけで、右端の値には関わらない
- **発生年月が最初の記録より後にある場合も、発生年月より前の点は差し引かない。** B11側でこの前後関係を入力エラーにしないと決めているため(B11「バリデーション」)、集計側が一意に決まる規則を持つ必要がある
  - ただし**発生年月より前の記録も、残債の値としては使う**(その記録が指す日に遡って差し引くことはしない)。発生年月が決めるのは「いつから差し引くか」だけで、残債を選ぶ範囲は狭めない
  - 範囲まで狭めると、**発生年月より前の記録しか持たない負債**で起点以降に採れる記録が1件も無くなり、過去の全期間が残債0円になる。既存の負債に発生年月だけを後から入力した場合(残債が変わらない保存では履歴が増えない。B11「残債の履歴」)にこの形になり、**実際にはずっとあった負債が過去から消えて純資産が過大に出る**。最後の点だけ現在の残債に戻るので、このカードが解消しようとした「右端の崖」もそのまま残る([PR #143](https://github.com/KunitoObara/FIRE_FIRE/pull/143) のレビュー指摘)
- 円グラフの負債スライス・純額の併記・FIRE達成度ゲージ・負債サマリは**発生年月の影響を受けない**。いずれも「いま」の額であり、起点をどこに置いても現在の残債は変わらない
- 積み上げ表示の負債の帯([B1-15](https://trello.com/c/9PoKqOdR))も同じ規則に従う。帯が0でなくなる左端が発生年月になる
- 表示期間(1年/3年/5年/全期間)を切り替えても規則は変わらない。発生年月が表示期間より前にある負債は、**期間の最初の点から差し引かれた状態**で描かれる(段差は画面の外にある)

**実装時に直すもの**(発生年月の分。[PR #143](https://github.com/KunitoObara/FIRE_FIRE/pull/143) で実装済み):

- 残債を求める関数(`src/frontend/src/lib/dashboard/aggregation.ts` の `resolveDebtBalanceAt`)に**起点**の概念を入れた。起点は発生年月があればその月、無ければ最も古い記録の日で、起点より前は0を返す。呼び出し側(`sumDebtBalanceAt`)の形は変えていない
- **比較は `yyyy-MM-dd` の桁に揃えた**(発生年月に `-01` を足して日付として比べる)。月へ切り詰める向き(`date.slice(0, 7) >= originatedOn`)は**採れない** — 発生年月が未入力の負債では起点が最も古い記録の日になるため、月に揃えると「最初の記録と**同じ月の、記録より前の日**」まで起点に含まれ、「最初に残債を記録した日から反映する」という約束が崩れる
- **発生年月より前の記録も、残債の値としては使う。** 起点より前の点を差し引かないことは入口の判定だけで担保できており、記録を選ぶ範囲まで狭めると、発生年月より前の記録しか持たない負債で過去の全期間が0円になる(前掲「発生年月が最初の記録より後にある場合」)
- `Debt` 型・`src/frontend/src/schemas/debts.ts`・`src/frontend/src/lib/debts/form-values.ts`・`DebtInputForm` に発生年月を足した。**既存ドキュメントには無いキーなので、パース時は`null`を既定にしてある**(`categoryAxes.debtIds` に `.default([])` を入れたのと同じ扱い)
- `firestore.rules` の `isValidDebt` は許可キーと必須キーを両方 `hasAll` / `hasOnly` で見ているため、**どちらにも足した**。保存側が常にキーを書く(未入力は`null`)ことと揃えてある
- 形の検査は**月を01〜12に絞る**(`^\d{4}-(0[1-9]|1[0-2])$`)。桁だけを見る形だと `2020-13` が通り、当月との比較も文字列の辞書順なので保存まで素通りする。クライアント側(`DEBT_ORIGINATED_ON_PATTERN`)とルールで同じ形にしてある

**不動産を含む分類軸の集計**

[B4](#b4-資産分類マスタ設定画面) の分類軸は、集計対象として [B5〜B7](./screen-requirements-real-estate.md) で登録した**物件**も選べる(要件定義書 4.3 / 4.5)。物件は**1件ずつ選び、物件ごとに「利ざや(時価 - ローン残高)を反映する」か「時価を反映する」かを選ぶ**(B4「集計対象に不動産を含める」)。分類軸の集計は次の式になる。

> 対象の資産種別の合計 **+ 対象の物件の額(物件ごとに利ざや または 時価)** - 対象の負債の残債

- **物件を1件も選んでいない分類軸の集計はこれまでと変わらない。** 既存の分類軸は物件の選択を持たないため、B5に物件が登録されていてもダッシュボードの数字は動かない(負債の選択と同じ「未選択=含めない」。B4)
- **利ざやは負になりうる**(オーバーローンの物件。[不動産管理系画面の要件](./screen-requirements-real-estate.md) B6)。**0で止めず符号のまま集計する。** 0に丸めると、資産を上回るローンを負っていることがダッシュボードから消える
- 物件の額は**マイナス残高の資産種別と同じ扱い**で、負であれば積み上げの0より下に積まれる。負債の帯とは別の帯なので、両方が0より下に並ぶことがある

**「いま」の額と過去の額**

- **「いま」を表す表示は、履歴ではなく現在の時価・ローン残高(B7で最後に保存した値)を使う。** 対象は負債と同じ3つ(**推移グラフの最新点・分類別内訳の不動産スライスと純額の併記・FIRE達成度ゲージの現在資産額**)で、履歴に従うのは過去の点だけとする
  - 理由も負債と同じ(前掲「負債を含む分類軸の集計」)。物件の履歴に付く日付は保存した日で、資産残高の最新の日付はCSVを最後に取り込んだ日である。後者が古いのが普通なので、「その時点以前で最も新しい記録」を最新点にも当てると、**物件を登録した直後に不動産がB1のどこにも現れない**
- 過去の点は、**その時点以前で最も新しい記録**の時価・ローン残高から求める(B7が保存のたびに残す履歴。[同要件](./screen-requirements-real-estate.md) B7「時価・ローン残高の履歴」)
  - 利ざやを反映する物件では、**同じ記録の時価とローン残高を組で使う**。時価は最新の記録・ローン残高は別の日の記録、という混ぜ方をすると、実在しない日の利ざやを描くことになる(履歴を日付ごとに組で持つ理由でもある)
- **反映し始める起点はB7の取得年月。** 未入力の物件は、負債と同じく最初に記録した日が起点になる。起点より前の点には物件を積まない
  - 起点から最初の記録までの期間は、**最も古い記録を遡って当てる**(負債の「発生年月からの反映」と同じ)。この期間の実際の時価・ローン残高はアプリが知りえないため
  - **この期間は利ざやが実態より大きく出る。** 取得直後の時価は今より低い(または同じ)ことが多く、ローン残高は今より多いのが普通なので、当時の利ざやは知っている中でいちばん古い値より小さいはずである。負債で承知のうえで採った近似と同じ性質の誤差で、**同じ理由で承知のうえで採る** — 起点が「アプリに登録した月」のままで右端に崖が出る状態のほうが、グラフの読み違いとしては大きい
  - 当初の購入価格や借入額から補間する案は採らない(負債と同じ理由。入力が1つ増えるうえ、補間もまた近似にとどまる)
  - **取得年月が最初の記録より後にある場合も、取得年月より前の点には積まない。** B7側でこの前後関係を入力エラーにしないため(同要件 B7)、集計側が一意に決まる規則を持つ。ただし取得年月より前の記録も、額としては使う(負債と同じ)

**グラフでの見せ方**

- 積み上げ推移グラフでは、対象の物件を**「不動産」1本の帯にまとめる**。分類別内訳(円グラフ)でも**1スライス**にまとめる
  - 物件ごとに帯・スライスを分けない。物件の数だけ色スロット(`--chart-1`〜`--chart-8`)を食い、実際に保有している資産種別が「その他」へ押し出される(負債を1つにまとめるのと同じ理由)。物件別の額はB5・B6で見られる
  - 色は資産分類カラーのスロットを使わず、**不動産専用の固定色**にする([DESIGN.md](../DESIGN.md) 3章)。負債と同じく**スロットを消費しない**
  - 負債のハッチング(斜線)とは**別の模様(点)**を重ねる。利ざやが負の物件では帯が0より下に積まれて負債の帯と隣り合うため、色だけに頼ると区別が付かない([DESIGN.md](../DESIGN.md) 3章)
  - 帯・スライスの並びは**資産種別のスロット順の後ろ、負債の前**に固定する(「資産種別 → 不動産 → 負債」)。資産・不動産・負債の順は式の並びと同じで、凡例を読む順が集計の順になる
  - 負債と同じく**擬似的な分類ID**で表し、表示名「不動産」との一致で判定しない。資産種別の名前はCSVの列名そのものなので、「不動産」という名前の資産種別が現れうる(むしろマネーフォワードに不動産を登録していれば現れる。後述の重複注意はこの状況そのものである)
- 円グラフの**構成比の分母は、各スライスの絶対値の合計**になる(資産種別 + 不動産 + 負債)。負債のスライスを置いた時点で分母が純額でなくなっているのと同じで、カードに併記する差引後の純額が「%は純資産に対する割合ではない」ことを示す
  - 併記する**純額には不動産を含める**(資産 + 不動産 - 負債)。含めないと、同じカードの中でスライスの合計と純額が別のものを数えることになる
  - 対象の物件の合計が0円のときはスライスを出さない(0円以下の資産種別・0円の負債を出さないのと同じ)。合計が負(オーバーローン)のときは**絶対値で面積を取り、凡例には符号付きの額を出す**
- **FIRE達成度ゲージ**は、B8の対象分類が物件を含む分類軸であれば不動産を含んだ額になる。**既定の「総資産」は含まない** — 既定はCSVの「合計(円)」列をそのまま採るため(前掲「FIRE達成度の現在資産額(対象分類)」)、手動で登録した物件はどこにも入らない。不動産を含めた達成度を見たい場合は、B4で物件を選んだ分類軸を作り、B8の対象分類に指定する

**負債反映の切替との関係**

- **資産推移グラフの「負債反映 ON / OFF」切替は、不動産には効かない。** 切替が動かすのは対象の**負債(B11)の帯**だけで、不動産の帯は分類軸の設定どおりに積まれ続ける
  - 切替はカードの中の表示の切替であり、分類軸の設定(どの物件をどちらの額で反映するか)を上書きするものではない。切替で利ざやと時価を行き来させると、**同じ分類軸について円グラフ・ゲージと推移グラフが違う額を出す**(あちらは切替の影響を受けない)
  - したがって**「資産のみ」でも、利ざやで反映している物件はローン控除後の額のまま**である。0の線より上だけを見て「借入を一切引いていない状態」と読まれないよう、**利ざやで反映している物件がある分類軸では、その旨をカードに注記する**
- 切替そのものを出す条件は変えない(表示中の期間のどこかで**負債の帯**が0でないとき)。不動産の帯の有無は条件に入れない — 押しても不動産の帯は動かないため

**CSV取込データとの重複**

マネーフォワードに不動産を登録していると、資産残高CSVにも「不動産」等の**資産種別として同じ物件が現れる**。この状態で同じ物件をB4の分類軸に選ぶと、**同じ資産を2回数える**。

- **アプリ側で突き合わせて防ぐことはしない。** 物件名(B7でユーザーが付ける名前)とCSVの列名は一致せず、金額も一致しない(マネーフォワードの評価額とB7の手動時価は別の値)ため、同一の物件かどうかを判定する手掛かりが無い。名前や金額の近さで推測して黙って除外すると、**別物の資産が集計から消える**ほうの誤りが起こる
- 代わりに**B4の画面上で注意を促す**(B4「集計対象に不動産を含める」)。分類軸を組むときが、資産種別と物件の両方を並べて見ている唯一の場面である
- 重複を避ける組み方は2つあり、どちらもユーザーの判断に委ねる — 分類軸の資産種別からCSVの「不動産」を外す(資産種別を1件も選ばない軸ではこれができないため、明示的に選ぶ形にする必要がある)か、物件を分類軸で選ばない
- 同じ理由で、**利ざやで反映している物件のローンをB11にも登録して同じ分類軸で選ぶと、二重に差し引かれる**(要件定義書 4.8)。こちらは物件とローンの結び付きをアプリが持たないため同様に判定できず、やはり注記で知らせる

**収支サマリ**

入出金明細CSV(B2)から取り込んだ取引を、**画面上で選んだ年月の1ヶ月分**だけ集計するカード。集計に数える行・費目の粒度・読み取り範囲は [入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) を正とし、本節には画面側の扱いだけを置く。

| 項目 | 内容 |
|---|---|
| 表示項目 | 選択中の年月、その月の収入・支出・収支(差引)、費目別支出(円グラフ+凡例)、B3への導線(「詳細を見る」) |
| 入力項目 | 年月選択 |

- 集計するのは**振替でも計算対象外でもない取引だけ**([同書](./transaction-import-requirements.md) 5章)。自口座間の移動を収入と支出の両方に数えると、収支が0のまま両者だけが膨らむため
- 費目別支出は**大項目**で集計する([同書](./transaction-import-requirements.md) 6章)。中項目まで割ると項目数がカードに収まらない。中項目まで見たい場合はB3へ渡す
- 支出は金額の絶対値で表示する。CSV上は支出がマイナスだが、「収入」と並べて置く数字に符号が付くと差引の符号と紛らわしい。符号を持つのは「収支」だけとし、そちらは `formatSignedJpy` で必ず符号を出す(色だけに意味を持たせない)
- **絶対値にするのは表示側ではなく集計側。** `CashflowSummary.expense` と `ExpenseByCategory.amount` は0以上の値として組み立てる([同書](./transaction-import-requirements.md) 5章「集計した値の符号」)。`CashflowSummaryCard` は収支を `income - expense` で出し、支出を `formatJpy` へそのまま渡す作りなので、負の支出を渡すと符号が表に出るうえに**赤字が黒字として出る**
- **分類軸切替セレクタの影響を受けない**(前掲「分類軸の切り替えが及ぶ範囲」)。入出金明細の集計であり、資産の分類軸とは別の軸のため
- **表示期間切替(1年/3年/5年/全期間)の影響も受けない。** 対象の月はカードの中の年月選択だけで決まる。効くのは資産推移グラフと分類別内訳だけで、FIRE達成度ゲージが追従しないのと同じ扱いになる
- 読むのは**選択中の年月の1ヶ月分**だけとする([同書](./transaction-import-requirements.md) 8章)。取引は月に数百件のペースで積み上がるため、全件を読むと表示のたびに読み取りが増え続ける
- 選択した年月に取引が1件も無い場合は空状態とし、その旨とB2への導線を出す(後述「選択した年月にデータが無いとき」)

**年月の選択**

対象の月を画面上で選べるようにする。当月しか見られないと、月初は数件の取引だけを見ることになり、締まった月の収支を後から振り返る手段が画面に無い([B11-9](https://trello.com/c/J8iqCwQk) の起票理由)。

- **既定は当月。** 開いた直後に出るものはこれまでと同じにする
- 選択した年月は**URLのクエリに載せる**(`month=yyyy-MM`)。分類軸・表示期間・負債反映と同じ扱いで、リロードやリンク共有で同じ表示を再現できる([CODING_STANDARDS.md](../src/frontend/docs/CODING_STANDARDS.md) 2章)
  - 未指定・`yyyy-MM` として読めない値・**当月より後の月**は当月として解釈する(分類軸・表示期間の解決と同じ「不正な値は既定へ落とす」)
- **選べる上限は当月。** マネーフォワードの入出金明細は発生済みの取引を書き出すもので、未来の月には数える取引が無い。URLで未来月を直接指定されても前項のとおり当月に丸めるので、**ピッカー側でも選ばせる意味がない**(押した先で当月に戻る操作を残すことになる)
- **下限は設けない。** 取り込んである最も古い月をこの画面は知らない(読むのは選択中の1ヶ月だけ)。範囲を出すために全期間を読むのは、当月だけを読むと決めた理由([同書](./transaction-import-requirements.md) 8章)と正面から衝突する
- UIは shadcn の Date Picker と同じ構成(ボタン+ポップオーバー)とし、**中身は月のグリッド**(年の前後ナビ + 1〜12月)を自前で組む(PO判断)
  - shadcn(react-day-picker)の `Calendar` は**日単位の選択しか持たない**。`captionLayout="dropdown"` の月・年のドロップダウンは表示月を移動するためのもので、確定には日をクリックさせることになる。選んだ日が結果に一切効かない操作を画面に置かないため、日のグリッドは使わない
  - B11の発生年月が `<input type="month">` なのと形が違うのは、あちらが入力フォームの1項目(他の入力欄と形を揃える場所)、こちらがダッシュボードの表示切替であるため
  - **前月/翌月の矢印は併置しない。** ポップオーバーを開けば隣の月も同じ操作数で選べる。行き来が煩わしいと分かってから足す
- 年月を切り替えても、資産推移グラフ・分類別内訳・FIRE達成度ゲージ・負債サマリ・直近CSV取込日時は変わらない。**切り替えで読み直すのはその月の取引だけ**とし、資産残高・分類軸・負債・FIRE目標を引き直さない(切替のたびに画面全体の読み取りが増える)
- 一度見た月に戻ったときは読み直さない。月ごとに別のキャッシュに載せる(B3が期間ごとにキャッシュを分けているのと同じ扱い)

**選択した年月にデータが無いとき**

選択した年月の取引が1件も無ければ、カードは空状態にする。月初(まだ当月の取引を取り込んでいない)や、取り込んでいない過去の月を選んだときに**正常に起こる**状態なので、エラーとしては扱わない。

- 文言は「まだ取り込んでいない」と**言い切らない**。読むのは選択中の1ヶ月だけで、他の月に取引があるかどうかをこの画面は知らないため(B3の「選択した期間に取引がありません」と同じ理由)。別の月を選ぶ手とCSV取込の導線を両方添える
- **取得そのものに失敗したときは空状態を出さない。** データはあるのに「ありません」と読める表示になるため、失敗は失敗として出す(この画面の他のウィジェットと同じ扱い)。年月切替が独立した取得になる分、**再試行の導線もカードの中に要る**
- **取引はあるが支出が1件も無い月**(全て収入・振替・計算対象外だった月)は空状態にしない。収入・支出・収支の3つの数字は出し、円グラフだけを出さない。0円として出さないと、取り込んである取引を「無い」と伝えることになる([同書](./transaction-import-requirements.md) 5章の「振替しかない月」と同じ考え方)
  - **円グラフのあった場所には「この月の支出はありません」旨の一言を置く。** 空欄のまま詰めると、費目別支出が出ない理由が「支出が無いから」なのか「表示が壊れているから」なのかを画面から区別できない。CSV取込や別の月への導線は添えない — 取引は取り込めており、次にすべきことが無いため(選択月にデータが無いときの空状態とはここが違う)
  - カード自体は縮めず、3つの数字とB3への導線はそのまま残す。支出が無い月は月初以外でも普通に起こる(全額が振替・計算対象外だった月)ので、そのたびにカードの高さが変わるより、同じ位置に同じものが並ぶほうがよい

**費目別支出の円グラフ**

費目別支出を、金額の一覧ではなく**円グラフ+凡例**で出す(PO判断)。分類別内訳カードと同じ構成にして、同じ画面に並ぶ2枚のカードで読み方を覚え直さずに済むようにする。

- 凡例には**色見本・費目名・構成比・金額**を出す(分類別内訳の凡例と同じ)。円グラフの色は背景とのコントラストが3:1に届かないものがあるため、色だけに頼らせない
- **構成比の分母はその月の支出合計。** 費目別支出は全て0以上で、負債スライスのような符号の違うスライスが無いので、%はそのまま支出に占める割合になる(分類別内訳のように分母の断り書きを添える必要が無い)
- 色は `--chart-1`〜`--chart-8` の**8スロットに収め**、**選択中の月に現れる費目を名前順に並べて割り当てる**(PO判断)。費目マスタは持たない方針([同書](./transaction-import-requirements.md) 6章)なので、資産分類のような「マスタの登録順」がそもそも無い
  - **「その他」は8スロットのうち1つを使う。** 費目が8以下なら全てに個別の色が付き、9以上になった月だけ**個別色は名前順の先頭7件までで、8番目のスロットが「その他」になる**。9色目を作らない(パレットは8色しかなく、増やせば識別できない色同士が並ぶ。[DESIGN.md](../DESIGN.md) 3章)
  - **月をまたぐと同じ費目の色が変わりうる。** ある月にだけ現れる費目が並びを1つずらすため。[DESIGN.md](../DESIGN.md) 3章の「分類軸や表示期間を切り替えても同じ分類は同じ色」は**資産分類カラー**(B4の登録順に紐づく)の約束であり、マスタを持たない費目に同じ保証は置けない。凡例に費目名が出ているので、色が動いても費目を読み違えることはない
  - 金額の多い順にスロットを配る案は採らない([DESIGN.md](../DESIGN.md) 3章)。月ごとに順位が入れ替わって色が動くのは同じで、加えて同じ月でも取り込み直すたびに動く
  - 並びを固定するために選択月より広い範囲(直近12ヶ月など)の費目を読む案も採らない。読み取りが月あたり十数倍になるうえ、新しい費目が現れた月には結局並びがずれる
  - **資産分類カラーとパレットは共有するが、割り当ての軸は別。** 同じ画面で「投資信託」と「食費」に同じ色が当たることはあるが、**色の一致に意味は無い**。資産と費目は別の軸の内訳であり、見比べる関係にない(見比べる相手がある資産推移グラフと分類別内訳が割り当てを共有しているのとは事情が違う)
  - 8スロットに収まらない費目は**「ほかの費目」**にまとめる(スロットの数え方は上記)。負債専用のハッチングはここでは使わない(符号の違うスライスが無いため)
    - **受け皿の名前を資産側の「その他」と別にする**(PO判断)。費目名はマネーフォワードのCSVの値そのもので([同書](./transaction-import-requirements.md) 6章)、大項目には**「その他」が実在する**。同じ名前を使うと、費目が9件以上ある月に凡例へ「その他」が2行並び、どちらが何を指すのかが画面から読めなくなる。名前で束ねて1スライスにする案は採らない — 費目名で分岐することになり、分類をハードコードしない方針([要件定義書](./fire-asset-management-requirements.md) 4.3 / [DESIGN.md](../DESIGN.md) 3章)に反する
    - 受け皿は資産側と同じく**擬似的な分類ID**で表し、表示名との一致では判定しない
- 登場アニメーションは分類別内訳の円グラフと同じ扱いにする([DESIGN.md](../DESIGN.md) 9章)。**年月を切り替えてデータが差し替わったときも再生する**(切り替えた結果が変わったことを見せるため。資産推移グラフが分類軸切替で再生するのと同じ)

**実装時に直すもの**(年月選択と円グラフの分):

- `fetchDashboardData`(`src/frontend/src/lib/dashboard/dashboard-data.ts`)が `fetchMonthlyTransactions(now)` を一括取得に混ぜて `DashboardData.cashflow` に詰めている。**取引の取得を分ける** — `DashboardData` から `cashflow` を外し、収支サマリ側で年月をキーにした取得を持つ。混ぜたままだと、月を変えるたびに資産残高・分類軸・負債・FIRE目標まで読み直すことになる
- `buildCashflowSummary(transactions, now)`(`src/frontend/src/lib/dashboard/aggregation.ts`)は対象月を `now` から決めている(`CashflowSummary.month`)。**選択中の年月を受け取る形に変える**
- `resolveTransactionMonthRange(now)`(`src/frontend/src/lib/transactions/period.ts`)と `fetchMonthlyTransactions(now)`(`src/frontend/src/lib/csv-import/transaction-repository.ts`)も選択中の年月から範囲を出す形に変える。**当月だけを前提にしたdocstringも直す** — 「今日より後の日付が付いた取引もその月のものとして数える」は当月の話で、過去の月では月末が今日より前になる
- 収支サマリのキャッシュキーに**年月を足す**(B3が `[...TRANSACTIONS_DATA_QUERY_KEY, periodId]` としているのと同じ形)。B2の入出金明細取込後の無効化は前方一致で全ての月に効かせる(B2「取込完了後は…B1・B3のキャッシュを無効化する」)
- `CashflowSummaryCard` の見出し「収支サマリ(今月)」を、見出し+年月ピッカーに置き換える。カードは `cashflow === null` を「未取込」として扱っているが、これからは「**選択月にデータなし**」の意味になるので、`DASHBOARD_EMPTY_STATES.cashflow` の文言(「入出金明細のデータがまだありません」)も直す
- **カードに読み込み中・失敗(再試行)・空の3状態を持たせる。** 今の `CashflowSummaryCard` は `cashflow === null` の1状態しか持たず、取得の成否は画面全体の失敗表示(`resolveFailureView` と `DASHBOARD_FAILURE_MESSAGES`)が引き受けている。取得を切り出すと収支サマリだけが失敗しうるので、この3つを区別しないと**取得失敗が「未取込」として出る**(前掲「選択した年月にデータが無いとき」)。文言と再試行の可否を1組で決める形は `resolveFailureView` に既にあるので、そこを使い回せるかを含めて検討する
- 費目別支出の色割り当てに `buildBreakdownSlices`(`src/frontend/src/lib/dashboard/category-color.ts`)をそのまま使えない。あちらは資産の内訳向けに `AssetCategory[]` の登録順と負債スライスを前提にしている。費目には登録順も負債も無いので、共有するなら引数の形から見直す(名前順の一覧を渡す・負債の引数を持たない形)
- 円グラフの再生の引き金(`buildBreakdownKey` 相当)には**選択中の年月を含める**。費目と金額だけでは、同じ内訳の月へ切り替えたときに再生が漏れる([DESIGN.md](../DESIGN.md) 9章)
- shadcn の `popover` を導入する。`radix-ui` は既に依存にあるため**新しいnpmパッケージは増えない**([DESIGN.md](../DESIGN.md) 7章の表に足す)
- 「当月」を前提にしたテスト(`dashboard-data.test.ts` の「収支サマリの集計と対象月の判定に同じ時刻を使う」など)は、**選択月を渡す形に読み替える**。あわせて**当月以外の月を選んだケース**を足す(当月しか渡さないテストデータでは、範囲の計算を当月固定のまま残しても通ってしまう)

**負債サマリ**

登録済みの負債(B11)を、分類軸とは無関係にそのまま並べるカード。

| 項目 | 内容 |
|---|---|
| 表示項目 | 負債合計、項目別の残債(項目名・残債・金利・残りの返済期間)、最終更新日、B11への導線 |
| 入力項目 | なし |

- **分類軸切替セレクタの影響を受けない。** 分類軸で絞ると、負債を集計対象に選んでいない軸を表示中に「登録したはずの負債が消える」ことになる。負債を分類軸に効かせるかどうかは資産との差引をどう見るかの話で、負債そのものの一覧とは別
- 項目別の残債は**残債の多い順**に並べる。B11の並び順(登録順)ではなく金額順にするのは、ここが「いま何をどれだけ返済中か」を把握するための表示のため。件数が多い場合は上位のみを出し、残りは件数で示してB11へ渡す
- 金利・残りの返済期間は登録されていれば添える(B11で任意入力のため未登録もある)。未登録の項目は欄を空にし、0%や0ヶ月とは表示しない
- **発生年月は出さない。** このカードが答えるのは「いま何をどれだけ返済中か」で、いつ借りたかは並びにも金額にも効かない。発生年月は推移グラフの起点を決めるための入力であり、確認する場所はB11の入力欄そのものになる
- 最終更新日はB11で最後に保存した日付。時価と同じく手動更新のため、いつ時点の残債かが分からないと信用してよいか判断できない(B6の最終更新日と同じ考え方)
- 負債が1件も登録されていない場合は空状態とし、B11への導線を出す。負債が無いこと自体はエラーではない

**グラフの表示アニメーション**

資産推移グラフ・分類別内訳・FIRE達成度ゲージは、描画時にアニメーションで表示する。対象・再生時間・再生しない条件・`prefers-reduced-motion`時の扱いは [DESIGN.md](../DESIGN.md) 9章を正とし、本書には重複して持たせない。

**Googleアカウント連携の失敗通知**

[A8 アカウント連携画面](./screen-requirements-auth.md) 経由でログインした場合、Googleアカウントの連携が失敗することがある。A8には連携を実行するタイミングが2つある(2FA登録済みなら**A5の検証成功後**、2FA未登録ならパスワード検証時点で**その場で**実行しA3へ進む)が、**どちらの分岐の失敗もこの通知の対象**とする。連携の成否にかかわらずサインイン自体は成立しているためログインはやり直させず、B1到達時に一過性の通知(トースト)で連携できなかったことを伝える。

- 失敗の要因はGoogle資格情報の期限切れ、`auth/credential-already-in-use`(そのGoogleアカウントが別のFIRE-FIREアカウントで使用済み)、通信失敗などを想定する。いずれもサインインは成立しているため扱いは同じ
- 文言は「Googleアカウントの連携ができませんでした。アカウント設定からやり直せます」のように、ログイン自体は成功していることが伝わる形にする
- 通知はその場の1回のみとし、以降のログインでは繰り返さない(連携していない状態自体はエラーではないため)
- 「1回のみ」は**そのログインフローの中で1回**という意味で、通知済みフラグをFirestoreやカスタムクレームに永続化しない。連携失敗はA8を経由したログインの直後にしか起こらず、A8の連携セッションと同じくメモリ上で引き回せば足りる
- リロード等で通知を見逃しても行き止まりにはならない。連携に失敗したアカウントはGoogleが未連携のままなので、次にGoogleログインを試みれば再び `auth/account-exists-with-different-credential` となり **A8 アカウント連携画面** に到達して連携をやり直せる。したがってこの通知は [A8-2] のB10側UI(連携状況の確認・やり直し)がリリースされていなくても成立し、[A8] 単体でリリースできる
- B10の連携アカウント管理は「現在どのログイン方法が使えるか」を確認・変更するための画面であり、連携失敗からの復帰手段としては必須ではない
- 連携のやり直しは **B10 アカウント設定画面** の連携アカウント管理で行う(Trelloカード [A8-2] で実装済み。[screen-requirements-account.md](./screen-requirements-account.md)「連携アカウントの管理」)

- 収支サマリの「詳細を見る」押下 → **B3 収支明細一覧画面** へ遷移
  - **選択中の年月は引き継がない**(PO判断、[B11-9](https://trello.com/c/J8iqCwQk))。B3の期間絞り込みは「直近1ヶ月/3ヶ月/今年/全期間」で、特定の月を指す選択肢を持たないため。過去の月を見ている最中に押すと直近1ヶ月のB3が開く食い違いは残る。解消するにはB3側に年月指定を足すことになり、期間の解決・URLパラメータ・打ち切り判定まで触るので別カードで扱う

## B2. CSV取込画面

- **画面目的**: マネーフォワードCSV(資産残高推移/入出金明細)をアップロードし取込む

| 区分 | 項目 |
|---|---|
| 表示項目 | 取込種別タブ(資産残高推移/入出金明細)、直近の取込履歴、プレビューエリア |
| 入力項目 | CSVファイル選択 |
| 主な操作 | 「ファイルを選択」、プレビュー確認後「取込を実行する」ボタン、「キャンセル」 |

**取込種別ごとの違い**

タブは2つあるが、CSVの形もデータモデルも冪等性の取り方も種別ごとに別物で、共通するのは文字コードの判定とファイルサイズの歯止めだけになる。

| | 資産残高推移 | 入出金明細 |
|---|---|---|
| 元のエクスポート | 「資産推移」 | 「収入・支出詳細」 |
| CSVの形 | 日付 × 資産種別の横持ち。種別の列は保有状況で増減する | 取引1件が1行の縦持ち。列は固定 |
| 保存先 | `users/{uid}/assetSnapshots/{yyyy-MM-dd}` | `users/{uid}/transactions/{マネーフォワードのID}` |
| 再取込 | 同じ日付を上書き | 同じ `ID` を上書き |
| 仕様の正本 | 本節 | [入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) |

**入出金明細タブ**

CSVの列構成・データモデル・重複排除・上限値は [入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) を正とする。画面側の扱いは次のとおり。

- プレビューには件数・期間・サンプル行に加えて、**集計から外れる件数**(振替・計算対象外)と**新規/上書きの内訳**を出す([同書](./transaction-import-requirements.md) 7章)。振替だらけのファイルを取り込んで収支サマリが動かないとき、その理由が取込の前に分かるようにするため
- サンプル行の列は日付・内容・金額・口座・大項目/中項目とする(資産残高推移のプレビューが資産種別を横に並べるのとは別の表になる)
- 取込完了後は取込履歴と、B1・B3のキャッシュを無効化する。資産残高推移タブがB1のキャッシュを落としているのと同じ理由で、取り込んだ取引はB3の一覧とB1の収支サマリそのものになる
- タブを切り替えても選択中のファイルとプレビューは捨てない(既存の `forceMount` の扱いを変えない)
- **未実装タブの案内文言(`UNIMPLEMENTED_IMPORT_TYPE_NOTICE`)と `implemented` フラグは、この取込の実装(B2-3)で外した。** 2つの取込種別はどちらも実装済みで、種別ごとに別のコンポーネントを割り当てる

**遷移条件**

取込種別によらず共通。

- ファイル選択後、パース成功 → プレビューエリアに取込対象データ(件数・期間・サンプル行)を表示し、実行前確認を求める
- パース失敗(形式不正) → エラー表示、取込不可のまま画面に留まる
- プレビュー確認後「取込を実行する」押下 → データ反映処理を実行し、完了メッセージを表示(画面に留まり連続アップロード可能)
- 「キャンセル」押下 → プレビューを破棄し、ファイル未選択状態に戻る

## B3. 収支明細一覧画面

- **画面目的**: 入出金明細CSVから取り込んだ個々の取引データを一覧・検索する

| 区分 | 項目 |
|---|---|
| 表示項目 | 取引一覧(日付・費目(大項目/中項目)・金額・口座・摘要)、絞り込み後の件数 |
| 入力項目 | 絞り込み条件(期間、費目(大項目・中項目)、口座、キーワード検索) |
| 主な操作 | 絞り込み、並び替え(日付/金額)、ページ送り |

取引データの中身(どの行が入るか、費目とは何か)は [入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) を正とする。本節は画面側の扱いだけを持つ。

**表示する行**

- **取り込んだ取引をすべて表示する。** 収支サマリの集計から外れる行(振替・計算対象外)もここには出す([同書](./transaction-import-requirements.md) 5章)。一覧に出ないと、取込に失敗したのか除外されたのかを画面から区別できない
- 集計から外れる行には**印(バッジ)を付ける**。印が無いと、一覧の金額を足してもB1の収支サマリと合わない理由が分からない。「振替」と「計算対象外」は別の印にする — 前者はマネーフォワードが自動で付ける分類、後者はユーザーが下した判断で、意味が違う
- 金額は符号をそのまま表示する(収入がプラス、支出がマイナス)。B1の収支サマリが支出を絶対値で見せるのとは扱いが違うが、こちらは1件ごとの取引を並べる場所であり、CSVの値と突き合わせられるほうがよい
- **費目の列には大項目と中項目を両方出す。** B1の収支サマリが大項目だけで集計するのに対し、ここは中項目まで絞り込める場所なので、絞り込んだ結果がどの中項目なのかが行から読めないと絞り込みの結果を確かめられない。大項目を主、中項目を従として1つの列に収める(B2のプレビューが「大項目/中項目」で並べるのと揃える)。中項目が空の取引は大項目だけを出し、「(未分類)」のような名前を補わない([同書](./transaction-import-requirements.md) 6章)
- 取引が1件も無い場合は空状態とし、B2への導線を出す。絞り込みに一致しないだけの0件とは区別する

**絞り込みと読み取り範囲**

- 費目の絞り込みは**大項目と中項目の2段**とする。大項目を選ぶと中項目セレクタの選択肢がその配下に絞られ、大項目が未選択のときは全ての中項目を並べる([同書](./transaction-import-requirements.md) 6章)
- **Firestoreから読むのは選択中の期間の分だけ**で、費目・口座・キーワードの絞り込みと並び替えはその範囲に対してクライアント側で行う([同書](./transaction-import-requirements.md) 8章)
- 費目・口座の選択肢は取り込んだ取引から動的に組み立てる。費目マスタは持たない(資産分類軸(B4)とは別物)
- **選択肢を作る対象は、上記で読み込んだ期間内の取引とする**(選択肢のために全期間を別途読み直さない)。選択肢のためだけに全件を読むと、期間で読む量を抑えている意味が無くなる
- **ただし選択中の費目・口座は、その期間に1件も無くても選択肢に残し、該当が無いことを添える。** 期間を切り替えると選択肢の集合が変わるため、URLに載っている選択値が消えることがある。黙って外すと、結果が0件なのは「本当に無い」からなのか「選択が外れた」からなのかを画面から区別できない(打ち切りを黙って欠けさせないのと同じ理由)
- **読み取りが上限で打ち切られたら、そのことを画面に出す。** 黙って古い側が欠けると、一覧に無いことを「取り込んでいない」と読み違える。判定は**1件余分に読んで上限を超えたか**で行い、選択中の期間では分岐しない — 実際に達しやすいのは「全期間」だが、取引が増えれば短い期間でも起こる([同書](./transaction-import-requirements.md) 8章)
- 絞り込み・並び替え・ページの状態はURLに載せる(既存の実装を変えない)

**遷移条件**

- 「CSVを取り込む」ボタン押下 → **B2 CSV取込画面** へ遷移
- 取引データの編集・削除機能は本ドキュメントの対象外とする(参照専用画面)

## B4. 資産分類マスタ設定画面

- **画面目的**: 資産分類軸(総資産、純金融資産、投資性資産等)をユーザーが追加・編集・削除できる

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録済み分類一覧(分類名、集計対象の口座/資産種別・不動産・負債の紐付け状況) |
| 入力項目 | 分類名、集計対象(口座/資産種別の選択、不動産の選択と物件ごとの「利ざやのみ反映」、負債の選択。いずれも複数選択可) |
| 主な操作 | 「新規分類を追加」ボタン、既存分類の編集、削除 |

**集計対象に負債を含める**

集計対象の選択欄は「**資産種別**」「**不動産(手動)**」「**負債**」の3つのグループに分ける(不動産のグループは後述「集計対象に不動産を含める」)。負債の選択肢は [B11 負債入力画面](#b11-負債入力画面) で登録済みの負債で、選んだ負債はその分類軸の集計から差し引かれる(B1「負債を含む分類軸の集計」)。

- 資産種別と負債は**別のフィールドとして保存する**。資産種別はCSVの列名(名前)が唯一の識別子だが、負債はB11で採番するIDを持ち、同じ名前の負債を複数登録できるため、同じ配列に混ぜると区別できない
- **資産種別を1件も選ばない状態は、これまでどおり「すべての資産種別が対象」を意味する。** 負債の選択には**この読み替えを適用しない** — 負債を1件も選ばない状態は「負債を含めない」とする。両方を「未選択=すべて」にすると、既存の分類軸(負債の選択を持たない)が負債の登録と同時に黙って純資産の軸へ変わる
  - この非対称は分かりにくいので、画面上に明示する。資産種別の選択欄には未選択時に「すべての資産種別が対象」と出し(既存の一覧表示と同じ文言)、負債の選択欄には未選択時に「負債は差し引かない」と出す
  - 結果として**負債だけを集計対象にした分類軸は作れない**(資産種別が未選択なら全資産が対象になるため)。負債だけを見るための画面はB1の負債サマリとB11であり、分類軸で代替しない
- 一覧の紐付け状況には、**負債を含む軸だけ**資産種別に続けて負債の件数を出す(例:「すべての資産種別が対象 / 負債 2件」)。負債を含む軸かどうかが一覧で分からないと、B1で値が資産合計と違う理由が追えない。含まない軸に「負債なし」と書き添えないのは、大半の軸に同じ但し書きが並ぶだけになるため
  - **件数は実際に差し引かれる負債の数で出す**(次項の削除済みの参照は数えない)。参照の数をそのまま出すと、一覧の「負債 2件」とB1で差し引かれている額が食い違い、一覧に件数を出した目的そのものを外す
- B11で削除された負債が分類軸に残っている場合、その負債は選択から外れたものとして扱う(集計対象にせず、編集フォームにも出さない)。B4側で保存し直せば参照も消える
  - **外れたことは黙らせず、一覧と編集フォームの両方に表示する。** [B8 FIRE目標設定画面](./screen-requirements-fire-goal.md#b8-fire目標設定画面) が対象分類の削除で既定へ戻すときに「その旨を表示する」としているのと同じ理由で、黙って外すと分類軸が何を差し引いているかが変わったことに気付けず、B1の値が前と違う理由を追えなくなる。存在しない選択肢を選択中として出さない・黙って戻さない、というB8の出し方に揃える
  - 一覧には削除済みの参照を持つ軸にだけ件数を添える(例:「すべての資産種別が対象 / 負債 1件(1件は削除済み)」)。編集フォームには負債の選択欄に、参照を外したことと保存し直せば消えることを出す
  - **負債の選択肢が読み込み中・取得失敗のあいだは出さない。** 登録済みの負債が分からない状態では削除済みかどうかを判定できず、「取得に失敗しただけ」を「削除された」と読ませることになる(この状態ではフォーム側が保存自体を止めている)
  - 削除済みの参照があること自体は保存を妨げない。エラーではなく、集計の基準が変わった事実の通知として出す

**集計対象に不動産を含める**

3つ目のグループ「**不動産(手動)**」の選択肢は [B5〜B7](./screen-requirements-real-estate.md) で登録済みの物件で、選んだ物件はその分類軸の集計に**加算**される(B1「不動産を含む分類軸の集計」)。グループ名に「(手動)」を付けるのは、資産種別のグループにCSV由来の「不動産」が並ぶことがあり、名前だけでは同じものに見えるため。

- **物件ごとに「利ざやのみ反映」チェックボックスを持つ。** チェックがある物件は**利ざや(時価 - ローン残高)**、無い物件は**時価**を反映する。居住用は取り崩せないので利ざやで見たいが投資用は時価で見たい、のように見方が物件ごとに変わるため、軸に1つの設定にしない
  - 物件を選んだときの**既定はチェックあり(利ざやのみ)**。このカードの目的が利ざやの反映であることに加え、時価を既定にすると、ローンが残っている物件を選んだ瞬間に控除前の額がダッシュボードへ載る。少なく出るほうを既定にする
  - チェックボックスは選んだ物件の行にだけ出す(選んでいない物件に反映方法だけが残っていると、何が集計されるのか行から読めない)
  - 選択を外した物件の反映方法は**保存しない**。選び直したときは既定(利ざやのみ)に戻る。選択と反映方法を別々に覚えると、画面に出ていない設定が保存され続ける
- **物件を1件も選ばない状態は「不動産を反映しない」を意味する。** 負債と同じで、資産種別の「未選択=すべてが対象」の読み替えはしない。適用すると、物件の選択を持たない既存の分類軸が、物件の登録と同時に黙って不動産を含む軸へ変わる
  - 未選択時には選択欄に「不動産は反映しません」と出す(負債の「負債は差し引かない」と同じ扱い)
- 選択肢には**物件名と簡略表記の所在地**(B5と同じ形)を並べる。物件名は重複を許す([同要件](./screen-requirements-real-estate.md) B7)ため、名前だけでは同名の物件のどちらを選んだのか分からない。所在地は任意入力なので、未入力の物件は名前だけで並ぶ
- 資産種別・負債と**別のフィールドとして保存する**。物件はB7で採番するIDを持ち、反映方法(利ざや / 時価)を1件ごとに添える必要があるため、名前の配列である `assetTypeNames` にも、IDだけの配列である `debtIds` にも混ぜられない
- **物件の選択肢が読み込み中・取得失敗のあいだは保存を止める**(負債と同じ)。選択肢が出ないまま保存すると、選択済みの物件が黙って外れた分類軸で上書きされる
- **CSV取込データとの重複を、この欄で赤字で注意する。** 文言は「**CSV取込データとの重複に注意してください**」とし、マネーフォワードに登録済みの不動産が資産種別としてCSVに現れている場合、同じ物件を選ぶと二重に数えることを添える(B1「CSV取込データとの重複」)。分類軸を組むときが、資産種別と物件を並べて見ている唯一の場面である
  - 赤字が入力エラーに読まれないよう、**注意であることが分かるラベル(「注意」)を添える**([DESIGN.md](../DESIGN.md) 3章の「負債の金額には必ずラベルを添える」と同じ理由)。位置も入力エラーが出る場所(欄の直下)ではなく、選択肢の上に置く
  - **利ざやで反映する物件のローンを負債にも選ぶと二重に差し引かれる**ことも同じ欄に添える。ただしこちらは赤字にしない — 2つの注意を同じ強さで並べると、カードで指定された重複の注意が埋もれる
- 一覧の紐付け状況には、**不動産を含む軸だけ**物件の件数を出す(例:「すべての資産種別が対象 / 不動産 2件 / 負債 2件」)。負債の件数を出しているのと同じ理由で、B1の値が資産合計と違う理由を一覧から追えるようにするため
  - **利ざや / 時価の内訳は一覧に出さない。** 反映方法は物件ごとに変わるので、内訳まで並べると1行に収まらなくなる。何をどちらで反映しているかは編集フォームで確かめる
- B6で削除された物件が分類軸に残っている場合の扱いは、**削除済みの負債とすべて同じ**(集計対象にせず、編集フォームにも出さず、一覧と編集フォームの両方に外したことを表示し、保存し直せば参照も消える)。物件の削除は未実装で([同要件](./screen-requirements-real-estate.md)「物件の削除」)、[B6-1](https://trello.com/c/0Frlp1Q1) で実装される
- 分類軸が持てる物件の件数は**50件**までとする(`assetTypeNames`・`debtIds` と同じ値)。物件の登録件数そのものには上限を設けていないため([同要件](./screen-requirements-real-estate.md)「今後の検討事項」)、51件目以降を持つ物件は分類軸で選べない。単一ユーザー運用では到達しない前提の歯止めであり、達したなら物件側の上限とあわせて見直す

**遷移条件**

- 新規追加・編集の保存 → 一覧に反映し、**B1 ダッシュボード画面** の分類軸切替セレクタにも反映する
- 削除操作時、既存の資産データが紐づいている分類は削除を禁止し、エラーメッセージを表示する。**負債だけ・物件だけが紐づいている分類も同じく削除を禁止する** — 集計対象が割り当てられた分類軸を消させない、という制約は資産・不動産・負債で分ける理由が無いため
- **物件の扱いは負債とすべて同じ**にする(次の3点)。判定は実際に集計対象になっている件数で行う・物件を参照している分類軸に限り取得できないあいだは「判定できない」と出す・資産種別が紐づいている分類軸には取得の成否によらず削除禁止の文言を出す。2つの集計対象で判定の仕方を変える理由が無く、分けると「負債は取得できたが物件は取得できていない」ときの文言が組み合わせの数だけ増える
- **禁止の判定は「実際に集計対象になっている件数」で行い、参照の件数では行わない。** 参照している負債がB11ですべて削除済みの分類軸は、資産種別も負債も1件も集計していないため削除できる。集計対象が無いのに「集計対象が紐づいているから消せない」と言うと、制約の理由と実態が食い違う
- **負債を参照している分類軸に限り、負債の情報を取得できていないあいだは削除を止め、「判定できない」旨を表示する。** 「集計対象が紐づいている」とは書かない — 紐づいていると判明したわけではなく、取得に失敗しただけの分類軸を「集計対象がある」と読ませないため(B1の「負債が見つからない」表示と同じ考え方)
  - **負債を1件も参照していない分類軸は、負債の取得に失敗していても削除できる。** その軸の可否は資産種別だけで決まり、負債の情報は判定に要らない。ここまで止めると、負債と無関係な分類軸まで取得失敗を理由に消せなくなる
  - **資産種別が紐づいている分類軸には、負債の取得に失敗していても「判定できない」ではなく削除禁止の文言を出す。** その軸は負債の情報が取れても削除できないままなので、「時間をおいてもう一度」と促すと永久に叶わない再試行を勧めることになる。判定できないと言ってよいのは、**負債の情報さえ揃えば可否が決まる軸**(資産種別が未選択で負債を参照している軸)だけ
- **`firestore.rules` 側の削除条件は資産種別だけを見る。** 負債・物件の参照が実際に集計対象かどうかは `debts` / `properties` の存在に依存するが、ルールには繰り返しが無く可変長の `debtIds` / `propertyValuations` を1件ずつ確かめられない。件数で代用すると上記の誤ったブロックがルール側に残るため、**正しく評価できる部分だけをルールが担保し、負債・不動産側の判定は画面に持たせる**。この緩和で通るのは「生きている負債・物件を参照したままの軸を画面を経由せず直接消す」経路だけで、負債・物件そのものは消えない

## B11. 負債入力画面

- **画面目的**: 住宅ローン・カードローン・奨学金などの負債を手動で登録・編集・削除する。B1の負債サマリと、B4の分類軸を通じたダッシュボードの集計に反映される

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録済み負債の入力フォーム(1件=1フォーム)、負債合計、負債ごとの最終更新日 |
| 入力項目 | 項目名、発生年月、金利(年利%)、残債(円)、残りの返済期間(年・ヶ月) |
| 主な操作 | 「負債を追加」ボタン(フォームを1件増やす)、各フォームの「削除」ボタン(フォームを1件減らす)、「保存」ボタン |

**入力項目の補足**

- **すべて手動入力で、自動計算は行わない**(要件定義書 4.8)。金利と残りの返済期間から毎月の返済額や完済日を導かない。時間が経っても残債は自動で減らない。集計に使うのは残債だけで、金利と残りの返済期間は参考情報として保持・表示する
- 必須は**項目名と残債**の2つ。発生年月・金利・残りの返済期間は任意で、未入力は「未登録」として保存する(0%・0ヶ月とは区別する。B1の負債サマリでも欄を空にする)
- **発生年月**は借入を開始した月で、資産推移グラフがこの負債を反映し始める起点になる(B1「負債を含む分類軸の集計」)。持つのは**年と月まで**(`yyyy-MM`)
  - 日まで持たない。推移グラフは月次の点で描くので日を入れても描画は変わらず、何年も前の借入の「日」を思い出させることになる
  - **任意にする。** 未入力の負債はこれまでどおり「最初に残債を記録した日」から反映する。必須にすると、既に登録済みの負債を開いた時点でバリデーションエラーになり、値を入れるまで他の項目も直せなくなる
  - 入力欄には、**入れると推移グラフのどこから負債が引かれるようになるのか**を短く添える。入れても負債サマリ・円グラフ・FIRE達成度ゲージの数字は変わらない(いずれも「いま」の額なので)ため、何のための欄かが画面から読めないと入力されないまま残る
- 残債は0円以上の整数(円単位)。完済した負債を0円のまま残せるようにするため、0を許す
- 金利は年利のパーセント値。0以上100以下で、小数を許す(0.375%のような値があるため)
- 残りの返済期間は「年」と「ヶ月」の2欄で入力する。総月数だけを入力させると「残り23年4ヶ月」を月数に直す計算をユーザーにさせることになる。保存時は総月数へ正規化し、表示は「◯年◯ヶ月」に組み立て直す
- **最終更新日は入力項目ではなく、保存時に自動で付ける**(B7のローン残高・時価と同じ扱い)。手動更新の値がいつ時点のものかが分からないと、B1の負債サマリの数字をどこまで信用してよいか判断できない

**残債の履歴**

保存のたびに、**残債が前回と変わった負債についてのみ、その日の残債を履歴として記録する**。ユーザーに追加の入力は求めない。

- 履歴は資産推移グラフが各時点の残債を引くために使う(B1「負債を含む分類軸の集計」)。履歴が無いと、過去の純資産を現在の残債で描くことになる
- 同じ日に複数回保存した場合は、その日の記録を上書きする(CSV取込が同じ日付を上書きするのと同じ冪等な扱い)
- 残債が変わっていない保存では記録を増やさない。同じ値の点が並ぶだけで、推移の描画結果は変わらないため
- 負債を削除すると履歴も一緒に消える。資産推移グラフからはその負債の控除が過去に遡って消えることになるため、削除の確認ではこれを明示する(後述)

**追加・削除と保存**

- 「負債を追加」は**画面上のフォームを増やすだけ**で、この時点では保存しない。「削除」も同様に画面上のフォームを減らすだけで、保存するまで確定しない。1件ずつ保存する形にせず、**画面全体を「保存」で一括保存する**。負債は複数まとめて見直すことが多く、行ごとの保存だと途中まで保存された状態が残る
- したがって保存前の削除は取り消せる(画面を離れれば元に戻る)。削除ボタン自体には確認を挟まない
- **保存時に、既存の負債を削除する場合のみ確認ダイアログを挟む**([DESIGN.md](../DESIGN.md) 6章の「削除のブロッキング確認」)。ダイアログには削除する件数と、残債の履歴も消えて資産推移グラフから遡って控除が消えることを書く
- 削除する負債は**項目名と残債額を並べて示す**。項目名は重複を許す(後述「バリデーション」)ため、名前だけでは同名の負債が2件あるときにどちらが消えるのか確認できず、誤操作を防ぐという確認ダイアログの目的を果たせない。画面上の識別はIDで行い、表示だけを人が読める組み合わせにする
- 削除する負債をB4の分類軸が集計対象にしている場合は、**該当する分類軸の名前をすべて列挙し**、ダッシュボードの集計が変わる旨とあわせてダイアログに出す。負債はチェックボックスで複数の分類軸から独立に選べるため、同じ負債を2つ以上の軸が対象にしていることがある。件数だけを示す形は採らない — どの軸の集計が変わるかを確かめるためにB4を開き直させることになり、確認ダイアログがその場で判断させるためのものであるという目的を外れる。分類軸は多くても数件なので列挙が長くなりすぎることはない。**削除自体は禁止しない** — 分類軸から参照されているだけの負債まで消せなくすると、完済した負債を整理できなくなる(B8の対象分類がB4の削除を禁止しないのと同じ考え方)
- 保存はまとめて行い、一部だけ書き込まれた状態を残さない。途中で失敗した場合はその旨を表示し、画面の入力値は保持する

**バリデーション**

- 項目名が空、残債が空・数値でない・負の数 → インラインエラーを表示し、保存しない([DESIGN.md](../DESIGN.md) 6章)
- 金利が0未満・100超、残りの返済期間の「年」が0〜99の範囲外、「ヶ月」が0〜11の範囲外 → インラインエラーを表示し、保存しない(いずれも整数。総月数は最大1,199ヶ月になる)
- 発生年月が**当月より後**、または`yyyy-MM`として読めない値 → インラインエラーを表示し、保存しない。まだ借りていない負債を過去のグラフに反映させないため
  - 下限は**1900-01**とする。桁を打ち間違えた年(`0202`)を止める歯止めで、実在しうる借入年を締め出さない値に置く
  - **残債の履歴との前後関係はエラーにしない。** 履歴はユーザーに見えないところで積まれる記録なので、「最初の記録より後の発生年月」を入力エラーとして突き返すと、原因が画面から分からないまま保存できなくなる。この場合の集計上の扱いはB1側で決める(「負債を含む分類軸の集計」)
- 残りの返済期間は**片方の欄だけが入力された場合、空欄側を0として総月数へ正規化する**(年=5・ヶ月=空欄 → 60ヶ月)。エラーにはしない — 任意入力の欄で「5年ちょうど」を表すのに0の明示を強いるのは冗長なため。範囲チェックは入力された側の欄にだけ効く。**両方が空欄のときだけ「未登録」**として扱い、0ヶ月(=総月数0)と区別する(「入力項目の補足」)
- 項目名の重複は許す。同じ名前のカードローンを複数登録することがあり、識別はIDで行うため
- 項目名の文字数上限は**60文字**とし、B7の物件名に揃える(分類軸名の40文字ではなく物件名に合わせるのは、どちらもユーザーが名付ける管理対象そのもので、金融機関名を含む長めの名前が付くため)。上限値は定数と `firestore.rules` の両方に置き、値を揃える(物件名・分類軸名と同じ扱い)
- 登録できる負債の件数は**50件**までとする。B4の集計対象の選択肢がそのまま増えるため青天井にはせず、値は分類軸の集計対象の上限(`assetTypeNames` の50件)に揃える。分類軸が持つ負債IDの配列も同じ50件を上限とする。文字数上限と同じく、定数と `firestore.rules` の両方に置いて値を揃える

**遷移条件**

- 保存成功 → 画面に留まり完了メッセージを表示する(続けて別の負債を編集できるようにするため。B2の取込完了と同じ扱い)
- バリデーションエラー → インラインエラー表示、保存しない
- 共通ヘッダー/サイドバーから他の主要画面へ自由に遷移可能

**不動産のローン残高(B7)との関係**

B11の負債と、[B7 不動産登録・編集画面](./screen-requirements-real-estate.md#b7-不動産登録編集画面) のローン残高は**別々に管理し、どちらかがもう一方を参照することはしない**。役割が違うため。

| | 用途 | ダッシュボードの集計 |
|---|---|---|
| B7のローン残高 | 物件ごとの利ざや(時価 - ローン残高)を出すための項目 | **その物件をB4で「利ざやのみ反映」で選んだときだけ**、利ざやの中で差し引かれた形で入る |
| B11の負債 | 分類軸の集計対象として資産から差し引く | B4で選べば入る |

- 住宅ローンをB11にも登録するかはユーザーの判断に委ねる。ただし**同じローンを両方に入れ、同じ分類軸で「利ざやのみ反映」の物件とその負債を選ぶと、二重に差し引かれる**(B1「CSV取込データとの重複」)。物件とローンの結び付きをアプリが持たないため、突き合わせて防ぐことはできない
  - 二重にしない組み方は2つある — 物件を「利ざやのみ反映」で選び、そのローンはB11の負債として分類軸で選ばない(または登録しない)か、物件を時価で反映してローンはB11の負債として差し引く
  - **この関係が生まれたのは [B4-8](https://trello.com/c/8U3xoGJj) で物件を分類軸の集計対象にしてからである。** それ以前はB7のローン残高がダッシュボードに一切入らず、「両方に入れても二重に差し引かれることはない」と書いてあった。過去のコメントやコードにこの記述が残っていたら、本項が正
- B11の画面にはこの関係を注記として置く。注記が無いと、B7に入れたローンがどういうときにダッシュボードへ出るのかが画面から読めない
- 将来B6の利ざやをB11の負債から引く形にする場合は、両画面の結び付け方を含めて別途設計する(要件定義書 4.5の「複数ローンの紐付け」と同じ扱い)

**データの持ち方**

- 負債は `users/{uid}/debts/{debtId}` に1件1ドキュメントで持つ。項目名・発生年月・金利・残債・残りの返済期間(総月数)・最終更新日・登録日時を持ち、**残債の履歴は同じドキュメント内に「日付→残債」のマップとして持つ**
  - 発生年月は `yyyy-MM` の文字列で、未入力は`null`(金利・残りの返済期間と同じ扱い)。`firestore.rules` の許可キーと必須キーの両方に足し、**形だけ**を検査する
  - **「当月より後でない」ことはルールでは見ない。** `request.time`はUTCで、クライアントが入れるのはローカルの年月なので、月をまたぐ前後で正常な入力を弾きうる(`updatedAt`と同じ制約。[要件定義書](./fire-asset-management-requirements.md) 8.1)。判定は画面に持たせる
  - 履歴をサブコレクションにしない理由は、B1が負債の件数だけ問い合わせを増やさずに推移を描けるようにするため。手動更新の履歴は多くても年に数件で、ドキュメントサイズの上限に近づく増え方をしない
  - マップの値の形はルールでは検査しきれないため(`byType`・`assumptions`と同じ制約)、書き込み側のスキーマで担保する
  - **履歴の件数は600件を上限とする**(月1回の更新で50年分)。件数上限を持つのは`assumptions.entries`(200件)と同じ理由で、ルールに書く数値を実装時に決め打ちさせないため。この履歴は削除以外で減らず運用年数に応じて単調に増えるので、`byType`のように「資産種別の数で自然に頭打ちになる」性質に頼れない
  - 上限に達した場合は**保存を拒否し、その旨を表示する**。古い記録から捨てる案は採らない — 過去の資産推移グラフの値が、負債を更新しただけで黙って変わることになる。到達しない前提で置く歯止めであり、実際に達したなら履歴の持ち方から見直す
- `firestore.rules` に `users/{uid}/debts/{debtId}` の許可を追加する。既定拒否のままでは読み書きできない
- B4の分類軸(`users/{uid}/categoryAxes/{axisId}`)に負債IDの配列を足す。ルール側は `hasOnly` の許可キーと、**集計対象が空の分類軸だけ削除を許す条件**の両方を直す必要がある(負債だけが割り当てられた分類軸が削除できてしまうため)
