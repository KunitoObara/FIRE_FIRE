# 入出金明細CSV取込 要件定義書

## 1. 位置付け

本ドキュメントは [FIRE-FIRE 要件定義書](./fire-asset-management-requirements.md) 4.2節「マネーフォワードCSV連携」のうち、**入出金明細(取引データ)**の取込と、そこから導かれる収支の集計について詳細化したものである。フェーズとしては同7章の **Phase 2**(入出金明細CSV取込、収支サマリ)にあたる。

資産残高推移CSVの取込(Phase 1、実装済み)は本書の対象外である。両者は同じ [B2 CSV取込画面](./screen-requirements-dashboard.md#b2-csv取込画面) のタブに並ぶが、CSVの形・データモデル・冪等性の取り方がいずれも異なるため、共通するのは文字コードの判定とファイルサイズの歯止めだけになる。

**画面をまたぐ仕様をここに集約する。** 入出金明細の取込は B2(取り込む)・B3(一覧する)・B1(集計して見せる)の3画面に効き、「どの行を集計に数えるか」「費目とは何か」を画面ごとの文書に書くと同じ内容が3箇所に散る。画面固有の表示項目・操作・遷移条件は [screen-requirements-dashboard.md](./screen-requirements-dashboard.md) 側に置き、本書を参照する形にする([auth-login-requirements.md](./auth-login-requirements.md) が4.1節に対して持っているのと同じ関係)。

## 2. 対象CSVの形式

マネーフォワードの「家計簿 > 収入・支出詳細」からエクスポートしたCSVを対象とする。

### 2.1 列構成

```
"計算対象","日付","内容","金額（円）","保有金融機関","大項目","中項目","メモ","振替","ID"
```

| 列名 | 内容 | 必須 |
|---|---|---|
| 計算対象 | `1` = 家計簿の計算に含める / `0` = 含めない | ○ |
| 日付 | 取引日(`yyyy/MM/dd`) | ○ |
| 内容 | 摘要。B3の一覧・キーワード検索の対象 | ○ |
| 金額（円） | 符号付きの整数。**収入がプラス、支出がマイナス** | ○ |
| 保有金融機関 | 口座名 | ○ |
| 大項目 | 費目の上位(例:食費) | ○ |
| 中項目 | 費目の下位(例:外食) | ○ |
| メモ | ユーザーがマネーフォワード側で付けた自由記述 | — |
| 振替 | `1` = 自口座間の振替 / `0` = それ以外 | ○ |
| ID | マネーフォワードが取引に振る識別子 | ○ |

- **「必須」は列の存在を指し、値の非空は求めない。** 中項目・メモは未設定の取引がありうるので、空文字を正常な値として受ける。列そのものが無い場合はパース失敗とする(2.3)
- **知らない列は無視する。** マネーフォワードのエクスポートは非公式フォーマットで、列が追加されうる。必須列が揃っていれば取り込め、余分な列は捨てる
- 列の順序には依存しない。ヘッダー行の名前で引く
- **同じ名前の列が複数ある場合はパース失敗とする。** どちらを採るか決められないため(資産残高推移の `duplicate-column` と同じ扱い)

**公式な仕様書は存在しない。** 上記は現行のエクスポートを前提とした定義であり、実装時には手元のエクスポートのヘッダー行と突き合わせて確かめること。列名が変わっていた場合は、実装をこの表に合わせるのではなく本書を直す。

### 2.2 文字コードと書式

| | 扱い |
|---|---|
| 文字コード | Shift_JIS(CP932)を既定とし、UTF-8(BOM有無を問わず)も受ける。判定は資産残高推移と共通の `src/frontend/src/lib/csv/decode.ts` をそのまま使う |
| 日付 | `yyyy/MM/dd`。アプリ内では `yyyy-MM-dd`(`STORED_DATE_FORMAT`)に直して持つ |
| 金額 | 桁区切りのカンマ・先頭のマイナス記号を許す。小数は現れない前提だが、現れた場合はパース失敗とする(円未満の取引は無い) |

### 2.3 パース失敗の条件

失敗したときは**1件も取り込まない**。エラーを表示して画面に留まり、部分取込はしない(要件定義書 4.2、B2の遷移条件)。資産残高推移と共通の理由(`too-large` / `empty-file` / `unreadable` / `no-data-rows` / `too-many-rows` / `invalid-date` / `invalid-amount` / `missing-column` / `duplicate-column`)に加え、入出金明細では次を足す。

| 理由 | 条件 |
|---|---|
| `invalid-id` | `ID` 列の値がドキュメントIDとして使えない(3.2) |
| `duplicate-id` | 同一ファイル内に同じ `ID` の行が複数ある |
| `invalid-flag` | `計算対象` / `振替` が `0` / `1` 以外 |
| `too-long` | 文字列の列が3.1の上限を超えている |

**`duplicate-date` は入出金明細には無い。** 同じ日付に複数の取引があるのは正常な状態で、資産残高推移(1日1行)とは前提が逆になる。

## 3. データモデル

### 3.1 コレクション

取引1件を1ドキュメントとして `users/{userId}/transactions/{transactionId}` に保存する。

| フィールド | 型 | 上限 | 由来 |
|---|---|---|---|
| `date` | string (`yyyy-MM-dd`) | — | 日付 |
| `content` | string | 200文字 | 内容 |
| `amount` | number | — | 金額（円）。符号をそのまま保つ |
| `account` | string | 100文字 | 保有金融機関 |
| `categoryMajor` | string | 40文字 | 大項目 |
| `categoryMinor` | string | 40文字 | 中項目(未設定は空文字) |
| `memo` | string | 1,000文字 | メモ(未設定・列が無い場合は空文字) |
| `isTransfer` | boolean | — | 振替 = `1` |
| `isCalculationTarget` | boolean | — | 計算対象 = `1` |
| `importedAt` | timestamp | — | 取込日時 |

- **CSVの生ファイルは保存しない**(要件定義書 4.2)。上表の列の値だけがFirestoreへ渡る
- `計算対象` と `振替` は**捨てずに保存する**。集計から外す行(5章)を、取り込まないのではなく取り込んだうえで除くため
- 費目マスタは持たない。B3の費目セレクタの選択肢は、取り込んだ取引から動的に組み立てる(6章)

**文字数の上限**

**具体値を実装時の裁量に委ねず、ここで決めておく。** 他のユーザー入力文字列(B7の物件名60文字、B4の分類軸名40文字)は値と根拠をこの形で先に決めており、揃える。値は `src/frontend/src/constants/transactions-import.ts` と `firestore.rules` の両方に置き、一致させる。

- **費目(大項目・中項目)はB4の分類軸名と同じ40文字。** どちらも画面のセレクタに並ぶ分類の名前で、長さの想定が変わる理由が無い
- **口座名はB7の所在地と同じ100文字。** 金融機関名に支店・口座種別が付いても収まる
- **内容は200文字。** 店名や振込依頼人名が入る欄で、費目より長いが自由記述ほどではない
- **メモは1,000文字。** ユーザーがマネーフォワード側で書いた自由記述で、他と同じ桁に収める理由が無い

**上限を超える値があればパース失敗(`too-long`)とし、1件も取り込まない。** 切り詰めて通す案は採らない — 元のCSVを保存しない設計(要件定義書 4.2)なので、切り詰めた分は取り込み直しても戻らない。上限は現実の値より十分に大きく取ってあるため、超えるのは列がずれているなどファイルが想定と違うときであり、そこで止まるほうが正しい。

`firestore.rules` には次を要求する規則を足す。他のコレクションと同じく `canAccessOwnData()`(メール確認済み + TOTP検証済み + 本人)を前提とし、**`delete` は許可しない**(取引を消す画面が無いため。`assetSnapshots` と同じ扱い)。

- `keys().hasOnly([...])` で上表のフィールド以外を混ぜさせない
- `date` は `isIsoDate()`
- `amount` は数値、`content` / `account` / `categoryMajor` / `categoryMinor` / `memo` は文字列で、上表の文字数を `size()` で要求する
- `isTransfer` / `isCalculationTarget` は真偽値、`importedAt` は timestamp
- **ドキュメントIDの形も `matches()` で要求する**(3.2)。パス変数 `transactionId` に対して文字種と長さを見る

**ドキュメントIDの検証をルール側にも置くのは、冪等性がIDの形に依存しているため。** 3.2の検証をパーサーだけに置くと「クライアントの実装を信頼した検証」になり、SDKを直接叩く経路で形の崩れたIDのドキュメントが作れる。そうなると同じ取引が別IDで重複しうるが、4章の冪等性は「IDがマネーフォワードの値そのもの」であることに依存している。他のフィールドの制約をパーサーとルールの両方に置いているのと同じ扱いにする。

**他ユーザーのデータに届く穴ではない。** 書き込みは `canAccessOwnData()` で本人の領域に限定済みで、これは一貫性のための要求である。

`__…__` を弾く条件をルール側で重ねて書くかは実装時に決める。**Firestore自体がその形式のドキュメントIDを拒否する**ため、ルールで再度見ても増える保証が無い可能性がある。確かめたうえで、書かないと決めたならその理由をルールのコメントに残す。

取込履歴(`csvImports`)は資産残高推移と共通で、`typeId` に `'transaction'` を入れる。**この値は既にルールで許可済み**なので、履歴側のルール変更は要らない。

### 3.2 ドキュメントIDにマネーフォワードの `ID` を使う

`transactionId` は CSV の `ID` 列の値をそのまま使う。

ただしFirestoreのドキュメントIDには使えない値があるため、**`^[A-Za-z0-9_-]{1,200}$` に一致し、かつ `__` で始まって `__` で終わらないこと**を検証する。外れた行が1件でもあれば `invalid-id` としてファイル全体のパースを失敗させる。

- **加工して通す案は採らない。** 使えない文字を落としたりエンコードしたりすると、マネーフォワード側が同じ `ID` を返しているのにアプリ側のIDが実装の都合で決まることになり、加工規則を変えた瞬間に同じ取引が二重に入る
- 上限を200文字にしているのはFirestoreの上限(1500バイト)より十分に小さい値で足りるため。実際の `ID` はこれよりはるかに短い

## 4. 再取込の冪等性

**同じCSVを何度取り込んでも結果は同じになる。** 資産残高推移が「同じ日付を上書きする」ことで得ている性質(要件定義書 4.2)を、取引では「同じ `ID` を上書きする」ことで得る。

- 取込は `set`(マージなし)で行う。マネーフォワード側で費目を直してからエクスポートし直した場合、新しい値で置き換わる
- 期間の重なるファイルを続けて取り込んでも、重なった分は上書きされるだけで積み上がらない
- 書き込みは `writeBatch` を500件ずつに分ける(`FIRESTORE_BATCH_LIMIT`)。**途中で失敗したときは手前のバッチが残る**ので、資産残高推移と同じく「何件まで反映したか」を画面に伝え、取り込み直せば揃うことを添える(`buildPartialImportNotice`)

**却下した案**

- *日付+内容+金額+口座からハッシュを作る* — `ID` 列に依存しない利点はあるが、同日・同額・同内容の取引(交通費など)が実際に複数あり、1件に潰れて集計が狂う
- *取込対象期間の既存データを消してから入れ直す* — 重複は原理的に起きないが、削除と書き込みの間で失敗すると取引が消えたままになる。取引は再エクスポートすれば戻るとはいえ、失敗が「データが減る」方向に出る設計は避ける

## 5. 集計から外す行

**振替と計算対象外の行は、取り込んだうえで収支の集計から外す。**

| 行 | Firestoreへの保存 | 収支サマリ(B1)の集計 | 一覧(B3)の表示 |
|---|---|---|---|
| `isTransfer == true` | する | 含めない | する(除外の印を付ける) |
| `isCalculationTarget == false` | する | 含めない | する(除外の印を付ける) |
| それ以外 | する | 含める | する |

- **振替を数えないのは、自分の口座間の移動が収入と支出の両方に現れるため。** 銀行から証券口座へ100万円移すと `-1,000,000` と `+1,000,000` の2行が立ち、収支は0のまま収入と支出だけが100万円ずつ膨らむ。費目別支出でも実態のない支出が最上位に来る
- **計算対象を尊重するのは、それがマネーフォワード側でユーザーが下した判断そのものだから。** アプリ側で読み替える理由が無い
- **取り込まない案は採らない。** 取り込まないと、B3の一覧に出ない取引が生まれ、「取込に失敗したのか、除外されたのか」を画面から区別できなくなる。取り込んだうえで集計から外せば、B3で現物を確認できる
- B3では除外行にバッジ等の印を付ける。印が無いと、一覧の金額を足しても収支サマリの数字にならない理由が分からない

### 集計した値の符号

**収入も支出も0以上の値として持つ。** 収入は `amount > 0` の合計、支出は `amount < 0` の合計の**絶対値**で、`CashflowSummary.expense` と `ExpenseByCategory.amount` が負になることは無い。符号を落とすのは集計の時点で、表示側では反転しない。

生CSVの符号(支出がマイナス)をそのまま保つのは、Firestoreに保存する `Transaction.amount`(3.1)と、それを1件ずつ並べるB3の一覧だけである。

この取り決めが要るのは、B1の既存コンポーネントが**値を加工せずに受け取る契約**になっているため。`CashflowSummaryCard` は収支を `income - expense` で出し、支出も費目別支出も `formatJpy` へそのまま渡す。`formatJpy` は負の値を `- ¥ 84,200` と符号付きで整形するので、支出を負のまま渡すと次の2つが同時に起きる。

- 支出にマイナスが付く(「支出は絶対値で表示する」に反する)
- 収支が `income - (負の値)` すなわち `income + |支出|` になり、**赤字が黒字として出る**

型(`CashflowSummary` / `ExpenseByCategory`)にはこの取り決めが書かれていないため、実装時にコメントで残す。

## 6. 費目は大項目・中項目の2階層で持つ

CSVの `大項目` と `中項目` を両方保存する。

- **B1の費目別支出は大項目で集計する。** 中項目まで割ると項目数が多くなりすぎ、ダッシュボードのカードとして読めない
- **B3の絞り込みは大項目・中項目の両方を選べる。** 大項目を選ぶと中項目セレクタの選択肢がその配下に絞られ、大項目が未選択のときは全ての中項目を並べる
- 費目マスタ(B4の資産分類軸に相当するもの)は**持たない**。費目名はCSVの値そのもので、マネーフォワード側で追加・改名されうる。選択肢は取り込んだ取引から動的に組み立てる(口座名も同じ扱い)
- 中項目が空の取引は「(未分類)」等ではなく**空のまま**扱い、中項目セレクタの選択肢にも出さない。マネーフォワードが空で返しているものにアプリ側で名前を与えない

**表記ゆれをどこまで吸収するか**

費目名がCSVの値そのものである以上、同じ費目が違う文字列として現れうる。**前後の空白だけ落とし(trim)、それ以上の正規化はしない。**

- 前後の空白は**画面で見えない差**なので、残すと「見た目が同じなのに別々に集計される費目」が生まれる。ユーザーが原因を突き止めようがない差であり、落とす
- 全角/半角の違いや大文字小文字の違いは**画面で見える差**なので、統一しない。マネーフォワード側で別々の費目として立てているものを、アプリが同じものと決めつけることになる。口座名も同じ扱い
- 正規化を増やすほど、規則を変えたときに同じ費目が別物へ移る。`ID` を加工しないのと同じ理由で、加工は最小限にとどめる(3.2)
- **それでも表記ゆれが残れば、同じつもりの費目がB1の費目別支出とB3のセレクタに分裂して現れる。** これは不具合ではなく上記の方針の帰結で、直すなら費目マスタを持つ話になる(10章)

**却下した案**

- *大項目だけを保存する* — 型(`Transaction.category`)を変えずに済むが、中項目は再取込しないと戻らない。捨てる情報は保存しておいて表示側で畳むほうが安い
- *「食費/外食」のように連結した1文字列にする* — 情報は残るが、大項目での集計のたびに文字列を分解することになり、費目名に `/` が含まれると壊れる

## 7. 取込前のプレビュー

パースに成功したら、**取込を実行する前にプレビューを表示して確認を求める**(要件定義書 4.2、B2の遷移条件)。資産残高推移と同じ構成で、内容を入出金明細向けに置き換える。

| 項目 | 内容 |
|---|---|
| 件数 | 取り込む取引の件数。うち集計から外れる件数(振替・計算対象外)を内訳として添える |
| 期間 | 最も古い取引日 〜 最も新しい取引日 |
| サンプル行 | 先頭 `CSV_PREVIEW_ROW_LIMIT` 件(日付・内容・金額・口座・大項目/中項目) |
| 新規/上書きの内訳 | 既にFirestoreにある `ID` の件数を「上書き」として示す(資産残高推移の `AssetBalanceImportPlan` と同じ) |

「集計から外れる件数」をプレビューに出すのは、振替だらけのファイルを取り込んだときに収支サマリが動かない理由を、取込の前に分かるようにするため。

## 8. 上限と読み取りの制約

| | 値 | 理由 |
|---|---|---|
| ファイルサイズ | `MAX_CSV_FILE_BYTES`(5MB、資産残高推移と共通) | 取り違えて巨大なファイルを選んだときの歯止め |
| 1回に取り込める行数 | `MAX_TRANSACTION_ROWS` = 20,000 | 20,000件は500件ずつで40バッチ。これを超えるなら期間を分けてエクスポートしてもらう |
| B3が表示する件数 | `TRANSACTION_SCAN_LIMIT` = 9,999 | 打ち切りの判定に1件余分を読むため、`limit()` に渡すのは `+ 1` した10,000になる(下記)。**`FIRESTORE_QUERY_LIMIT_MAX`(10,000)を超えられないのは `limit()` に渡す値のほう**なので、表示件数側を1つ下げてある |

**取引は資産残高と違って際限なく増える。** 資産残高推移は当月が日次・それ以前は月末のみで10年分でも数百件にしかならないが、取引は月に数百件のペースで積み上がり、数年で `TRANSACTION_SCAN_LIMIT` に届く。したがって B3・B1 は全件を読まない。

- **B3は選択中の期間で範囲クエリを掛ける**(`where(date, >=, from)` + `where(date, <=, to)` + `orderBy(date, 'desc')` + `limit`)。既定の「直近1ヶ月」なら読むのは数百件で済む
- **費目・口座・キーワードの絞り込みと並び替えは、読み込んだ範囲に対してクライアント側で行う。** Firestoreの複合条件に載せると組み合わせごとに複合インデックスが要り、キーワードの部分一致は元々表現できない
- **打ち切りの判定は、選択中の期間で分岐しない。** 実際に上限へ達しやすいのは「全期間」だが、取引が増えれば短い期間でも起こる。`periodId === 'all'` で分岐すると、その日が来たときに黙って古い側が欠ける
- **`limit(TRANSACTION_SCAN_LIMIT + 1)` で1件余分に読み、`TRANSACTION_SCAN_LIMIT` 件を超えて返ってきたら打ち切りと判定する。** 表示に使うのは先頭の `TRANSACTION_SCAN_LIMIT` 件
  - 「取得件数が上限と一致したか」で判定すると、**該当件数がちょうど上限と同じだった場合にも打ち切りの案内が出る**。データは欠けていないので実害は小さいが、一度でも誤った案内を見ると、本当に打ち切られたときの案内も信じられなくなる
  - 取引は際限なく増えるデータなので、ちょうど一致する状況は他のコレクションより起こりやすい
  - **`+ 1` した値のほうが `FIRESTORE_QUERY_LIMIT_MAX` を超えてはならない。** 超えるとクエリが `invalid-argument` で拒否され1件も読めなくなる(B1-3で踏んだのと同じ罠)。`TRANSACTION_SCAN_LIMIT` を9,999にしてあるのはこのためで、`limit()` に渡る値がちょうど上限の10,000になる。**この2つの値は必ずセットで動かす**
- 打ち切ったときは**そのことを画面に出す**。黙って欠けると、一覧に無いことを「取り込んでいない」と読み違える
- **B1の収支サマリは当月だけを読む。** 表示するのが当月の収入・支出・費目別支出であり、それ以上を読む理由が無い
- 単一フィールドの範囲クエリなので**複合インデックスは要らない**(`firestore.indexes.json` の変更なし)

## 10. 今後の検討事項

- **マネーフォワード側で削除した取引がアプリに残り続ける。** 取込は追加と上書きだけで、消えた `ID` を検知する手段が無い。取引を削除する画面を設けるか、期間を指定した洗い替えを用意するかは、実際に困ってから決める
- **月次の収支推移グラフは本フェーズの範囲外。** 要件定義書 4.4 が求めているのは「月次収支・費目別支出」で、B1の収支サマリは当月を出す。過去の月を並べるかどうかは別途
- **表記ゆれで同じ費目が分裂したときに束ねる手段が無い。** 6章のとおり正規化は前後の空白までにとどめるため、全角/半角や大文字小文字が違う費目は別々に集計される。束ねるには費目マスタ(名前の別名を持つ仕組み)が要り、それは「費目マスタを持たない」という本書の前提そのものを覆す。実際に困ってから決める
- 費目別支出の予算・目標との比較(家計管理としての機能)は要件定義書に無く、FIRE進捗の可視化という本アプリの目的からも外れるため対象外とする
- 複数口座で同じ取引が二重計上される(同じ買い物がカードと銀行の両方に現れる)ケースの扱い。マネーフォワード側が振替として印を付けていれば5章で外れるが、付いていない場合は検知できない
