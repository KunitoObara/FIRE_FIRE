# 画面要件定義書:認証系画面(A1〜A8)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.1節の認証系画面(A1〜A8)について、画面ごとの要件を詳細化したものである。認証方式の全体方針は [ログイン画面・認証機能 要件定義書](./auth-login-requirements.md) を参照。

## 2. ソーシャルログイン導線の共通仕様(A1・A4)

Googleによるソーシャルログイン([auth-login-requirements.md](./auth-login-requirements.md) 3.8)は、A1とA4に同一の「Googleで続ける」ボタンとして設置する。Google側ではサインアップとログインを区別できないため、どちらの画面から開始しても処理は共通で、遷移先だけが結果によって変わる。

| 区分 | 項目 |
|---|---|
| 表示項目 | 「または」区切り線、Googleブランドアイコン付きボタン |
| 主な操作 | 「Googleで続ける」ボタン |

- ボタンはメール/パスワードのフォームの下、区切り線を挟んで配置する。ソーシャルログインを主導線に見せないため、スタイルはアウトライン(副次ボタン)とする
- 押下でGoogleのサインインポップアップを開く。ポップアップが閉じられた/キャンセルされた場合はエラーを表示せず元の画面に留まる
- ポップアップがブラウザにブロックされた場合のみ、画面内に「ポップアップを許可してください」の旨をエラー表示する
- 処理中はボタンを無効化し、二重にポップアップを開かせない

**共通の遷移条件**

- Googleログイン成功・新規アカウント作成 → メールアドレスはGoogle側で確認済みのため**A2をスキップ**し、**A3 2FA登録画面** へ遷移
- Googleログイン成功・既存アカウントで2FA未登録 → **A3 2FA登録画面** へ遷移
- Googleログイン成功・既存アカウントで2FA登録済み → **A5 2FA検証画面** へ遷移
- 同一メールアドレスのパスワードアカウントが既に存在(`auth/account-exists-with-different-credential`) → **A8 アカウント連携画面** へ遷移
- ポップアップを閉じた/キャンセル → 遷移せず、元の画面に留まる(エラー表示もしない)
- 通信失敗・プロバイダ未設定等 → 画面内にフォーム全体のエラーとして表示、遷移しない

## A1. サインアップ画面

- **画面目的**: 新規ユーザーがメールアドレス・パスワードでアカウントを作成する

| 区分 | 項目 |
|---|---|
| 表示項目 | 画面タイトル、パスワードポリシーの充足状況(リアルタイム更新)、利用規約・プライバシーポリシーへのリンク、ログイン画面への導線 |
| 入力項目 | メールアドレス、パスワード、パスワード(確認用)、利用規約・プライバシーポリシー同意チェックボックス |
| 主な操作 | 「アカウント作成」ボタン、パスワード表示/非表示トグル、「Googleで続ける」ボタン(2章の共通仕様) |

**パスワード表示/非表示トグル**

- パスワード欄・パスワード(確認用)欄それぞれの右端に目のアイコンを置き、押下で入力値の平文表示と伏字表示を切り替える
- 2つの欄のトグルは独立して動作する(一方を平文にしても他方は伏字のまま)
- 初期状態は伏字

**入力内容の確認モーダル**

「アカウント作成」ボタン押下では直接アカウントを作成せず、確認モーダルを表示する。

| 区分 | 項目 |
|---|---|
| 表示項目 | 入力したメールアドレス、パスワード(伏字。実際の文字数を伏せるため入力値の長さに依らない固定長)、「以上の内容でアカウント作成します」 |
| 主な操作 | 「もどる」ボタン、「はい」ボタン |

- バリデーションエラーがある場合はモーダルを表示せず、画面内にインラインエラーを表示する
- 「もどる」押下 → モーダルを閉じる。入力値は保持し、アカウントは作成しない
- 「はい」押下 → アカウント作成を実行する

**遷移条件**

- 入力値バリデーションOK(メール形式・パスワードポリシー・パスワード一致・規約同意チェック済み) → 入力内容の確認モーダルを表示(この時点ではアカウントを作成しない)
- モーダルで「はい」押下かつメールアドレス未登録 → アカウント作成 → 確認メール送信 → **A2 メールアドレス確認待ち画面** へ遷移
- モーダルで「もどる」押下 → モーダルを閉じ、A1に留まる
- バリデーションエラー(メール形式不正、パスワードポリシー違反、パスワード不一致、規約未同意) → モーダルを表示せず画面内にエラー表示、遷移しない
- メールアドレス重複 → 画面内にエラー表示、遷移しない
- 通信失敗・レート制限等でアカウント作成に失敗 → フォーム全体のエラーとして画面内に表示、遷移しない
- 「ログインはこちら」リンク押下 → **A4 ログイン画面** へ遷移
- 「Googleで続ける」ボタン押下 → 2章の共通仕様に従う。ただしA1では**利用規約・プライバシーポリシー同意チェックが未チェックの場合はポップアップを開かず**、チェックボックスのインラインエラーを表示する(新規登録の同意取得はメール/パスワードとGoogleで差を付けない)

## A2. メールアドレス確認待ち画面

- **画面目的**: サインアップ直後にメールアドレスの確認を促す

| 区分 | 項目 |
|---|---|
| 表示項目 | 送信先メールアドレス、確認手順の案内文、再送結果のメッセージ、サインアップ画面へのやり直し導線 |
| 入力項目 | なし |
| 主な操作 | 「確認メールを再送する」ボタン |

**確認完了の検知**

確認リンクは別タブ・別デバイスで開かれるためこの画面へ通知が来ない。そのため一定間隔のポーリングと、タブが表示状態に戻った時点の再確認で確認完了を検知し、ユーザー操作なしにA3へ進む。「確認しました」のようなボタンは置かない。

**確認メールの再送**

- 押下後は一定時間(60秒)ボタンを無効化し、残り秒数を表示する。Firebase Authenticationのレート制限(3.7節のとおり追加のロック機構は実装しない方針)に当たる前に、ユーザーに分かる形で連打を止めるため
- **リクエストがFirebaseに届いた失敗(レート制限・原因不明)でも同じクールダウンを置く**。レート制限に当たった直後こそ連打を止める必要があるため
- 逆に**リクエストがFirebaseに届かなかった失敗(接続不可・設定不足)ではクールダウンを置かない**。原因がローカル環境側にあり、直したらすぐ再試行できる方がよいため
- 再送の成否は画面内のメッセージで伝える(成功・レート制限・接続不可・設定不足・原因不明)。下記のセッション喪失を除き、いずれの場合も画面を離れない

**遷移条件**

- メール内リンクをクリックして確認完了 → **A3 2FA登録画面** へ遷移
- 「確認メールを再送する」ボタン押下 → 確認メールを再送し、画面はそのまま留まる
- セッションが無い状態でこの画面に到達(直接アクセス・セッション期限切れ) → **A1 サインアップ画面** へ遷移。送信先の表示も再送もサインイン中のユーザーを前提とするため
- 画面に滞在中、再送操作時にセッション喪失を検知(トークン期限切れ・ユーザー削除) → **A1 サインアップ画面** へ遷移。再送先のユーザーが失われており、その場での再送も確認完了の検知も成立しないため
- 「サインアップからやり直してください」リンク押下 → **A1 サインアップ画面** へ遷移

## A3. 2FA登録画面

- **画面目的**: TOTP認証アプリ(Google Authenticator等)と連携し、2FAを有効化する。サインアップ完了の必須ステップ

| 区分 | 項目 |
|---|---|
| 表示項目 | QRコード、手動入力用シークレットキー、(検証成功後)リカバリーコード一覧 †  |
| 入力項目 | 認証アプリの確認コード(6桁) |
| 主な操作 | 「確認する」ボタン、(検証成功後)「保存しました。開始する」ボタン |

**遷移条件**

- 確認コード検証成功 → リカバリーコードを表示 † → ユーザーが保存を確認して「開始する」ボタン押下 → **B1 ダッシュボード画面** へ遷移
- 確認コード誤り → エラー表示、再入力可能

> † **リカバリーコードは未実装。** [auth-login-requirements.md](auth-login-requirements.md) 3.3 でリカバリー手段はオープン課題とされており、Identity Platformにもバックアップコードの機能が無い(Cloud Functions + Firestoreでの自前実装が必要)ため、A3本体から切り出してTrelloカード [A3-2] 2FAリカバリーコード で扱う。
>
> 現在の実装は、確認コードの検証成功後にリカバリーコードを出さず「2段階認証の設定が完了しました」の表示と「開始する」ボタンのみを出してB1へ進む。[A3-2] の実装時に、上記†の記述どおりリカバリーコード一覧の表示とダウンロードを差し込む。

## A4. ログイン画面

- **画面目的**: 既存ユーザーがメールアドレス・パスワードで一次認証を行う

| 区分 | 項目 |
|---|---|
| 表示項目 | サインアップ画面への導線 |
| 入力項目 | メールアドレス、パスワード、「ログイン状態を保持する」チェックボックス |
| 主な操作 | 「ログイン」ボタン、「パスワードをお忘れの方」リンク、「Googleで続ける」ボタン(2章の共通仕様) |

**遷移条件**

- 認証成功(2FA登録済み) → **A5 2FA検証画面** へ遷移
- 認証失敗(メールアドレス/パスワード誤り、アカウント無効化) → エラーメッセージ表示、遷移しない。理由は区別せず「メールアドレスまたはパスワードが正しくありません」として表示する(「未登録」「無効化済み」のように状態を伝えると、そのメールアドレスが登録されているかどうかを外部から判定できてしまうため)
- メール未確認のアカウントでログイン試行 → **A2 メールアドレス確認待ち画面** へ誘導
- メール確認済みで2FA未登録のアカウントでログイン試行 → **A3 2FA登録画面** へ誘導。2FAは全ユーザー必須([auth-login-requirements.md](auth-login-requirements.md) 3.3)のため、サインアップを途中で離脱したアカウントを未完了の手順まで戻す
- 「パスワードをお忘れの方」リンク押下 → **A6 パスワードをお忘れの方画面** へ遷移
- 「アカウントをお持ちでない方」リンク押下 → **A1 サインアップ画面** へ遷移
- 「Googleで続ける」ボタン押下 → 2章の共通仕様に従う

> 「ログイン状態を保持する」の選択は、一次認証の実行前にFirebase Authのセッション永続化方式へ反映する(チェック時はブラウザを閉じても保持、未チェック時はタブを閉じると失効)。既定はチェック済み。2FAありのログインで実際にセッションが作られるのはA5の検証成功時のため、A5もこの選択を引き継ぐ。Googleログイン・A8のアカウント連携も同じくA4での選択を引き継ぐ。

## A5. 2FA検証画面

- **画面目的**: 一次認証成功後、認証アプリの確認コードによる二次認証を行う。一次認証の手段(メール/パスワード、Google、A8のアカウント連携)を問わず共通で通る

| 区分 | 項目 |
|---|---|
| 表示項目 | 一次認証済みのメールアドレス(確認表示) |
| 入力項目 | 確認コード(6桁)。「リカバリーコードを使う」への切り替え可能 † |
| 主な操作 | 「検証する」ボタン、「リカバリーコードを使う」リンク † |

**遷移条件**

- 確認コード(またはリカバリーコード †)検証成功 → **B1 ダッシュボード画面** へ遷移(「ログイン状態を保持する」チェック時はセッション有効期間を延長)
- A8から到達した場合のみ、検証成功後に**Googleアカウントの連携を実行してから**B1へ遷移する。連携に失敗した場合はサインイン自体は成立しているためB1へ進み、連携できなかった旨をB1側で通知する(ログインをやり直させない)。通知の文言・表示条件は [screen-requirements-dashboard.md](./screen-requirements-dashboard.md) B1「Googleアカウント連携の失敗通知」を参照
- 検証失敗 → エラー表示、再入力可能
- リカバリーコード使用時、使用済みコードは以後無効化する †

> † A3と同じく、リカバリーコード関連はTrelloカード [A3-2] 2FAリカバリーコード で扱う。A5を先に実装する場合は、認証アプリの確認コードによる検証のみを実装し、「リカバリーコードを使う」導線は [A3-2] で追加する。
>
> 現在の実装は上記のとおり確認コードによる検証のみで、「リカバリーコードを使う」導線は出さない(HTMLモック `src/frontend/docs/html_mock/a5-mfa-verify.html` には含まれているが、[A3-2] で差し込む)。検証セッションはA4からメモリ上でのみ受け渡すため、A5を直接開いた場合やリロードした場合は自動でA4へ戻す。検証セッションの期限切れはA5に留まってエラーを表示し、「ログイン画面へ」の導線からA4へ戻ってもらう。

## A6. パスワードをお忘れの方画面

- **画面目的**: パスワードを忘れたユーザーがリセットメールを受け取るための入力画面

| 区分 | 項目 |
|---|---|
| 表示項目 | 案内文、ログイン画面への導線 |
| 入力項目 | メールアドレス |
| 主な操作 | 「リセットメールを送信する」ボタン |

**遷移条件**

- 送信操作後 → 送信完了メッセージを画面内に表示(未登録メールアドレスでも同一メッセージを表示し、アカウントの存在有無を推測されないようにする)。画面遷移はしない
- 「ログインに戻る」リンク押下 → **A4 ログイン画面** へ遷移

> Googleのみで作成されたアカウント(パスワード未設定)のメールアドレスが入力された場合、リセットメールは実際には送信されない。上記のとおりアカウントの存在有無を伏せる方針のため、画面表示は送信完了時と同一のメッセージとする。

## A7. パスワード再設定画面

- **画面目的**: リセットメールのリンクから遷移し、新しいパスワードを設定する

| 区分 | 項目 |
|---|---|
| 表示項目 | (リンク無効・期限切れ時の)エラー案内 |
| 入力項目 | 新パスワード、新パスワード(確認用) |
| 主な操作 | 「パスワードを再設定する」ボタン |

**遷移条件**

- 再設定成功 → 完了メッセージ表示後、**A4 ログイン画面** へ遷移
- リンクが無効・期限切れ → エラー表示し、**A6 パスワードをお忘れの方画面** への再遷移導線を表示
- パスワードポリシー違反・確認用不一致 → インラインエラー表示、遷移しない

## A8. アカウント連携画面

- **画面目的**: 既存のメール/パスワードアカウントと同一のメールアドレスでGoogleログインが行われたとき、パスワードによる本人確認を経て両プロバイダを同一アカウントに連携する

| 区分 | 項目 |
|---|---|
| 表示項目 | 対象のメールアドレス(Googleから取得したもの)、連携が必要な理由の案内文、連携せずにログイン画面へ戻る導線 |
| 入力項目 | パスワード(既存アカウントのもの) |
| 主な操作 | 「連携してログイン」ボタン、パスワード表示/非表示トグル、「パスワードをお忘れの方」リンク |

**到達条件**

A1・A4の「Googleで続ける」でGoogleログインを実行し、同一メールアドレスのパスワードアカウントが既に存在する場合(`auth/account-exists-with-different-credential`)にのみ到達する。Identity Platformの「メールアドレスごとに1つのアカウント」設定が有効であることが前提([auth-login-requirements.md](auth-login-requirements.md) 3.8)。

**案内文の方針**

「このメールアドレスは既にパスワードでご登録済みです。パスワードを入力すると、次回からGoogleでもログインできるようになります」のように、**エラーではなく追加の手続き**として提示する。既存アカウントを乗っ取られたような印象を与えない。

**連携の実行タイミング**

- パスワード検証だけではサインインが完了しない(2FA登録済みユーザーは `auth/multi-factor-auth-required` となる)ため、**A5の2FA検証成功後にGoogleアカウントの連携を実行する**
- 2FA未登録の既存アカウント(サインアップを途中離脱したケース)ではパスワード検証時点でサインインが成立するため、その場で連携を実行してからA3へ進む
- 連携待ちのGoogle資格情報はA5の検証セッションと同じくメモリ上でのみ受け渡す。短命なOAuthクレデンシャルであり、永続化すると期限切れの資格情報で連携を試みることになるため

**遷移条件**

- パスワード検証成功(2FA登録済み) → **A5 2FA検証画面** へ遷移し、検証成功後に連携を実行して **B1 ダッシュボード画面** へ
- パスワード検証成功(2FA未登録) → 連携を実行し、**A3 2FA登録画面** へ遷移(2FAは全ユーザー必須のため)
- パスワード誤り → インラインエラー表示、再入力可能。この画面に到達している時点でメールアドレスの登録は確定しているため、A4のような曖昧化(「メールアドレスまたはパスワードが正しくありません」)は行わず「パスワードが正しくありません」と表示する
- 「連携せずにログインへ戻る」リンク押下 → Googleログインを取りやめ、**A4 ログイン画面** へ遷移
- 「パスワードをお忘れの方」リンク押下 → **A6 パスワードをお忘れの方画面** へ遷移
- 連携セッションが無い状態でこの画面に到達(直接アクセス・リロード) → **A4 ログイン画面** へ自動で遷移。A5と同じく、メモリ上の資格情報が失われた状態では処理を続行できないため

> メール未確認のパスワードアカウントに、同一メールアドレスのGoogleを連携した場合の `emailVerified` の扱いはIdentity Platform側の挙動に依存する。連携後も未確認のまま残るならA2へ誘導する必要があるため、実装時に `fire-fire-dev` で実挙動を確認する。
