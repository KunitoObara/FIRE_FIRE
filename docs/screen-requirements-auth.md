# 画面要件定義書:認証系画面(A1〜A8)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.1節の認証系画面(A1〜A8)について、画面ごとの要件を詳細化したものである。認証方式の全体方針は [ログイン画面・認証機能 要件定義書](./auth-login-requirements.md) を参照。

## 2. ソーシャルログイン導線の共通仕様(A1・A4)

Googleによるソーシャルログイン([auth-login-requirements.md](./auth-login-requirements.md) 3.8)は、A1とA4に同一の「Googleで続ける」ボタンとして設置する。Google側ではサインアップとログインを区別できないため、どちらの画面から開始しても処理は共通で、遷移先だけが結果によって変わる。

| 区分 | 項目 |
|---|---|
| 表示項目 | 「または」区切り線、Googleブランドアイコン付きボタン |
| 主な操作 | 「Googleで続ける」ボタン |

- ボタンはメール/パスワードのフォームの下、区切り線を挟んで配置する。ソーシャルログインを主導線に見せないため、スタイルはアウトライン(副次ボタン)とする
- 押下でGoogleのサインインポップアップを開く。ポップアップが閉じられた/キャンセルされた場合はエラーを表示せず元の画面に留まる
- ポップアップがブラウザにブロックされた場合のみ、画面内に「ポップアップを許可してください」の旨をエラー表示する
- 処理中はボタンを無効化し、二重にポップアップを開かせない
- **A1では、利用規約・プライバシーポリシーへの同意チェックが済むまでボタンを無効化し、押せない理由をボタンの下に添える。** Googleで作成する場合も同意は必要で、ポップアップを開かせてから断るより開く前に条件が分かる方が親切なため。A4にはこのチェックボックスが無いので常に押せる

**Googleログインの共通の遷移条件**

- Googleログイン成功・新規アカウント作成 → メールアドレスはGoogle側で確認済みのため**A2をスキップ**し、**A3 2FA登録画面** へ遷移
- Googleログイン成功・既存アカウントで2FA未登録 → **A3 2FA登録画面** へ遷移
- Googleログイン成功・既存アカウントで2FA登録済み → **A5 2FA検証画面** へ遷移
- 同一メールアドレスのパスワードアカウントが既に存在(`auth/account-exists-with-different-credential`) → **A8 アカウント連携画面** へ遷移
- ポップアップを閉じた/キャンセル → 遷移せず、元の画面に留まる(エラー表示もしない)
- 通信失敗・プロバイダ未設定等 → 画面内にフォーム全体のエラーとして表示、遷移しない

## 3. 認証フロー途中のログアウト導線の共通仕様(A2・A3)

A2・A3はFirebase上ではサインイン済みだが、メールアドレス確認(A2)・2FA登録(A3)が終わっていないため主要機能に進めない状態である。この状態のユーザーは、URLでB1〜B10を直接叩いてもガードによってA2/A3へ差し戻されるため、**そのままでは別のアカウントでログインし直す手段が無い**。行き止まりを避けるため、両画面に同一のログアウト導線を置く。

| 区分 | 項目 |
|---|---|
| 主な操作 | 「別のアカウントでログイン」リンク |

- 文言は「ログアウト」ではなく **「別のアカウントでログイン」** とする。この状態のユーザーが求めているのはサインイン状態の終了そのものではなくアカウントの切り替えであり、実行内容(セッションの破棄)は同じでも目的が伝わる方を採る
- 実行内容はログイン後のログアウトと同一で、確認ダイアログを挟む点も共通([screen-requirements-account.md](./screen-requirements-account.md) 2章)。ただしダイアログの**注記だけ**は「未完了の手順が残っている」旨に差し替える(A2 はメールアドレスの確認、A3 は2FAの登録)。この状態では TOTP が未登録で、共通ヘッダー版の「再ログインには認証アプリの確認コードが必要」が事実と異なるため。出し分けの正は account.md 2章の表
- 画面下部の補助的な導線として置く。A2の主導線は確認メールの受信待ち、A3の主導線は認証アプリの登録であり、そちらより目立たせない

**共通の遷移条件**

- 「別のアカウントでログイン」リンク押下 → 確認ダイアログを表示 → 「ログアウトする」でセッションを破棄し **A4 ログイン画面** へ遷移(履歴を置き換える)
- 確認ダイアログで「キャンセル」 → ダイアログを閉じ、元の画面(A2 / A3)に留まる

> A5・A8にこの導線は置かない。どちらもまだサインインが成立していない段階で、破棄すべきセッションが無く、既存の「ログイン画面へ」(A5)・「連携せずにログインへ戻る」(A8)がそのまま離脱手段になっているため。
>
> A2には既に「サインアップからやり直してください」→A1の導線があるが、これは**同じアカウントでサインアップをやり直す**ための導線であり、別のアカウントに切り替える用途は満たさない。両方を併置する。

## A1. サインアップ画面

- **画面目的**: 新規ユーザーがメールアドレス・パスワードでアカウントを作成する

| 区分 | 項目 |
|---|---|
| 表示項目 | 画面タイトル、パスワードポリシーの充足状況(リアルタイム更新)、利用規約・プライバシーポリシーへのリンク、ログイン画面への導線 |
| 入力項目 | メールアドレス、パスワード、パスワード(確認用)、利用規約・プライバシーポリシー同意チェックボックス |
| 主な操作 | 「アカウント作成」ボタン、パスワード表示/非表示トグル、「Googleで続ける」ボタン(2章の共通仕様) |

**パスワード表示/非表示トグル**

- パスワード欄・パスワード(確認用)欄それぞれの右端に目のアイコンを置き、押下で入力値の平文表示と伏字表示を切り替える
- 2つの欄のトグルは独立して動作する(一方を平文にしても他方は伏字のまま)
- 初期状態は伏字

**入力内容の確認モーダル**

「アカウント作成」ボタン押下では直接アカウントを作成せず、確認モーダルを表示する。

| 区分 | 項目 |
|---|---|
| 表示項目 | 入力したメールアドレス、パスワード(伏字。実際の文字数を伏せるため入力値の長さに依らない固定長)、「以上の内容でアカウント作成します」 |
| 主な操作 | 「もどる」ボタン、「はい」ボタン |

- バリデーションエラーがある場合はモーダルを表示せず、画面内にインラインエラーを表示する
- 「もどる」押下 → モーダルを閉じる。入力値は保持し、アカウントは作成しない
- 「はい」押下 → アカウント作成を実行する

**遷移条件**

- 入力値バリデーションOK(メール形式・パスワードポリシー・パスワード一致・規約同意チェック済み) → 入力内容の確認モーダルを表示(この時点ではアカウントを作成しない)
- モーダルで「はい」押下かつメールアドレス未登録 → アカウント作成 → 確認メール送信 → **A2 メールアドレス確認待ち画面** へ遷移
- モーダルで「もどる」押下 → モーダルを閉じ、A1に留まる
- バリデーションエラー(メール形式不正、パスワードポリシー違反、パスワード不一致、規約未同意) → モーダルを表示せず画面内にエラー表示、遷移しない
- メールアドレス重複 → 画面内にエラー表示、遷移しない
- 通信失敗・レート制限等でアカウント作成に失敗 → フォーム全体のエラーとして画面内に表示、遷移しない
- 「ログインはこちら」リンク押下 → **A4 ログイン画面** へ遷移
- 「Googleで続ける」ボタン押下 → 2章の共通仕様に従う。ただしA1では**利用規約・プライバシーポリシー同意チェックが未チェックの場合はポップアップを開かず**、2章のとおりボタン自体を無効化して押せない理由を添える(新規登録の同意取得はメール/パスワードとGoogleで差を付けない)
  - 既にGoogleで登録済みのユーザーがA4ではなくA1から「Googleで続ける」を押した場合も、同様に同意チェックを求める。**これは意図した仕様**である。Google側ではサインアップとログインを区別できず、押下前に既存ユーザーかどうかを判定できないため、A1では常に同意済みを条件とする。既存ユーザーにはA4側にも同じ導線があり、そちらを使えばチェックは不要

## A2. メールアドレス確認待ち画面

- **画面目的**: サインアップ直後にメールアドレスの確認を促す

| 区分 | 項目 |
|---|---|
| 表示項目 | 送信先メールアドレス、確認手順の案内文、再送結果のメッセージ、サインアップ画面へのやり直し導線 |
| 入力項目 | なし |
| 主な操作 | 「確認メールを再送する」ボタン、「別のアカウントでログイン」リンク(3章の共通仕様) |

**確認完了の検知**

確認リンクは別タブ・別デバイスで開かれるためこの画面へ通知が来ない。そのため一定間隔のポーリングと、タブが表示状態に戻った時点の再確認で確認完了を検知し、ユーザー操作なしにA3へ進む。「確認しました」のようなボタンは置かない。

確認リンク自体の受け口は、A7と共通のアクションURL `/auth/action`(`mode=verifyEmail`)である。リンクを開いた側のタブでは確認の適用と結果表示だけを行い、サインイン状態を前提にしない(別のブラウザ・別の端末で開かれうるため)。次の手順へ進めるのは、上記のポーリングを行っているこの画面の側とする。

**確認メールの再送**

- 押下後は一定時間(60秒)ボタンを無効化し、残り秒数を表示する。Firebase Authenticationのレート制限(3.7節のとおり追加のロック機構は実装しない方針)に当たる前に、ユーザーに分かる形で連打を止めるため
- **リクエストがFirebaseに届いた失敗(レート制限・原因不明)でも同じクールダウンを置く**。レート制限に当たった直後こそ連打を止める必要があるため
- 逆に**リクエストがFirebaseに届かなかった失敗(接続不可・設定不足)ではクールダウンを置かない**。原因がローカル環境側にあり、直したらすぐ再試行できる方がよいため
- 再送の成否は画面内のメッセージで伝える(成功・レート制限・接続不可・設定不足・原因不明)。下記のセッション喪失を除き、いずれの場合も画面を離れない

**遷移条件**

- メール内リンクをクリックして確認完了 → **A3 2FA登録画面** へ遷移
- 「確認メールを再送する」ボタン押下 → 確認メールを再送し、画面はそのまま留まる
- セッションが無い状態でこの画面に到達(直接アクセス・セッション期限切れ) → **A1 サインアップ画面** へ遷移。送信先の表示も再送もサインイン中のユーザーを前提とするため
- 画面に滞在中、再送操作時にセッション喪失を検知(トークン期限切れ・ユーザー削除) → **A1 サインアップ画面** へ遷移。再送先のユーザーが失われており、その場での再送も確認完了の検知も成立しないため
- 「サインアップからやり直してください」リンク押下 → **A1 サインアップ画面** へ遷移
- 「別のアカウントでログイン」リンク押下 → 確認ダイアログを経てログアウトし、**A4 ログイン画面** へ遷移(3章の共通仕様)

## A3. 2FA登録画面

- **画面目的**: TOTP認証アプリ(Google Authenticator等)と連携し、2FAを有効化する。サインアップ完了の必須ステップ

| 区分 | 項目 |
|---|---|
| 表示項目 | QRコード、手動入力用シークレットキー、(検証成功後)リカバリーコード一覧  |
| 入力項目 | 認証アプリの確認コード(6桁) |
| 主な操作 | 「確認する」ボタン、(検証成功後)「リカバリーコードをダウンロード」ボタン・「保存しました。開始する」ボタン、「別のアカウントでログイン」リンク(3章の共通仕様) |

**遷移条件**

- 確認コード検証成功 → リカバリーコードを発行して一覧表示 → ユーザーが保存を確認して「保存しました。開始する」ボタン押下 → **B1 ダッシュボード画面** へ遷移
- 確認コード誤り → エラー表示、再入力可能
- リカバリーコードの発行時にセッションが失われていた → **A4 ログイン画面** へ遷移。2FAの登録は済んでいるため、QRコード生成時の同じ失敗(A1へ戻す)とは戻し先が異なる
- 「別のアカウントでログイン」リンク押下 → 確認ダイアログを経てログアウトし、**A4 ログイン画面** へ遷移(3章の共通仕様)
  - この導線は**QRコードを表示している登録前の状態でのみ出す**。確認コードの検証に成功したあと(リカバリーコードの表示中)は出さない。表示中のリカバリーコードは平文が手に入る最後の機会で、ここでログアウトさせると保管前に失われるため。この状態から抜けたい場合は「保存しました。開始する」でB1へ進み、共通ヘッダーからログアウトする

> リカバリーコードの仕様(本数・形式・保存方法・使用時の動作)は [auth-login-requirements.md](auth-login-requirements.md) 3.3 を参照。平文が手に入るのはこの表示だけで、画面を離れると再表示できない(その場合はB10で再発行する)。
>
> リカバリーコードの発行に失敗した場合も、2FAの登録自体は成立している。この画面で行き止まりにしないよう、「2段階認証の設定が完了しました」の表示のまま「リカバリーコードを再発行する」とB1へ進む導線を出し、あとからB10で発行できることを伝える。

## A4. ログイン画面

- **画面目的**: 既存ユーザーがメールアドレス・パスワードで一次認証を行う

| 区分 | 項目 |
|---|---|
| 表示項目 | サインアップ画面への導線、(ログアウト直後のみ)「ログアウトしました」の表示 |
| 入力項目 | メールアドレス、パスワード、「ログイン状態を保持する」チェックボックス |
| 主な操作 | 「ログイン」ボタン、「パスワードをお忘れの方」リンク、「Googleで続ける」ボタン(2章の共通仕様) |

**遷移条件**

- 認証成功(2FA登録済み) → **A5 2FA検証画面** へ遷移
- 認証失敗(メールアドレス/パスワード誤り、アカウント無効化) → エラーメッセージ表示、遷移しない。理由は区別せず「メールアドレスまたはパスワードが正しくありません」として表示する(「未登録」「無効化済み」のように状態を伝えると、そのメールアドレスが登録されているかどうかを外部から判定できてしまうため)
- メール未確認のアカウントでログイン試行 → **A2 メールアドレス確認待ち画面** へ誘導
- メール確認済みで2FA未登録のアカウントでログイン試行 → **A3 2FA登録画面** へ誘導。2FAは全ユーザー必須([auth-login-requirements.md](auth-login-requirements.md) 3.3)のため、サインアップを途中で離脱したアカウントを未完了の手順まで戻す
- 「パスワードをお忘れの方」リンク押下 → **A6 パスワードをお忘れの方画面** へ遷移
- 「アカウントをお持ちでない方」リンク押下 → **A1 サインアップ画面** へ遷移
- 「Googleで続ける」ボタン押下 → 2章の共通仕様に従う
- ログアウト([auth-login-requirements.md](auth-login-requirements.md) 3.9)から到達 → 画面内に「ログアウトしました」を表示する。ログアウト操作の結果がここで初めて画面に出るため

**「ログアウトしました」の表示**

- ログアウト後の遷移先を専用の完了画面にせずA4に合流させる方針([screen-list-and-transitions.md](./screen-list-and-transitions.md) 2.6)のため、操作が成功したことをA4側で伝える
- ログアウト直後の1回だけ表示する。ガードによる差し戻しやセッション期限切れでA4に来た場合は表示しない — 自分でログアウトしていないのに「ログアウトしました」と出ると、意図しないログアウトが起きたように読めるため
- リロードすると消えてよい。ログアウトは成功しており、消えても行き止まりにならないため、表示済みフラグを永続化しない(B1のGoogle連携失敗通知と同じ扱い。[screen-requirements-dashboard.md](./screen-requirements-dashboard.md) B1)
- **表示するかどうかはメモリ上の一過性の状態で判断し、URLのクエリパラメータでは制御しない。** クエリだと `/login?loggedOut=1` を直接開くだけで表示でき、リロードでも消えないため、上記2点(自分でログアウトした直後の1回だけ・リロードで消える)がどちらも成立しなくなる
  - HTMLモックの `a4-login.html` が `?loggedOut=1` を使っているのは、静的ファイル間で状態を渡す手段が無いための便宜である。**実装ではこの方式を踏襲しない**

> 「ログイン状態を保持する」の選択は、一次認証の実行前にFirebase Authのセッション永続化方式へ反映する(チェック時はブラウザを閉じても保持、未チェック時はタブを閉じると失効)。既定はチェック済み。2FAありのログインで実際にセッションが作られるのはA5の検証成功時のため、A5もこの選択を引き継ぐ。Googleログイン・A8のアカウント連携も同じくA4での選択を引き継ぐ。

## A5. 2FA検証画面

- **画面目的**: 一次認証成功後、認証アプリの確認コードによる二次認証を行う。一次認証の手段(メール/パスワード、Google、A8のアカウント連携)を問わず共通で通る

| 区分 | 項目 |
|---|---|
| 表示項目 | 一次認証済みのメールアドレス(確認表示) |
| 入力項目 | 確認コード(6桁)。「リカバリーコードを使う」への切り替え可能 |
| 主な操作 | 「検証する」ボタン、「リカバリーコードを使う」リンク(切替後は「認証アプリのコードに戻る」リンク) |

**遷移条件**

- 確認コード検証成功 → **B1 ダッシュボード画面** へ遷移(「ログイン状態を保持する」チェック時はセッション有効期間を延長)
- リカバリーコード検証成功 → そのコードを使用済みにし、**TOTPの登録を解除**したうえで一次認証をやり直す → 2FA未登録として扱われ **A3 2FA登録画面** へ遷移(認証アプリを再登録し、リカバリーコードも新しく発行される)。B1へ直行しない理由は [auth-login-requirements.md](auth-login-requirements.md) 3.3 を参照
- リカバリーコード検証成功後の一次認証のやり直しに失敗 → A5に留まり「2段階認証を解除しました。ログイン画面からログインし直して…」と案内し、「ログイン画面へ」で **A4 ログイン画面** へ戻す(解除は済んでいるため、やり直せばA3へ進める)
- リカバリーコードは使用済みになったが2FAを解除できなかった → A5に留まり、コードが使用済みになったことと**別のコードで試し直す**ことを案内する(消費したコードは戻らないため、同じコードでの再試行は促さない。[auth-login-requirements.md](auth-login-requirements.md) 3.3)
- A8から到達した場合のみ、検証成功後に**Googleアカウントの連携を実行してから**B1へ遷移する。連携に失敗した場合はサインイン自体は成立しているためB1へ進み、連携できなかった旨をB1側で通知する(ログインをやり直させない)。通知の文言・表示条件は [screen-requirements-dashboard.md](./screen-requirements-dashboard.md) B1「Googleアカウント連携の失敗通知」を参照
- 検証失敗 → エラー表示、再入力可能(検証セッションの期限切れを除く。下記のとおり再入力させない)
- リカバリーコード使用時、使用済みコードは以後無効化する

> 検証セッションはA4からメモリ上でのみ受け渡すため、A5を直接開いた場合やリロードした場合は自動でA4へ戻す。検証セッションの期限切れはA5に留まってエラーを表示し、「ログイン画面へ」の導線からA4へ戻ってもらう。
>
> **メールアドレスの確認表示は、引き継げなかった場合に限り宛名を伏せて「一次認証が完了しています」と出す。** A4からの経路では入力値をそのまま引き継げるが、Googleログイン経由ではFirebaseが投げるMFAのエラーに載る値を使うため、得られないことがある。宛名だけのために画面を出し分けたりA4へ戻したりはしない(検証セッション自体は有効で、確認コードの検証はそのまま行えるため)。
>
> **検証セッションが期限切れになったら、確認コードの入力欄と「検証する」は無効化する。** 同じ検証セッションでは何度送り直しても期限切れのままで、ユーザーに無駄な再試行をさせてしまうため。無効化はリカバリーコードの入力へ切り替えて戻ってきても解かない(切り替えでは検証セッションは戻らない)。ただし**「リカバリーコードを使う」導線は期限切れ後も残す** — リカバリーコードの検証は検証セッションを使わず、メールアドレスとパスワードでTOTPを解除して一次認証をやり直すため、期限切れの後でも成立する。認証アプリを失っているユーザーをA4へ往復させないための扱いである。
>
> **「リカバリーコードを使う」導線は、パスワードによる一次認証を通った場合にのみ表示する。** リカバリーコードの検証はサーバー側でパスワードを再確認する必要があり([auth-login-requirements.md](auth-login-requirements.md) 3.3)、そのパスワードはメモリ上で引き継ぐため、Googleのポップアップだけで一次認証を通った場合はこの導線が成立しない。Googleのみのアカウントで認証アプリを失った場合の復旧手段は8章のオープン課題とする。
>
> **A8経由でA5に到達した場合はこの導線を出す。** A8でユーザーがパスワードを入力しており、A4からの経路と同じくパスワードを引き継げるため。ここで導線を隠すと、Googleログインを試みたら連携を求められ、その先で認証アプリを失っていることに気づいたユーザーが行き止まりになる。A8経由でリカバリーコードを使った場合も、2FAの解除後にやり直す一次認証が成功した時点でサインインが成立するため、**A3へ進む前にGoogleアカウントの連携を実行する**(連携の失敗の扱いは他の経路と同じ)。

## A6. パスワードをお忘れの方画面

- **画面目的**: パスワードを忘れたユーザーがリセットメールを受け取るための入力画面

| 区分 | 項目 |
|---|---|
| 表示項目 | 案内文、ログイン画面への導線 |
| 入力項目 | メールアドレス |
| 主な操作 | 「リセットメールを送信する」ボタン、(送信完了の表示中のみ)「別のメールアドレスで送り直す」ボタン |

**遷移条件**

- 送信操作後 → 送信完了メッセージを画面内に表示(未登録メールアドレスでも同一メッセージを表示し、アカウントの存在有無を推測されないようにする)。画面遷移はしない
- 「別のメールアドレスで送り直す」ボタン押下 → 送信完了メッセージを閉じて入力欄に戻る(入力値は保持する)。画面遷移はしない。メールが届かない原因の多くは宛先の打ち間違いのため、リロードやA4経由を挟まずに直せるようにする
- 「ログインに戻る」リンク押下 → **A4 ログイン画面** へ遷移

> Googleのみで作成されたアカウント(パスワード未設定)のメールアドレスが入力された場合、リセットメールは実際には送信されない。上記のとおりアカウントの存在有無を伏せる方針のため、画面表示は送信完了時と同一のメッセージとする。

## A7. パスワード再設定画面

- **画面目的**: リセットメールのリンクから遷移し、新しいパスワードを設定する

| 区分 | 項目 |
|---|---|
| 表示項目 | 変更対象のメールアドレス、パスワードポリシーの充足状況、(リンク無効・期限切れ時の)エラー案内 |
| 入力項目 | 新パスワード、新パスワード(確認用) |
| 主な操作 | 「パスワードを再設定する」ボタン、パスワード表示/非表示トグル |

**到達条件**

パスワードリセットメールのリンクから、ワンタイムコード(`oobCode`)付きで到達する。リンクの受け口はFirebaseのアクションURLに設定した `/auth/action` で、`mode=resetPassword` のときにこの画面へ引き渡す。アクションURLはFirebaseプロジェクトに1つしか設定できず、メールアドレス確認(A2)のリンクも同じURLに届くため、受け口側で `mode` を振り分ける(設定手順は [ci-cd-setup.md](./ci-cd-setup.md) 12章)。

**遷移条件**

- 初期表示時にリンクを検証し、有効な場合のみ入力欄を表示する。期限切れのリンクでパスワードを入力させてから失敗させないため
- 再設定成功 → 完了メッセージを表示し、数秒後に **A4 ログイン画面** へ自動遷移(「今すぐログイン画面へ」の導線も併置)。再設定してもサインイン状態にはならないため、A4でログインし直してもらう
- リンクが無効・期限切れ・使用済み、または `oobCode` が欠落 → エラー表示し、**A6 パスワードをお忘れの方画面** への再遷移導線を表示。確定時に初めて失効が判明した場合も同じ表示に切り替える
- パスワードポリシー違反・確認用不一致 → インラインエラー表示、遷移しない。ポリシーはA1サインアップと同一で、充足状況を入力に応じてリアルタイムに表示する
- 通信エラー・レート制限 → **リンクは有効な可能性があるため、A6へ戻さずその場でやり直せるようにする**。初期表示の検証で起きた場合は「再試行する」で同じリンクの検証をやり直し(A6への導線も併置)、再設定の確定で起きた場合はエラーを表示して入力値を保持したまま再送信できるようにする
- Firebaseの設定不足 → その場にエラーと対処法を表示する。設定を直して読み込み直す必要があるため、上記の再試行の対象には含めない

> 変更対象のメールアドレスは、リンクの検証時にFirebaseが返す値を表示する。どのアカウントのパスワードを変えようとしているかを、入力前に確かめられるようにするため。

## A8. アカウント連携画面

- **画面目的**: 既存のメール/パスワードアカウントと同一のメールアドレスでGoogleログインが行われたとき、パスワードによる本人確認を経て両プロバイダを同一アカウントに連携する

| 区分 | 項目 |
|---|---|
| 表示項目 | 対象のメールアドレス(Googleから取得したもの)、連携が必要な理由の案内文、連携せずにログイン画面へ戻る導線 |
| 入力項目 | パスワード(既存アカウントのもの) |
| 主な操作 | 「連携してログイン」ボタン、パスワード表示/非表示トグル、「パスワードをお忘れの方」リンク |

**到達条件**

A1・A4の「Googleで続ける」でGoogleログインを実行し、同一メールアドレスのパスワードアカウントが既に存在する場合(`auth/account-exists-with-different-credential`)にのみ到達する。Identity Platformの「メールアドレスごとに1つのアカウント」設定が有効であることが前提([auth-login-requirements.md](auth-login-requirements.md) 3.8)。

**案内文の方針**

「このメールアドレスは既にパスワードでご登録済みです。パスワードを入力すると、次回からGoogleでもログインできるようになります」のように、**エラーではなく追加の手続き**として提示する。既存アカウントを乗っ取られたような印象を与えない。

**連携の実行タイミング**

- パスワード検証だけではサインインが完了しない(2FA登録済みユーザーは `auth/multi-factor-auth-required` となる)ため、**A5の2FA検証成功後にGoogleアカウントの連携を実行する**
- 2FA未登録の既存アカウント(サインアップを途中離脱したケース)ではパスワード検証時点でサインインが成立するため、その場で連携を実行してからA3(メール未確認ならA2)へ進む
- 連携待ちのGoogle資格情報はA5の検証セッションと同じくメモリ上でのみ受け渡す。短命なOAuthクレデンシャルであり、永続化すると期限切れの資格情報で連携を試みることになるため
- **資格情報の期限切れはA8では検知しない**。連携の実行時に初めて判明する性質のもので、その時点ではパスワード検証(+2FA検証)が済んでサインインが成立しているため、A8やA4へ戻さず連携失敗として扱う。A5が「検証セッション期限切れ」に手動の「ログイン画面へ」導線を持つのと非対称になるが、A5は期限切れ時点でまだサインインが成立していないのに対し、A8の連携失敗はログインを取り消す理由にならないため意図的に揃えていない
- 連携に失敗した場合(資格情報の期限切れ、`auth/credential-already-in-use` 等)はサインインを維持したまま先へ進み、**B1到達時に失敗を通知する**([screen-requirements-dashboard.md](./screen-requirements-dashboard.md) B1「Googleアカウント連携の失敗通知」)。2FA登録済み・未登録のどちらの分岐でも同じ扱いとする

**遷移条件**

- パスワード検証成功(2FA登録済み) → **A5 2FA検証画面** へ遷移し、検証成功後に連携を実行して **B1 ダッシュボード画面** へ
- パスワード検証成功(2FA未登録・メール確認済み) → 連携を実行し、**A3 2FA登録画面** へ遷移(2FAは全ユーザー必須のため)
- パスワード検証成功(2FA未登録・**メール未確認**) → 連携を実行したうえで **A2 メールアドレス確認待ち画面** へ遷移。A4と同じく「メール未確認」を「2FA未登録」より優先して扱う(A1でサインアップしたがA2で離脱したアカウントが、同じメールアドレスのGoogleログインからA8に到達しうるため)
  - **ただしA3とA2のどちらへ進むかは、連携の実行後に `emailVerified` を取り直してから決める。** 連携するGoogleアカウントのメールアドレスはGoogle側で確認済みのため、連携によって `emailVerified` が true に変わりうる。パスワード検証の時点(=連携前)の値をそのまま使うと、確認済みになったユーザーを不要なA2へ送ってしまう
  - 取り直した結果が確認済みならA3へ、未確認のままならA2へ進む。取り直しに失敗した場合(通信失敗・設定不足・セッション消失)は連携前の判断をそのまま使う — 遷移先を誤っても `AppAccessGuard` が正しい手順へ差し戻すため、ここで止める理由が無い
- パスワード誤り → インラインエラー表示、再入力可能。この画面に到達している時点でメールアドレスの登録は確定しているため、A4のような曖昧化(「メールアドレスまたはパスワードが正しくありません」)は行わず「パスワードが正しくありません」と表示する
- 「連携せずにログインへ戻る」リンク押下 → Googleログインを取りやめ、**A4 ログイン画面** へ遷移
- 「パスワードをお忘れの方」リンク押下 → **A6 パスワードをお忘れの方画面** へ遷移
- 連携セッションが無い状態でこの画面に到達(直接アクセス・リロード) → **A4 ログイン画面** へ自動で遷移。A5と同じく、メモリ上の資格情報が失われた状態では処理を続行できないため
- 連携の実行に失敗(資格情報の期限切れ等) → A8には戻らず、上記「連携の実行タイミング」のとおりサインインを維持したまま **B1 ダッシュボード画面**(2FA未登録の分岐ではA3経由)へ進み、B1で失敗を通知する

> メール未確認のパスワードアカウントに、同一メールアドレスのGoogleを連携した場合に `emailVerified` が true へ変わるかはIdentity Platform側の挙動に依存する。**この挙動を前提に分岐を固定せず、連携後の値を毎回読み直して遷移先を決める**方針とした(上記)。どちらの挙動でも正しく遷移し、Identity Platform側が将来変わっても壊れないため、実挙動の確定はこの画面の要件上は不要になっている。
