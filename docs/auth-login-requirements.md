# ログイン画面・認証機能 要件定義書

## 1. 位置付け

本ドキュメントは [FIRE-FIRE 要件定義書](./fire-asset-management-requirements.md) の「4.1 認証・ユーザー管理」を詳細化したものである。
基本方針として Firebase Authentication の標準仕様に準拠しつつ、二要素認証(2FA)・パスワードリマインダー・ログイン通知・ソーシャルログイン(Google)の4点を追加要件として実装する。

## 2. 概要・目的

個人の資産・金融情報を扱うアプリであるため、パスワード認証に加えて認証アプリ(Google Authenticator等)によるTOTP型2FAを全ユーザー必須とし、不正ログインのリスクを低減する。あわせて、パスワード紛失時のリセット手段と、ログイン発生時の通知によって本人が異常を検知できる仕組みを備える。

## 3. 認証方式・技術方針

### 3.1 認証基盤

- **Firebase Authentication** をベースとする
- TOTP型2FAをFirebase公式のMFA機能で実現するため、Firebaseプロジェクトを **Identity Platform** にアップグレードする
  - Identity Platformは従量課金体系だが、標準認証方式(メール/パスワード等)は月間アクティブユーザー(MAU)50,000人まで無料。TOTP型2FAはSMSを送信しないため追加課金の対象外で、通常のMAUとしてカウントされるのみ。個人利用規模(数人程度)では実質無料で運用できる
  - SMSを使う電話認証・SMSベースMFAとは異なり課金体系が別建てである点に注意(参考: [Identity Platform pricing](https://cloud.google.com/identity-platform/pricing))
  - プロジェクト全体の認証基盤がこの前提に切り替わるため、[要件定義書](./fire-asset-management-requirements.md) 3章の技術スタック表(認証行)にも反映済み
- パスワードポリシー(8文字以上・大小英数字+記号の組み合わせ)は、Identity Platformの **パスワードポリシー機能** をコンソール側で設定し、サーバーサイドでも強制する(クライアント側のバリデーションのみに頼らない)

### 3.2 ID・パスワード仕様

| 項目 | 仕様 |
|---|---|
| ID | メールアドレス(RFC 5321 / RFC 5322に準拠する形式) |
| 検証方法 | Firebase Authenticationの標準メールフォーマット検証(RFC 5322準拠)に加え、クライアント側でも送信前にフォーマットを検証する。ブラウザ標準の `type="email"` による検証はエラーメッセージを日本語で制御できず表示位置も指定できないため使わず(フォームに `noValidate` を指定)、zodスキーマで検証してインラインエラーとして表示する。入力欄の `type="email"` はソフトウェアキーボードの最適化のために維持する |
| パスワード | 8文字以上。大文字・小文字・数字・記号を組み合わせる |
| パスワード強制ルール | Identity Platformのパスワードポリシー機能で `minLength: 8`、大文字/小文字/数字/非英数字の全要求を有効化 |

### 3.3 二要素認証(TOTP)

- Identity PlatformのマルチファクタTOTP機能を利用し、Google Authenticator等の認証アプリと連携する
- **全ユーザー必須**とし、サインアップ完了直後に2FA登録を強制するフローとする(2FA未登録の状態ではアプリの主要機能を利用させない)
- 「主要機能を使わせない」は画面側の表示制御(`AppAccessGuard`)だけでなく、**データ層でも強制する**。`firestore.rules`は本人性・メール確認に加えてIDトークンの `firebase.sign_in_second_factor == 'totp'` を要求し、2FAを通していないセッションからの資産データの読み書きを拒否する。B2 CSV取込のようにクライアントSDKから直接Firestoreを叩く経路では、画面を経由せずAPIを直接呼ばれた場合にルールが唯一の防御線になるため(パスワードが漏れた相手にTOTPを迂回させない、という2FAの目的そのもの)
- 登録フロー: シークレットキー発行 → QRコード表示 → 認証アプリでスキャン → 確認コード入力による有効化検証
- ログインフロー: メールアドレス・パスワードによる一次認証成功後、認証アプリの確認コード入力を求める二次認証を行う

#### リカバリーコード(認証アプリ紛失時の代替手段)

Identity Platformにバックアップコードの機能は無いため、Cloud Functions + Cloud Firestoreで自前に用意する。

| 項目 | 仕様 |
|---|---|
| 発行 | 2FA登録の完了直後(A3)に8本を発行し、その場で一度だけ平文を表示する。テキストファイルとしてダウンロードできる |
| 形式 | `XXXX-XXXX`(32文字の英数字から8文字。`0`/`1`と紛れる`O`/`I`は使わない) |
| 保存 | Firestoreにはコードごとのソルト付きscryptハッシュのみを保存し、平文は保存しない。クライアントからの読み書きはセキュリティルールで全面的に拒否し、Cloud Functions(Admin SDK)からのみ扱う |
| 再発行 | B10から再発行できる。再発行すると以前のコードはすべて無効になる |
| 使用 | A5で「リカバリーコードを使う」に切り替えて入力する。1本のコードは1回だけ有効で、使用後は無効化する |
| 使用時の動作 | サーバー側でパスワードによる一次認証を再確認したうえで、**TOTPの登録を解除する**。解除後は2FA未登録のアカウントとして扱われるため、ログインをやり直してA3で認証アプリを再登録する(再登録時にリカバリーコードも新しく発行される) |
| 解除に失敗した場合 | コードを使用済みにしてから解除する順序とし、解除に失敗しても消費したコードは戻さない(逆順にすると、解除済みなのに有効なコードが残り「1回限り」の前提が崩れるため)。画面には使用済みになった旨と、別のコードで試し直すよう案内する |
| 総当たり対策 | 3.7と同じく専用のロック機構は設けない。パスワードを知らない相手は、コードの照合より先に行うパスワード再確認がIdentity Platformのレート制限に当たるため試行を続けられない。パスワードが漏れている場合はこのレート制限を当てにできないが、コードの探索空間(40ビット)と1回の照合にかかるscryptのコスト(未使用コードの本数ぶん、最大8回)により、総当たりは現実的な時間・費用に収まらない |

リカバリーコードでその場のログインを完了させ(B1へ直行させ)ないのは、Identity PlatformがTOTPの確認コード以外で二次認証を完了できず、カスタムトークンで代替すると2FAを通らないサインイン経路を常設することになるため。認証アプリを紛失した状況では再登録が必要になるので、解除して再登録へ送る形にしている。

### 3.4 メールアドレス確認(email verification)

- サインアップ時にFirebase Authentication標準のメール確認機能を用い、確認メールを送信する
- メールアドレス未確認の間は主要機能の利用を制限する(ログイン自体は可能だが、機能利用前に確認を促す)

### 3.5 パスワードリマインダー(forgot password)

- ログイン画面に「パスワードをお忘れの方」導線を設置する
- Firebase Authentication標準のパスワードリセットメール機能を利用し、登録済みメールアドレス宛にリセットリンクを送信する
- リンク先の画面で新しいパスワードを設定する(3.2のパスワードポリシーを同様に適用)

### 3.6 ログイン通知機能

- **毎回のログイン成功時**に、登録済みメールアドレスへ通知メールを送信する
- 通知メールには日時・利用デバイス/ブラウザ情報などログインを識別できる情報を含める
- Firebase Authentication標準機能ではカスタム通知メールを送信できないため、Identity PlatformのBlocking Functions(ログイン後トリガー)からCloud Functionsを起動し、外部メール送信サービス経由で送信する構成を想定する
  - メール送信サービスは **Resend** を使う(選定理由は [src/backend/docs/TECH_STACK.md](../src/backend/docs/TECH_STACK.md) 4章、APIキーの登録手順は [ci-cd-setup.md](./ci-cd-setup.md) 5章)

**発火のタイミング**

Blocking Functions(`beforeUserSignedIn`)は**第2要素の検証が済んだあと**に発火する。2FAは全ユーザー必須なので(3.3)、第1要素だけ通って2FAで止まった試行は通知されない。「ログイン成功時」の定義とずれない。

**サインアップ直後の初回サインインも通知の対象とする**。アカウント作成時は `beforeUserCreated` に続いて `beforeUserSignedIn` も発火するため、2FA登録(A3)を終える前に1通届き、メールアドレス確認メール(3.4)と合わせて2通になる。それでも抑止しないのは、セッションが成立している以上「ログイン成功」であり、「毎回」に例外を作らないため。自分のメールアドレスで勝手にアカウントを作られた場合に気づける利点もある。

**送信に失敗した場合**

通知を送れなくても**ログインは成立させる**。Blocking Functionsで例外を投げるとサインインそのものが失敗するため、メール事業者の一時障害やタイムアウトがアプリの停止に直結してしまう。通知が届かないログインが起こりうることは受容し、失敗はCloud Functionsのログに残す。

**環境の区別**

開発環境(`fire-fire-dev`)からのログインでも同じ経路で送信する。ローカル開発もSTGのFirebaseへ直結しているため(CLAUDE.md「B0-1」)、本番と同じ経路を日常的に検証できる。受信箱で混ざらないよう、本番以外からの通知は件名に `[dev]` を付け、本文にプロジェクトIDを明記する。

### 3.7 ブルートフォース対策

- Firebase Authenticationが標準で備えるレート制限等の保護機構に委ね、追加のアカウントロック機構は実装しない

### 3.8 ソーシャルログイン(Google)

メール/パスワードに加え、**Googleアカウントによるサインアップ・ログイン**に対応する。対応プロバイダは当面Googleのみとし、Apple/X等の追加は8章のオープン課題とする。

**認証方式**

- Firebase Authenticationの `GoogleAuthProvider` を利用する。Identity Platformコンソールでの Google プロバイダ有効化と、承認済みドメインの登録が前提となる(手順は [ci-cd-setup.md](./ci-cd-setup.md) 10章)
- サインインは**ポップアップ方式**(`signInWithPopup`)を基本とする。ユーザーがポップアップを閉じた場合はエラー扱いとせず、元の画面に留まる
- サインアップ・ログインの区別はGoogle側では付かないため、A1(サインアップ)とA4(ログイン)のどちらから開始しても同一の処理とし、後述の分岐で遷移先を決める

**2FAとの関係**

- **Googleログインでも2FA(TOTP)は必須**とし、3.3の「全ユーザー必須」の方針を維持する。個人の資産・金融情報を扱う以上、一次認証の手段によって要求水準を変えない
- Googleログイン成功時、2FA未登録なら **A3 2FA登録画面**、登録済みなら **A5 2FA検証画面** を経てB1へ進む。Identity PlatformのMFAはフェデレーションログインにも適用され、2FA登録済みユーザーは第1要素(パスワード / Googleポップアップ)が**成功した時点で**サインインが完了せず `auth/multi-factor-auth-required` となる。第1要素の種類を問わず同じ形で第2要素へ引き継がれるため、A4からの経路と同じ検証セッションの受け渡しに乗せられる(第1要素が失敗した場合は `auth/wrong-password` 等それぞれのエラーとなり、この経路には入らない)

**メールアドレス確認(3.4)との関係**

- GoogleアカウントのメールアドレスはGoogle側で確認済み(`email_verified`)として渡るため、Googleログインで新規作成されたアカウントは **A2 メールアドレス確認待ち画面をスキップ**してA3へ進む

**既存アカウントとの連携(アカウントリンク)**

- Identity Platformの「メールアドレスごとに1つのアカウント」設定を有効にしておく(既定)。無効だと同一メールアドレスでパスワードアカウントとGoogleアカウントが二重に作られ、資産データの所有者が分岐してしまう
- 同設定下では、既存のパスワードアカウントと同じメールアドレスでGoogleログインを試みると `auth/account-exists-with-different-credential` となる。この場合は **A8 アカウント連携画面** へ遷移し、パスワードによる本人確認を経て両プロバイダを同一アカウントに連携する
- 連携後は同一アカウントに対してパスワード・Googleのどちらでもログインできる。2FA設定はアカウント単位のため連携によって変化しない
- 連携待ちのGoogle資格情報(OAuthクレデンシャル)は短命であり、メモリ上でのみ保持する。画面リロード・直接アクセス等で失われた場合はGoogleログインからやり直す

**パスワードリマインダー(3.5)との関係**

- Googleのみで作成されたアカウントにはパスワードが存在しないため、A6でそのメールアドレスを入力してもリセットメールは送信されない。ただしアカウントの存在有無を推測されないよう、画面表示はA6の既定どおり成功時と同一のメッセージとする

**ログイン通知(3.6)との関係**

- Blocking Functions(ログイン後トリガー)はGoogleログインでも発火する。通知メールには利用した**ログイン方法(パスワード / Google)**を含め、本人が身に覚えのないログイン手段を検知できるようにする

**連携アカウントの管理**

- 連携済みプロバイダの確認・追加・解除は **B10 アカウント設定画面** で行う(詳細は [screen-requirements-account.md](./screen-requirements-account.md))。認証手段が1つも無くなる解除は禁止する

### 3.9 ログアウト

サインイン中のセッションを利用者の意思で終了する手段を用意する。Firebase Authenticationはセッションをブラウザ側に保持し、リフレッシュトークンが有効な限り自動更新し続けるため、明示的なログアウト導線が無いとサインイン状態を終わらせる手段が存在しない。

- Firebase Authenticationの `signOut()` でローカルのセッションを破棄する。認証基盤側の追加設定は不要
- 導線はログイン後の**共通ヘッダーのユーザーメニュー**に置き、独立した画面は設けない(画面要件は [screen-requirements-account.md](./screen-requirements-account.md) 2章)
- 3.3のとおり2FAは全ユーザー必須で、再ログインには認証アプリの確認コードが要る。誤操作のコストが小さくないため、実行前に確認ダイアログを挟む
- ログアウト後は **A4 ログイン画面** へ遷移し、ログアウトした旨を画面内に表示する

**認証フロー途中からのログアウト**

メールアドレス未確認(A2)・2FA未登録(A3)の状態でもFirebase上はサインイン済みである。この状態のユーザーは先へ進めない一方、主要画面はA2/A3へ差し戻されるためログイン画面へ戻る手段も持たない。**別のアカウントでログインし直せるよう、A2・A3にもログアウト導線を置く**。実行内容はログイン後のログアウトと同一とする。

A5・A8はまだサインインが成立していない段階のため対象外で、既存の「ログイン画面へ」「連携せずにログインへ戻る」導線がそのまま離脱手段になる。

**セッション永続化(A4「ログイン状態を保持する」)との関係**

- `signOut()` は選択した永続化方式に関わらずローカルのセッションを破棄する。「ログイン状態を保持する」を選んでいた場合も、ログアウト後にブラウザを開き直してサインイン状態が復元されてはならない
- 永続化方式の選択はログアウト時に引き継がず、次回A4での選択に委ねる

**保持データの破棄**

ログアウト時にはサインイン中に画面が保持していた情報も破棄する。共有端末で次の利用者に前の利用者の資産額が見えることを防ぐため。

- クライアント側のデータ取得キャッシュを初期化する
- 検証セッション・連携セッションなど、メモリ上でのみ引き回している認証途中の状態も破棄する(3.3 / 3.8)
- Firestoreに保存された資産データそのものは当然削除しない

**適用範囲**

- ログアウトは**その端末・そのブラウザに閉じた操作**とする。リフレッシュトークンをRevokeする「全端末からのログアウト」は行わない(8章のオープン課題)
- 「ログイン状態を保持する」を選んでいた場合(既定)、認証状態はブラウザ全体で共有されるため同一ブラウザの他タブにも伝播し、他タブも自動的にA4へ戻る。保持しない場合の永続化はタブ単位のため他タブには伝播しない
- ログアウトはログイン通知(3.6)の対象外とする。Blocking Functionsはサインイン時にのみ発火し、ログアウトに相当するフックは存在しない

### 3.10 サインアップの制限(ベータ期間中の招待制)

**ベータ期間中は、あらかじめ承認したメールアドレスだけがアカウントを作成できる。** サービストップページ(A0)を公開すると、未ログインの訪問者がリンクを辿ってA1に到達できるため、表示上「招待制」と書くだけでは登録を止められない([公開画面の要件](./screen-requirements-public.md) A0)。

**Identity PlatformのBlocking Functions(`beforeUserCreated`)で実現する**([X5](https://trello.com/c/5k33KGEY))。 3.6のログイン通知が使っている `beforeUserSignedIn` と同じ仕組みで、こちらは**アカウント作成の直前**に発火する。関数の中で例外を投げるとアカウントは作成されない。

| 項目 | 仕様 |
|---|---|
| 判定に使うもの | 作成しようとしているアカウントのメールアドレス |
| 許可リストの置き場所 | Firestore。**クライアントからは読み書きとも拒否する**(`mfaRecoveryCodes` と同じ扱い) |
| 承認の操作 | 開発者がコンソールで許可リストに1件足す。アプリ側に管理画面は作らない(手順は [ci-cd-setup.md](./ci-cd-setup.md) 14章) |
| 許可されていない場合 | アカウントを作成せず、その旨を表示する。**表示先はA1とA4の両方**(A4からのGoogleログインでも新規作成は起こる。下記「Googleログインも同じ関数で塞がる」)。文言は2画面で共通 |

**なぜ事前承認(許可リスト)にしたか**

登録を止める方法は他にもあるが、次の理由でこの形にした。

- **Identity Platformのコンソール設定で新規登録そのものを禁止する**方法もある(Authentication → Settings → User actions)。コードは要らないが、承認した相手のアカウントを開発者が作ってパスワードを渡す運用になる。**パスワードを人づてに渡すほうが危ない**ため採らない。ただし**コードを書かずに今すぐ塞げる手段**として、実装が入るまでの繋ぎには使える
- **登録は通したうえで承認まで機能を使わせない**(事後承認)方法は、既存のフローと噛み合わない。サインアップ後は A2 メールアドレス確認 → A3 2FA登録と進む作りになっており、途中で止まったユーザーがそこから抜ける導線を別に用意することになる
- 承認された人が**自分でパスワードを決めてA1から登録できる**形を残せるのは、事前承認だけである

**Googleログインも同じ関数で塞がる**

`beforeUserCreated` はプロバイダを問わず発火するため、A1・A4の「Googleで続ける」(3.8)から新規アカウントが作られる経路も同時に塞がれる。**Googleログイン用に別の対策を作らない。**

ただし、**A8 アカウント連携は塞がらない**。既存のパスワードアカウントにGoogleを連携する操作はアカウントの作成ではないため、`beforeUserCreated` は発火しない。連携できるのは既に存在するアカウント = 既に承認済みのアカウントなので、これは意図した挙動である。

**許可リストとメールアドレスは、正規化してから完全一致で判定する**

**比べる前に、両側とも小文字化し前後の空白を取り除く。** 承認する側は手で入力するため、`Taro@Example.com` のような表記や、コピー時に紛れ込んだ空白で弾かれる事故が起きる。**招待した本人が登録できないのは、この機能の失敗のしかたとして最も避けたいもの**であり、正規化はその実害に対して安い。

- **正規化した以上のあいまい一致はしない。** ドット除去やプラス以降の切り捨て(`taro+fire@gmail.com` → `taro@gmail.com`)といったプロバイダ固有の正規化は行わない。事業者ごとに規則が違い、正しく実装しても「別人のアドレスを同一とみなす」方向に倒れうる
- 正規化しても、**承認したアドレスと違うアドレス**(Googleアカウント側のアドレスが別、等)では登録できない。招待を送る時点でどのアドレスで登録するかを決めておく必要がある

**開発者自身の経路は塞がない**

Blocking Functionsは**Admin SDK・コンソールからのユーザー作成では発火しない**。許可リストの設定を誤っても開発者がアカウントを作る手段は残るため、自分自身が締め出される事故にはならない。**この挙動は実装時に `fire-fire-dev` で実際に確かめる**(前提が外れていた場合、許可リストの誤設定から復旧できなくなるため)。

**7秒のバジェット**

Blocking Functionsの実行時間には上限がある(3.6でHTTP呼び出しを5秒で打ち切っているのと同じ制約)。許可リストの判定はドキュメント1件の読み取りで済ませ、複数コレクションの走査や外部サービスへの問い合わせを挟まない。

**エラーの伝わり方**

Blocking Functionsで投げた例外は、クライアントのSDKにはカスタムメッセージそのままの形では届かない。**`fire-fire-dev` へデプロイした実物で確かめた結果**は次のとおり。

Identity Platformはサーバーのエラーメッセージを次の形に包む。

```
BLOCKING_FUNCTION_ERROR_RESPONSE : HTTP Cloud Function returned an error: {"error":{"message":"…","status":"PERMISSION_DENIED"}}
```

SDKは `' : '` で分解して `BLOCKING_FUNCTION_ERROR_RESPONSE` を `auth/internal-error` に写し、コロンより後ろをエラーメッセージとして残す(`@firebase/auth` の `errorMap` と `_errorWithCustomMessage`)。したがって:

- **コードは常に `auth/internal-error`** で、他の内部エラーと区別が付かない
- **理由はメッセージ側にしか無い。** ただし `HttpsError` の第1引数に対応する `status` は残るため、**「未承認(`PERMISSION_DENIED`)」と「確かめられなかった(`INTERNAL`)」は区別できる**

**画面はこの2つを別の文言で扱う。** fail-closedで拒否された人に「招待されていません」と伝えると、**招待済みの人に「あなたは招待されていない」と言う**ことになるため。

- 判定は**`status` で行い、メッセージ本文(日本語の文言)では行わない。** 文言はいつでも変わりうるうえ、変えたときに黙って判定が外れる
- `PERMISSION_DENIED` を「未承認」と読んでよいのは、Identity Platformが `beforeCreate` のブロッキング関数を**プロジェクトに1つしか登録できない**ためである。アカウント作成の経路でこのエラーを出しうるのは `restrictSignUpToAllowlist` だけで、取り違える余地が無い。**2つ目の `beforeCreate` を足すときは、機械可読なマーカーでの判定に切り替える**
- 包み方が変わって `status` を読めない場合は、無理に読まず既存の「不明なエラー」の文言に落とす。取り違えて「招待されていません」を出すより害が小さい

判定は `src/frontend/src/lib/auth/signup-allowlist-error.ts` に1箇所だけ置き、A1のメール/パスワードとA1・A4の「Googleで続ける」の両方から呼ぶ。

**ベータ期間が終わったら外す**

この制限はベータ期間中の運用上の措置であり、恒久的な仕様ではない。外す判断は `noindex` の解除・A0の「現在は招待制」の記述と同じタイミングで行う([公開画面の要件](./screen-requirements-public.md) 3章、[X4](https://trello.com/c/8wpkp9Gt))。

## 4. 画面要件

| 画面 | 概要 |
|---|---|
| サインアップ画面 | メールアドレス・パスワード入力。パスワードポリシーをリアルタイムでバリデーション表示。「Googleで続ける」導線 |
| メールアドレス確認待ち画面 | サインアップ直後に表示。確認メール再送導線を含む(Google経由の作成時はスキップ) |

ログアウト(3.9)は共通ヘッダーのユーザーメニューからの操作であり、独立した画面は設けないため上表に行を持たない。ユーザーメニューと確認ダイアログの要件は [screen-requirements-account.md](./screen-requirements-account.md) 2章、A2・A3の離脱導線とログアウト後のA4での表示は [screen-requirements-auth.md](./screen-requirements-auth.md) を参照。

## 5. 非機能要件

- **アダプティブデザイン**: [要件定義書](./fire-asset-management-requirements.md) 5章の方針に準拠し、認証系画面もPC/タブレット/スマートフォンに対応する
- **セキュリティ**: パスワードはFirebase/Identity Platform側で管理し、平文保存は行わない。2FAシークレットもIdentity Platform側の管理に委ねる

## 6. アーキテクチャへの影響

- Firebaseプロジェクトを **Identity Platform** にアップグレードする必要がある(親ドキュメントの技術スタック表は更新済み)。認証基盤は従量課金体系になるが、MAU 50,000人までは無料でTOTP型2FAにも追加課金がないため、個人利用規模では実質コスト影響なし
- ログイン通知メール送信のため、Cloud Functions(Blocking Functions)と外部メール送信サービスとの連携が新たに必要になる
- ソーシャルログイン(3.8)のため、Identity Platform側でGoogleプロバイダの有効化・OAuthクライアントの用意・承認済みドメインの登録が必要になる(dev/prodの両プロジェクト)。アプリ側のコード変更のみでは動かない
- 2FAリカバリーコード(3.3)のため、Cloud Functions(callable)とFirestoreのコレクションが必要になる。コードの検証ではサーバー側からIdentity PlatformのREST APIでパスワードを再確認するため、Web APIキーをSecret Managerに登録しておく必要がある([ci-cd-setup.md](./ci-cd-setup.md))

## 7. MVPスコープ

認証機能は資産管理アプリ全体のPhase 1(MVP)に含まれるため、本ドキュメントの3〜4章で定義した機能(サインアップ、メール確認、2FA必須登録・検証、ログイン、パスワードリマインダー、ログイン通知)はすべてMVPスコープに含める。

ソーシャルログイン(3.8)は当初スコープ外だったものを後から追加した要件で、同じくPhase 1の認証機能として扱う。ただしメール/パスワードによる認証フロー(A1〜A7)が動作することが前提のため、着手順序はそれらの実装後とする。

## 8. 今後の検討事項(オープン課題)

- ログイン通知メールの独自ドメイン化。現状はResendの共有ドメイン(`onboarding@resend.dev`)から送っており、宛先がResendアカウントの登録メールアドレスに限られる。利用者が開発者1人のうちは制約にならないが、SaaS化の際は所有ドメインの検証(SPF/DKIM)が必要になる
- Googleのみで作成したアカウントが認証アプリを紛失した場合の復旧手段。リカバリーコードの使用にはパスワードによる一次認証の再確認が必要なため(3.3)、パスワードを持たないアカウントではA5に「リカバリーコードを使う」導線を出せない。B10でのパスワード追加(下記)を用意すれば併せて解決する
- Google以外のソーシャルログイン(Apple / X 等)への拡張要否。3.8ではGoogleのみを対象としている
- Googleのみで作成したアカウントにパスワードを後から設定する導線(B10でのパスワード追加)の要否
- **一定時間操作が無い場合の自動ログアウト(アイドルタイムアウト)の要否**。3.9のログアウトは利用者の明示的な操作だけを対象としており、Firebaseのリフレッシュトークンは有効な限り自動更新されるため、放置されたセッションは自然には失効しない。個人利用かつ2FA必須である現状は受容するが、共有端末での利用やSaaS化を検討する際に再評価する
- **全端末からのログアウト(リフレッシュトークンのRevoke)の要否**。3.9は端末単位のログアウトのみを対象としている。実装するにはAdmin SDKの `revokeRefreshTokens` を呼ぶCloud Functionsと、B10側の導線が新たに要る。パスワード変更(A7)でも既存セッションを失効させないため、端末を紛失した場合の対処は現状「パスワード変更 + 2FA再設定」に頼ることになる
- 将来のSaaS化・権限モデル設計との連携方法
- 2FA登録(A3)を終えた直後のIDトークンに `sign_in_second_factor` が載るかを、初回の通し確認時に `fire-fire-dev` で確かめる(3.3)。載らない場合、A3を終えたユーザーは一度ログインし直すまでB2の取込が `permission-denied` になる。Identity PlatformのRESTリファレンスは登録完了の応答を「MFA登録を反映したIDトークン」と説明しており、Authエミュレータ(電話番号MFAのみ実装)も登録完了時点でこの請求を載せたトークンを発行するため、載る前提で実装している。外れていた場合はA3の完了後に再ログインへ誘導する対応を入れる
