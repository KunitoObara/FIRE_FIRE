# FIRE-FIRE 要件定義書

## 1. 概要・目的

個人のFIRE(Financial Independence, Retire Early)達成を支援するための資産管理WEBアプリケーション「FIRE-FIRE」を開発する。
マネーフォワードからエクスポートしたCSVデータを取り込み、資産全体をダッシュボードとして可視化するとともに、FIRE目標に対する達成度・到達期間の予測を行う。

## 2. 想定ユーザー

- **初期リリース時点**: 開発者本人専用(シングルユーザー利用)
- **将来構想**: 第三者にも公開するSaaS化を見据える
  - 権限モデル(管理者/一般ユーザーなど)は現時点では未定義とし、将来の拡張項目として本ドキュメントに記録するのみに留める
  - 初期実装では認証(ログイン)機能のみを実装し、マルチテナント設計・ロール管理は行わない

## 3. 全体アーキテクチャ

| レイヤー | 技術・方針 |
|---|---|
| フロントエンド | Next.js(React)、アダプティブデザイン(PC/タブレット/スマホ対応) |
| バックエンド | サーバレス構成(Firebaseを想定) |
| 認証 | Firebase Authentication(Identity Platformへアップグレード。TOTP型2FA必須化のため。従量課金体系になるが、月間アクティブユーザー(MAU)50,000人まで無料。TOTP自体もSMSを送信しないため追加課金なし。個人利用規模では実質無料) |
| データストア | Cloud Firestore(NoSQL)を想定。分類マスタ等は拡張しやすいスキーマとする |
| ファイルストレージ | Firebase Storage(将来の用途向けに確保。**CSVの生ファイルは保管しない** — 下記) |
| ホスティング | 要決定(Vercel または Firebase Hosting) |
| 開発支援ツール | Claude Codeを契約し、実装効率化に活用 |

> 上記は「サーバレス/Firebase」という方針に基づく標準的な構成案であり、各サービスの詳細な選定(Firestore vs 他DB、ホスティング先など)は実装フェーズで確定する。

## 4. 機能要件

### 4.1 認証・ユーザー管理

- Firebase Authentication(Identity Platform)によるログイン機能を実装する。2FA(TOTP)必須化・パスワードリマインダー・ログイン通知・Googleソーシャルログインなどの詳細は [ログイン画面・認証機能 要件定義書](./auth-login-requirements.md) を参照
- ログイン手段はメールアドレス/パスワードに加え、**Googleアカウント**によるソーシャルログインに対応する。いずれの手段でも2FA(TOTP)は必須とする
- 初期リリースは本人専用のシングルユーザー運用
- 将来のSaaS化・複数ユーザー対応(権限モデル、データ分離方式)は本ドキュメントでは範囲外とし、別途設計する

### 4.2 マネーフォワードCSV連携

入出金明細(取引データ)の取込とそこから導く収支の集計は、CSVの列構成・データモデル・重複排除・集計から外す行まで含めて [入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) を参照。本節は両方の取込に共通する方針を定める。

- **取込方式**
  - MVPでは手動アップロードのみ対応(CSVファイルをアプリ画面からアップロード)
  - 将来的に定期自動取得への対応を検討する(方式は未確定。マネーフォワード公式APIまたはスクレイピング等、実装コスト・利用規約を踏まえて別途検討)
- **取込対象データ**
  - 資産残高推移(各口座の日次/月次残高)
  - 入出金明細(取引データ) — 費目別の収支分析に必要なため取込対象に含める
- **アップロードしたCSVの生ファイルは保管しない**(3章のアーキテクチャ表と対応)
  - ブラウザ上でパースし、抽出した数値だけをFirestoreへ保存する。Firebase Storageへは置かない
  - 保管しない理由は、元データがマネーフォワード側に残っており必要になればいつでも再エクスポートできること、取込は同じ日付を上書きする冪等な処理で取り込み直せば必ず同じ状態に収束すること、そして資産情報の保管場所を増やさずに済むこと
  - 取込の記録としては、いつ・どのファイル名で・何件・どの期間を取り込んだかを取込履歴として残す(B2の表示項目)
  - 監査目的で原本を残す必要が出た場合は、Firebase Storageへの保管を改めて設計する(保管期間・削除方針の決定を伴う)

### 4.3 資産分類(ポートフォリオの切り替え表示)

総資産ポートフォリオに加え、以下のような分類軸で切り替え表示できるようにする。

- 総資産
- 純金融資産
- 金融資産
- 投資性資産(投資信託 + 株式 + iDeCo)
- 流動限定金融資産(iDeCo + 小規模企業共済)

**設計上の要件**: 分類軸は開発中・運用中に追加される可能性があるため、コードにハードコードせず、マスタデータとして追加・編集可能な拡張性のある設計とする。

分類軸の集計対象には、資産種別に加えて **4.8 の負債** も選べるものとする。純金融資産のように「資産 - 負債」で定義される分類軸を、専用の計算式をコードに持たずに表せるようにするため。負債を含む分類軸では、集計は「対象の資産種別の合計 - 対象の負債の残債」になる。

さらに **4.5 の不動産(手動で登録した物件)** も集計対象として選べるものとする。物件は手入力でしか登録されず、マネーフォワードのCSVには現れないため、分類軸がダッシュボードへ載せる唯一の経路になる。物件は**1件ずつ選び、物件ごとに「利ざや(時価 - ローン残高)を反映する」か「時価を反映する」かを選ぶ**。居住用は取り崩せないので利ざやで見たいが投資用は時価で見たい、のように物件ごとに見方が変わるため。したがって集計は「対象の資産種別の合計 + 対象の物件の額(利ざや または 時価) - 対象の負債の残債」になる。

- **CSVの資産種別に不動産が含まれている場合は二重計上になる。** マネーフォワードに不動産を登録していれば「不動産」等の資産種別としてCSVに現れるため、同じ物件をB7でも登録して分類軸で選ぶと同じ資産を2回数える。アプリ側で突き合わせる手掛かりが無い(物件名とCSVの列名は一致しない)ので、**画面上で注意を促すに留める**(詳細は[画面要件](./screen-requirements-dashboard.md) B4)
- 利ざやを反映する物件のローン残高は、この経路でダッシュボードの集計に効く。同じローンを4.8の負債にも登録して同じ分類軸で選ぶと二重に差し引かれる(4.8 末尾)

### 4.4 資産ダッシュボード

以下の指標・グラフを表示する。

- 資産推移グラフ(時系列。資産種別の積み上げで、4.3の分類軸が対象にする負債を反映するかどうかを画面上で切り替えられる。分類軸が対象にする不動産は「不動産」1本の帯として積む。4.3の分類軸で切り替え可能)
- 分類別内訳(円グラフ・構成比、4.3の分類軸で切り替え可能)
- FIRE達成度ゲージ/到達予測日
- 収支サマリ(月次収支・費目別支出の円グラフ) — 入出金明細データを基に集計。対象の月は画面上で選べる(既定は当月)
- 負債サマリ(負債合計・項目別の残債) — 4.8の負債を基に集計。分類軸の切り替えとは独立に、登録済みの負債をそのまま表示する

### 4.5 不動産管理

- 複数物件の登録に対応する
- 管理項目
  - 物件基本情報
  - 取得年月(その物件を取得した月。任意)
  - 時価(手動更新)
  - 住宅ローン残高
  - 賃貸収入/支出(収益物件に対応する場合)
- **利ざや計算**: 不動産時価 - 住宅ローン残高 を自動計算し表示する
- 1物件につき基本は1ローンを想定(複数ローンの紐付けなど詳細な構成は将来拡張)
- 時価・ローン残高の更新は手動で行う。ただし**更新のたびにその日付の時価とローン残高を履歴として記録**し、資産推移グラフが各時点の額を積めるようにする(4.8の残債の履歴と同じ扱いで、記録に追加の入力操作は求めない)
- 履歴は登録した月からしか積まれないため、**取得年月を入力すればその月まで遡って反映する**。遡る期間には最も古い記録の時価・ローン残高を当てる(4.8の負債と同じ扱い。詳細は[画面要件](./screen-requirements-dashboard.md) B1「不動産を含む分類軸の集計」)
- 物件は4.3の分類軸から集計対象として選べるようにし、選ばれた物件は4.4のダッシュボード(資産推移グラフ・分類別内訳・FIRE達成度)に反映する。**分類軸で選ばれていない物件はダッシュボードに現れない** — B5〜B7だけで管理する物件を残せるようにするため

### 4.6 FIRE目標設定・達成度・到達期間予測

以下2つの目標設定方式に両対応し、ユーザーが切り替えられるようにする。

1. **目標資産額を直接設定**: 例)「金融資産3,000万円」のようにゴール額を直接入力し、現在資産との差分・到達予測時期を計算
2. **年間支出額から目標額を逆算**: 想定生活費(年間支出額)を入力し、4%ルールなど任意の係数から必要資産額を自動算出した上で到達予測

達成度(現在資産 ÷ 目標資産)をゲージ等で可視化し、現在のペースに基づく到達予測日を算出する。

- 達成度の分子(現在資産)は、4.3の分類軸から選んだ**達成度の対象分類**で数える。既定は総資産
- 到達予測は、**4.7の想定利回りによる資産の複利成長 + 毎月の積立額**で先へ進める。「現在のペース」は積立額の初期値として月次収支から提示する形で満たし、**積立額そのものは手入力の設定値**とする — 予測のたびに複数月の取引を読み直すことになり、[入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) 8章が決めた読み取り範囲と両立しないため
- 4.5の不動産と4.8の負債は、**予測の全期間で据え置く**。時価も残債も手動更新が前提で、自動で増減させると4.8の「自動計算は行わない」に反する
- **将来予測(シミュレーション)は専用の画面を設けず、この到達予測日として表す。** 係数を変えて何度も試す用途は現時点では想定しない(前提を変えたければB8・B9の設定を変えて保存する)
- 算出方式の詳細(月次の複利、打ち切り、到達しない場合の扱い)は [FIRE目標・シミュレーション設定系画面の要件](./screen-requirements-fire-goal.md#到達予測日の算出) を参照

### 4.7 想定利回り・リスク等の手動設定

- **資産種別ごと**の想定利回り(年率)とリスクレベルを手動で設定できる
  - 口座ごとではない。マネーフォワードのCSVは資産種別の列しか出力せず、口座別の残高を持つ手段が無いため(詳細は [画面要件](./screen-requirements-fire-goal.md) B9)
  - **不動産時価はここではなく4.5の不動産管理(B7)で設定する。** 物件ごとに持つ値であり、資産種別ごとの前提値とは置き場所が違う
- 用途は以下の両方
  - 4.6の到達予測の入力パラメータとして使用(想定利回り)
  - ダッシュボードの分類別内訳の凡例でリスク度合いを可視化する際の表示用データとして使用(リスクレベル)
- リスクレベルは到達予測の計算そのものには効かせない。予測に幅を持たせるかは今後の検討事項とする

### 4.8 負債管理

- 住宅ローン・カードローン・奨学金などの負債を、項目ごとに登録できる
- 管理項目
  - 項目名
  - 発生年月(借入を開始した月。任意)
  - 金利(年利)
  - 残債
  - 残りの返済期間
- **すべて手動入力とする**。マネーフォワードは負債をCSVに出力しないため、4.2のCSV取込の対象にはならない
- **自動計算は行わない**。金利・残りの返済期間から毎月の返済額や完済日を導いたり、時間の経過で残債を自動的に減らしたりはしない。金利と残りの返済期間は参考情報として保持・表示するだけで、集計に使うのは残債のみ
- 残債の更新も手動で行う。ただし**更新のたびにその日付の残債を履歴として記録**し、資産推移グラフが各時点の残債を差し引けるようにする(履歴の記録に追加の入力操作は求めない)
- 履歴は登録した月からしか積まれないため、**発生年月を入力すればその月まで遡って反映する**。遡る期間には最も古い記録の残債を当てる(実際の残債は分からないため。詳細は[画面要件](./screen-requirements-dashboard.md) B1「発生年月からの反映」)。**当初借入額からの補間や、金利・返済期間からの逆算は行わない** — 上記の「自動計算は行わない」に反するため
- 4.3の分類軸から集計対象として選べるようにし、選ばれた負債は4.4のダッシュボード(資産推移グラフ・分類別内訳・FIRE達成度)に反映する
- 4.5の不動産のローン残高とは別に管理する。あちらは物件ごとの利ざや(時価 - ローン残高)を出すための項目で、**どちらかがもう一方を参照することはしない**
  - ただし4.3の分類軸で物件を「利ざやを反映する」で選んだ場合、その物件のローン残高は利ざやの中で差し引かれた形でダッシュボードに効く。**同じローンをこちらの負債にも登録し、同じ分類軸で選ぶと二重に差し引かれる**。どちらか一方にする(判断はユーザーに委ね、画面では注記で知らせる。[画面要件](./screen-requirements-dashboard.md) B4)
  - 物件を「時価を反映する」で選んだ場合は、ローン残高はダッシュボードに効かない。住宅ローンをこちらの負債として登録して分類軸で選べば、資産側は時価・負債側は残債として別々に見える

## 5. 非機能要件

- **アダプティブデザイン**: PC/タブレット/スマートフォンでの利用を想定し、画面幅に応じたレイアウト最適化を行う
- **拡張性**: 資産分類・不動産の管理項目など、今後の仕様追加を見越してマスタデータ／スキーマの拡張がしやすい設計とする
- **セキュリティ**: 個人の資産・金融情報を扱うため、Firebase Authenticationによる認証を必須とし、Firestoreのセキュリティルールでユーザー単位のデータアクセス制御を行う
  - **ただしユーザー単位のアクセス制御と、画面の要件そのものは別**である。後者にはルールで担保できていないものがあり、一覧を8.1に置いた。SaaS化(7章 Phase 5)の前に見直す

## 7. MVPスコープとフェーズ分け

早期リリースを優先し、MVPは以下のように狭いスコープから開始する。

| フェーズ | 内容 |
|---|---|
| **Phase 1(MVP)** | Firebase Authentication認証、手動CSVアップロード(資産残高推移)、基本ダッシュボード(資産推移グラフ、分類別内訳円グラフ) |
| **Phase 2** | 入出金明細CSV取込、収支サマリ(月次収支・費目別支出) |
| **Phase 3** | 不動産管理機能(物件登録、時価・ローン残高管理、利ざや自動計算)、負債管理(手動登録、分類軸への反映) |
| **Phase 4** | FIRE目標設定・達成度ゲージ・到達期間予測、想定利回り/リスクの手動設定とシミュレーション反映 |
| **Phase 5(将来検討)** | マネーフォワード定期自動取得への対応、SaaS化(マルチテナント・権限モデル設計) |

### 8.1 クライアントだけが担保している制約

**他人のデータに触れないことは `firestore.rules` が担保している**(`canAccessOwnData()`)。ここに挙げるのはそれとは別の話で、**画面の要件として決まっているのにルールでは検査していない制約**の一覧である。単一ユーザー運用の現在は、破れても壊れるのは自分のデータだけなので許容している。

**SaaS化(7章 Phase 5)の前にこの表を見直す。** そのときに探し始めると見落としたものが本番の穴になるため、先に洗い出して残す。一覧の維持は `firestore.rules` を変えたときに合わせて行う(ルール側にも同じ趣旨のコメントを置いてある)。

「ルールで書けるか」は Firestore のセキュリティルールの制約による区別である。**素直に書ける部類だった5件は [B4-6](https://trello.com/c/UnKHeOdv) で `firestore.rules` へ戻し、この表から落とした**(後掲)。残っているのは、ルールでは書けないものと、書けるが設計の判断が要るものになる。

**`properties.acquiredOn` / `properties.valueHistory` / `categoryAxes.propertyValuations` に関する行は [B4-8](https://trello.com/c/8U3xoGJj) で足したもので、フィールド自体がまだ実装されていない。** 実装したときに同じ性質の穴が開くことが分かっているので先に載せてある。ルールに探しに行っても現時点では見つからない。

| コレクション | ルールが見ていない制約 | 破れたときに起きること | ルールで書けるか |
|---|---|---|---|
| `categoryAxes` | 生きている負債・物件を参照したままの分類軸を削除させない(B4の遷移条件)。`assetTypeNames` 側だけをルールで見ている | 何も集計していない軸と区別せずに軸が消える。負債・物件そのものは消えない | **書けない** — 可変長の `debtIds` / `propertyValuations` を1件ずつ `exists()` で辿る必要がある([B4-3](https://trello.com/c/j64HuOy6)) |
| `categoryAxes` / `settings/fireGoal` / `settings/assumptions` | 参照先(負債ID・物件ID・分類軸ID・資産種別名)が実在すること | 存在しないものを指す設定が作れる。読み出し側は既定へフォールバックする作りなので表示は壊れない | **書けない**(可変長)。単一の `achievementAxisId` は `exists()` で書けるが、読み取りが増えB4の削除と競合する |
| `assetSnapshots.byType` / `settings/assumptions.entries` / `debts.balanceHistory` / `properties.valueHistory` | 値が数値であること(キーが動的に増減するマップ。`valueHistory` は値が時価とローン残高の組) | 数値でない値が混じり、集計側で弾かれる。1件の不整合で画面が空になる箇所がある | **書けない** — ルールに繰り返しが無い。件数の上限だけ見ている |
| `categoryAxes.assetTypeNames` / `.debtIds` / `.propertyValuations` | 要素が文字列であること(`propertyValuations` は値が `"spread"` / `"marketValue"` のいずれかであること) | 同上 | **書けない**(同上) |
| `debts.originatedOn` / `properties.acquiredOn` | 発生年月・取得年月が**当月より後でない**こと(形は `yyyy-MM` で検査済み) | まだ借りていない負債・まだ取得していない物件が、過去の資産推移グラフに反映される | **書けるが要検討** — `request.time` はUTCで、クライアントが入れるのはローカルの年月。月をまたぐ前後で正常な入力を弾く(`updatedAt` と同じ制約) |
| `debts` | 登録できる負債は50件まで(`DEBT_MAX_COUNT`) | 51件目以降が作れる。B4の `debtIds` の上限(50)と食い違う | **書けない** — ルールはコレクションの件数を数えられない |
| `debts.balanceHistory` / `properties.valueHistory` | 追記するのは**値が変わった日だけ**であること | 値が変わっていない日の記録が増える。履歴の件数上限(600件)に早く届く | **書けない** — 追記されたキーの値を「直前の記録」と比べる必要があり、キーの前後関係を辿れない |
| `debts.updatedAt` / `properties.updatedAt` | 保存した日そのものであること(形は `yyyy-MM-dd` で検査済み) | 「最終更新日」が実際と違う日付になり、いつ時点の残債・時価か分からなくなる | **書けるが要検討** — `request.time` はUTCで、クライアントが入れるのはローカル日付。日付が変わる前後でずれるため、許容幅を決めないと正常な保存を弾く |
| `transactions` | 1回の取込で20,000行まで(`MAX_TRANSACTION_ROWS`)/ 同一CSV内で `ID` が重複しないこと / 1件でも不正なら1件も取り込まないこと(入出金明細CSV取込 要件定義書 2.3) | 上限を超える取込や、部分的に反映された取込ができる | **書けない** — ルールは1ドキュメントずつ評価する |
| `assetSnapshots` | 1回の取込で20,000行まで(`MAX_ASSET_BALANCE_ROWS`) | 上限を超える取込ができる | **書けない**(同上) |
| `settings/assumptions` | 想定利回りが±100%以内・リスクレベルが3値のいずれか | 範囲外の想定でシミュレーションが動く | **書けない**(値がマップの中にあり繰り返しが要る) |

#### [B4-6] でルールへ戻した制約

ルールを読むときの手掛かりとして、既に担保されているものも残しておく。

| 戻した制約 | ルール側の書き方 |
|---|---|
| `importedAt` / `createdAt` / `updatedAt`(timestamp)がサーバー時刻であること | `isServerTime()`(`== request.time`)。`createdAt` は**作成時だけ**要求する — 更新では既存の値が `request.resource.data` に現れるため |
| `csvImports` の `periodFrom <= periodTo` | `yyyy-MM-dd` は辞書順が日付順なので文字列比較 |
| `settings/fireGoal` の方式ごとの必須 | `mode` ごとに必要な欄が `null` でないことを要求 |
| `debts.balanceHistory` の改ざん防止(過去へ遡って書き換えさせない・過去の日付を後から差し込ませない) | `isAppendOnlyBalanceHistory()`(B4-8で足した `properties.valueHistory` も同じ形で検査する)。`diff()` の `removedKeys()` が0件、かつ `affectedKeys()`(追加・削除・変更のすべて)が `updatedAt` の日だけ。B11は同じ日に2回保存するとその日の記録を上書きするので、その日だけは触れるようにしないと通常の保存し直しが落ちる |
| `transactions.amount` が整数であること | `is int`。JS SDKは安全な整数を `integerValue`、小数を `doubleValue` で送る |
