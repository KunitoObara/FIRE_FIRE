# 画面要件定義書:アカウント系画面(B10)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.5節のアカウント系画面(B10)、および2.6節のうちアカウントに関わる共通操作(ログアウト)について、要件を詳細化したものである。認証方式の全体方針は [ログイン画面・認証機能 要件定義書](./auth-login-requirements.md) を参照。

## 2. 共通ヘッダーのユーザーメニューとログアウト

ログアウト([auth-login-requirements.md](./auth-login-requirements.md) 3.9)の導線を、ログイン後(B1〜B10)の共通ヘッダーに置くユーザーメニューに収める。独立した画面は設けないため画面IDを持たず、B1〜B10のすべての画面で同一に振る舞う。

### ユーザーメニュー

ヘッダー右端のアバターを押下で開くメニューとする。アバターからB10へ直接リンクする形にしないのは、ログアウトの置き場所が他に無いためで、B10への導線はメニュー内の項目として残す。

| 区分 | 項目 |
|---|---|
| 表示項目 | ログイン中のメールアドレス、アバター |
| 入力項目 | なし |
| 主な操作 | 「アカウント設定」項目、「ログアウト」項目 |

- ログイン中のメールアドレスをメニューの先頭に表示する。ログアウトの前に、どのアカウントでログインしているかを確かめられるようにするため
- 「ログアウト」は破壊的な操作ではないが後戻りに手間がかかるため、他の項目と区別できる見た目にする
- サイドバーには置かない。サイドバーは主要画面への遷移だけを並べる場所であり([screen-list-and-transitions.md](./screen-list-and-transitions.md) 3.3)、画面遷移でない操作を混在させない

### ログアウトの確認ダイアログ

「ログアウト」押下では即座に実行せず、確認ダイアログを表示する。2FAが全ユーザー必須のため、再ログインにはパスワードに加えて認証アプリの確認コードが要り、誤操作のコストが小さくないため。

| 区分 | 項目 |
|---|---|
| 表示項目 | 「ログアウトしますか?」、ログアウト後に何が起きるかの注記(下記のとおり呼び出し元の状態で出し分ける) |
| 主な操作 | 「ログアウトする」ボタン、「キャンセル」ボタン |

- 「キャンセル」押下 → ダイアログを閉じ、元の画面に留まる。ログアウトは実行しない
- 「ログアウトする」押下 → ログアウトを実行し、**A4 ログイン画面** へ遷移する

**注記の出し分け**

ダイアログは共通のコンポーネントを1つ用意し、見出し・ボタン・実行内容は呼び出し元によらず同一とする。**注記の文言だけは呼び出し元の2FA登録状況に応じて出し分ける。**

| 呼び出し元 | 注記の内容 |
|---|---|
| ログイン後の共通ヘッダー(B1〜B10) | 再ログインにはパスワードに加えて認証アプリの確認コードが必要である旨 |
| A2・A3(3章の「別のアカウントでログイン」) | ログアウトして A4 へ移動する旨と、未完了の手順が残っていること(A2 はメールアドレスの確認、A3 は2FAの登録)。**認証アプリの確認コードには触れない** |

A2・A3 で確認コードに触れないのは、その時点では TOTP がまだ登録されておらず、「次回のログインで確認コードが必要」が事実と異なるため。誤操作を止めるという確認ダイアログの目的は、未完了の手順をやり直すことになると伝えれば同じく満たせる。

### ログアウト実行時の処理

- Firebase Authenticationの `signOut()` でローカルのセッションを破棄する
- クライアント側のデータ取得キャッシュを初期化する。共有端末で次の利用者に前の利用者の資産額が残って見えることを防ぐため
- メモリ上でのみ引き回している認証途中の状態(A5の検証セッション、A8の連携セッション)も破棄する
- A4へは**履歴を置き換えて**遷移する。ブラウザの「戻る」でログイン後の画面に戻れても、ガードがA4へ差し戻すだけで意味がないため
- 「ログイン状態を保持する」を選んでいた場合も、ログアウト後にブラウザを開き直してサインイン状態が復元されてはならない([auth-login-requirements.md](./auth-login-requirements.md) 3.9)

**エラー時の扱い**

- `signOut()` はローカルのセッション破棄が主で、失敗はほぼ起こらない。それでも失敗した場合はダイアログを閉じずにその場でエラーを表示し、再試行できるようにする。中途半端にA4へ遷移させると、サインイン状態のままログイン画面を見せることになるため
- Firebaseの設定不足でそもそも認証を初期化できない場合は、この画面に到達する前にガードが設定エラーを表示している

### 適用範囲

- ログアウトはその端末・そのブラウザに閉じた操作である。全端末からのログアウトは行わない([auth-login-requirements.md](./auth-login-requirements.md) 8章のオープン課題)
- 「ログイン状態を保持する」を選んでいた場合(既定)、同一ブラウザの他のタブにも認証状態の変化が伝播し、他タブも自動的にA4へ戻る
- ログアウトはログイン通知([auth-login-requirements.md](./auth-login-requirements.md) 3.6)の対象外

## B10. アカウント設定画面

- **画面目的**: ログイン後にパスワード変更・2FA再設定などのアカウント関連設定を行う

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録メールアドレス、2FA設定状況、連携済みログイン方法の一覧 †、リカバリーコードの残り本数 ‡ |
| 入力項目 | なし(操作はボタン起点。パスワードの現在値入力は不要) |
| 主な操作 | 「パスワード変更メールを送信する」ボタン、「2FAを再設定する」ボタン、「Googleと連携する」/「連携を解除する」ボタン †、「リカバリーコードを再発行する」ボタン ‡ |

**遷移条件**

- 「パスワード変更メールを送信する」押下 → **A6 パスワードをお忘れの方画面**〜**A7 パスワード再設定画面** と同じリセットメールフローを使用し、登録メールアドレス宛にリセットリンクを送信する(現在のパスワード入力は不要)
- 「2FAを再設定する」押下 → 本人確認(パスワード再入力等)を経て現在の2FA設定を無効化し、**A3 2FA登録画面** と同様のQRコード登録フローを再実行する
- 2FA再設定完了後 → **B1 ダッシュボード画面** へ遷移
- 「リカバリーコードを再発行する」押下 → 画面遷移せず、新しいコード一覧を画面内に表示する(A3の表示と同じく平文はその場限り。ダウンロードも同様に用意する)。以前のコードはすべて無効になる ‡

### リカバリーコードの再発行 ‡

2FAリカバリーコード([auth-login-requirements.md](./auth-login-requirements.md) 3.3)の再発行導線をこの画面に置く。以前のコードをすべて無効にして8本を作り直し、平文をその場で一度だけ表示する。

再発行にも「2FAを再設定する」と同じ**本人確認(パスワード再入力等)を求める**。再発行は以前のコードを無効化するため、セッションを乗っ取られた状態で実行されると、正規の利用者が持っているコードだけが使えなくなる(2FAそのものの突破には繋がらないが、認証アプリ紛失時の復旧手段を失う)。現状の `generateMfaRecoveryCodes` はサインイン済みであることしか確認していないため、この画面を実装する際に本人確認の要求を追加する。

> ‡ **B10側のUIは未実装。** Trelloカード [A3-2] 2FAリカバリーコード ではA3の発行・A5の使用と、発行/再発行に使うCloud Functions(`generateMfaRecoveryCodes`)までを実装済み。B10の画面自体がまだ無いため、この画面を作るカードで既存のcallableを呼ぶUI(残り本数の表示と再発行ボタン)を追加する。残り本数はFirestoreを直接読ませず、callableの応答から得る(セキュリティルールでクライアントからの参照を全面的に拒否しているため)。

### 連携アカウントの管理 †

ソーシャルログイン([auth-login-requirements.md](./auth-login-requirements.md) 3.8)で連携できるログイン方法を、この画面から確認・追加・解除する。

| 表示・操作 | 仕様 |
|---|---|
| ログイン方法の一覧 | 「メールアドレス / パスワード」「Google」を行として表示し、各行に連携状況(連携済み / 未連携)を示す。Google行には連携済みのGoogleアカウントのメールアドレスを併記する |
| 「Googleと連携する」 | 未連携の場合に表示。Googleのサインインポップアップを開き、成功したら現在のアカウントにGoogleを連携する |
| 「連携を解除する」 | 連携済みの場合に表示。確認ダイアログを挟んでから解除する |

**制約・エラー**

- **最後に残った1つのログイン方法は解除できない**。解除するとアカウントにサインインする手段が無くなるため、ボタンを無効化し理由を併記する(例: Googleのみで作成したアカウントはGoogleの解除不可)
- 連携しようとしたGoogleアカウントが**別のFIRE-FIREアカウントに既に紐付いている**場合(`auth/credential-already-in-use`)は連携できない。画面内にその旨をエラー表示する
- 連携しようとしたGoogleアカウントのメールアドレスが**このアカウントの登録メールアドレスと異なる**場合も連携自体は可能だが、ログイン通知([auth-login-requirements.md](./auth-login-requirements.md) 3.6)の宛先は登録メールアドレスのままである旨を注記する
- 解除・連携のいずれも、成否を画面内のメッセージで伝え、画面遷移はしない

> † **連携アカウントの管理は未実装。** Trelloカード [A8-2] 連携アカウント管理(B10) で扱う。[A8] ソーシャルログイン(Google)対応 ではA1・A4のログイン導線とA8 アカウント連携画面までを対象とし、B10側のUIは本ドキュメントの記述どおり後続カードで実装する。
