# 画面要件定義書:アカウント系画面(B10)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.5節のアカウント系画面(B10)、および2.6節のうちアカウントに関わる共通操作(ログアウト)について、要件を詳細化したものである。認証方式の全体方針は [ログイン画面・認証機能 要件定義書](./auth-login-requirements.md) を参照。

## 2. 共通ヘッダーのユーザーメニューとログアウト

ログアウト([auth-login-requirements.md](./auth-login-requirements.md) 3.9)の導線を、ログイン後(B1〜B11)の共通ヘッダーに置くユーザーメニューに収める。独立した画面は設けないため画面IDを持たず、B1〜B11のすべての画面で同一に振る舞う。

### ユーザーメニュー

ヘッダー右端のアバターを押下で開くメニューとする。アバターからB10へ直接リンクする形にしないのは、ログアウトの置き場所が他に無いためで、B10への導線はメニュー内の項目として残す。

| 区分 | 項目 |
|---|---|
| 表示項目 | ログイン中のメールアドレス、アバター |
| 入力項目 | なし |
| 主な操作 | 「アカウント設定」項目、「ログアウト」項目 |

- ログイン中のメールアドレスをメニューの先頭に表示する。ログアウトの前に、どのアカウントでログインしているかを確かめられるようにするため
- 「ログアウト」は破壊的な操作ではないが後戻りに手間がかかるため、他の項目と区別できる見た目にする
- サイドバーには置かない。サイドバーはログイン後に**相互に自由遷移できる主要画面(B1〜B11)を並べる場所**であり([screen-list-and-transitions.md](./screen-list-and-transitions.md) 3.3)、そこから出ていく操作は並べない。ログアウトはシェルの外(A4)へ抜ける唯一の導線のため、性質が異なる

### ログアウトの確認ダイアログ

「ログアウト」押下では即座に実行せず、確認ダイアログを表示する。2FAが全ユーザー必須のため、再ログインにはパスワードに加えて認証アプリの確認コードが要り、誤操作のコストが小さくないため。

| 区分 | 項目 |
|---|---|
| 表示項目 | 「ログアウトしますか?」、ログアウト後に何が起きるかの注記(下記のとおり呼び出し元の状態で出し分ける) |
| 主な操作 | 「ログアウトする」ボタン、「キャンセル」ボタン |

- 「キャンセル」押下 → ダイアログを閉じ、元の画面に留まる。ログアウトは実行しない
- 「ログアウトする」押下 → ログアウトを実行し、**A4 ログイン画面** へ遷移する

**注記の出し分け**

ダイアログは共通のコンポーネントを1つ用意し、見出し・ボタン・実行内容は呼び出し元によらず同一とする。**注記の文言だけは呼び出し元の2FA登録状況に応じて出し分ける。**

| 呼び出し元 | 注記の内容 |
|---|---|
| ログイン後の共通ヘッダー(B1〜B11) | 再ログインにはパスワードに加えて認証アプリの確認コードが必要である旨 |
| A2・A3(3章の「別のアカウントでログイン」) | ログアウトして A4 へ移動する旨と、未完了の手順が残っていること(A2 はメールアドレスの確認、A3 は2FAの登録)。**認証アプリの確認コードには触れない** |

A2・A3 で確認コードに触れないのは、その時点では TOTP がまだ登録されておらず、「次回のログインで確認コードが必要」が事実と異なるため。誤操作を止めるという確認ダイアログの目的は、未完了の手順をやり直すことになると伝えれば同じく満たせる。

### ログアウト実行時の処理

- Firebase Authenticationの `signOut()` でローカルのセッションを破棄する
- クライアント側のデータ取得キャッシュを初期化する。共有端末で次の利用者に前の利用者の資産額が残って見えることを防ぐため
- メモリ上でのみ引き回している認証途中の状態(A5の検証セッション、A8の連携セッション)も破棄する
- A4へは**履歴を置き換えて**遷移する。ブラウザの「戻る」でログイン後の画面に戻れても、ガードがA4へ差し戻すだけで意味がないため
- 「ログイン状態を保持する」を選んでいた場合も、ログアウト後にブラウザを開き直してサインイン状態が復元されてはならない([auth-login-requirements.md](./auth-login-requirements.md) 3.9)

**エラー時の扱い**

- `signOut()` はローカルのセッション破棄が主で、失敗はほぼ起こらない。それでも失敗した場合はダイアログを閉じずにその場でエラーを表示し、再試行できるようにする。中途半端にA4へ遷移させると、サインイン状態のままログイン画面を見せることになるため
- Firebaseの設定不足でそもそも認証を初期化できない場合は、この画面に到達する前にガードが設定エラーを表示している

### 適用範囲

- ログアウトはその端末・そのブラウザに閉じた操作である。全端末からのログアウトは行わない([auth-login-requirements.md](./auth-login-requirements.md) 8章のオープン課題)
- 「ログイン状態を保持する」を選んでいた場合(既定)、同一ブラウザの他のタブにも認証状態の変化が伝播し、他タブも自動的にA4へ戻る
- ログアウトはログイン通知([auth-login-requirements.md](./auth-login-requirements.md) 3.6)の対象外

## B10. アカウント設定画面

- **画面目的**: ログイン後にパスワード変更・2FA再設定などのアカウント関連設定を行う

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録メールアドレス、2FA設定状況、連携済みログイン方法の一覧 †、リカバリーコードの残り本数 ‡ |
| 入力項目 | 画面本体にはなし(操作はボタン起点)。「2FAを再設定する」「リカバリーコードを再発行する」「メールアドレス / パスワードの連携を解除する」は、後述の本人確認ダイアログでパスワードを再入力する |
| 主な操作 | 「パスワード変更メールを送信する」ボタン、「2FAを再設定する」ボタン、「Googleと連携する」/「連携を解除する」ボタン †、「リカバリーコードを再発行する」ボタン ‡、**「アカウントを削除する」ボタン** |

**遷移条件**

- 「パスワード変更メールを送信する」押下 → **A6 パスワードをお忘れの方画面**〜**A7 パスワード再設定画面** と同じリセットメールフローを使用し、登録メールアドレス宛にリセットリンクを送信する(現在のパスワード入力は不要)
- 「2FAを再設定する」押下 → 本人確認(パスワードの再入力)を経て現在の2FA設定を無効化し、**A3 2FA登録画面** と同様のQRコード登録フローを再実行する。無効化は `resetMfaEnrollment`(Cloud Functions)で行い、パスワードの照合もサーバー側で行う。クライアントSDKの `multiFactor().unenroll()` を使わないのは、2FA登録済みのユーザーの再認証がパスワードだけでは完了せず認証アプリの確認コードまで要求され、本人確認をパスワードの再入力とする方針と噛み合わないため。呼び出しにはサインイン済みのIDトークン(=2FAを通過したセッション)が要るので、パスワードだけで2FAを外せる経路にはならない
- 2FA再設定完了後 → **B1 ダッシュボード画面** へ遷移
- 「リカバリーコードを再発行する」押下 → 画面遷移せず、新しいコード一覧を画面内に表示する(A3の表示と同じく平文はその場限り。ダウンロードも同様に用意する)。以前のコードはすべて無効になる ‡
- 「アカウントを削除する」押下 → 確認ダイアログで**登録メールアドレスとパスワード**を入力させ、`deleteAccount`(Cloud Functions)を呼ぶ。成功したら **A0 サービストップページ** へ履歴を置き換えて遷移し、完了メッセージをそこで1回だけ出す(下記)

### リカバリーコードの再発行 ‡

2FAリカバリーコード([auth-login-requirements.md](./auth-login-requirements.md) 3.3)の再発行導線をこの画面に置く。以前のコードをすべて無効にして8本を作り直し、平文をその場で一度だけ表示する。

再発行にも「2FAを再設定する」と同じ**本人確認(パスワードの再入力)を求める**。再発行は以前のコードを無効化するため、セッションを乗っ取られた状態で実行されると、正規の利用者が持っているコードだけが使えなくなる(2FAそのものの突破には繋がらないが、認証アプリ紛失時の復旧手段を失う)。

本人確認の要求は画面側だけでなく `generateMfaRecoveryCodes` 自身が行う。UIを通さずcallableを直接叩かれても同じ穴が開くため。ただしA3の初回発行では本人確認を挟まない(2FA登録の直後に自動で発行するため)ので、**「いま登録されている2FAに対して有効なコードが既にある場合」に限ってパスワードを必須にする**。無効化されて困るコードが存在するときだけ、というのがこの条件の意味である。判定には保存済みコードの発行日時と2FAの登録日時の前後を使い、2FAを解除するとき(A5のリカバリーコード使用・B10の再設定)には保存済みのコードも破棄する。**必須でない場合も、パスワードが渡されていれば必ず検証する** — B10は未発行の状態でも本人確認ダイアログを出すため、素通しにすると「本人確認のため入力してください」と言いながら確かめていないことになる。

A3側でこの本人確認に当たった場合(サーバー側では発行が成功したのに応答が届かなかったとき)は、A3では解消できない。A3にパスワードの入力欄は無く、同じ操作を繰り返しても結果が変わらないため、A3は再発行ボタンを出さずB10での再発行へ案内する。

> ‡ **B10側のUIは実装済み。** Trelloカード [A3-2] 2FAリカバリーコード でA3の発行・A5の使用と、発行/再発行に使うCloud Functions(`generateMfaRecoveryCodes`)を、[B10] アカウント設定画面 で残り本数の表示・再発行ボタン・上記の本人確認を実装した。残り本数はFirestoreを直接読ませず、`getMfaRecoveryCodeStatus` の応答から得る(セキュリティルールでクライアントからの参照を全面的に拒否しているため)。

### アカウントの削除

アカウントと利用者のデータをすべて削除する導線をこの画面に置く([auth-login-requirements.md](./auth-login-requirements.md) 3.11)。**A10 プライバシーポリシーが「利用者からの削除の求めへの対応」を掲げる以上、実行する手段が要る。**

| 項目 | 仕様 |
|---|---|
| 置き場所 | この画面の**最後**。設定を見に来ただけの人の目に最初に入る場所ではない |
| 本人確認 | **登録メールアドレスの入力 + パスワードの再入力**。照合はどちらもサーバー側(`deleteAccount`)で行う |
| 消える範囲 | アカウント(認証情報)と、取り込んだ資産・入出金・不動産・負債のデータすべて。範囲の詳細は 3.11 |
| 成功後 | **A0 サービストップページ**へ履歴を置き換えて遷移し、「削除しました」をA0で1回だけ出す |
| 失敗時 | ダイアログを閉じず、その場にメッセージを出して入力し直せるようにする(他の本人確認ダイアログと同じ) |

- **本人確認をパスワードだけにしない。** 2FA再設定・リカバリーコード再発行・パスワード解除はパスワードのみで揃えてあるが、**削除だけは復旧できない**ため、確認の強度を1段上げて登録メールアドレスの入力も求める(PO判断)
- **入力の一致は画面では判定しない。** 画面は登録メールアドレスを持っているが、照合はサーバー側で行う。画面だけで判定すると、UIを通さない呼び出しが確認を素通りできる
- **パスワードでのログインが無いアカウント(Googleのみ)はボタンを無効化する。** 本人確認を通せないためこの画面からは削除できず([auth-login-requirements.md](./auth-login-requirements.md) 3.3の他の操作と同じ制約)、押せてしまうと入力しきってから断られることになる。**できない理由と、代わりに問い合わせへ案内する旨を併記する**
- **失敗の文言を2つに分ける。** 「データを消せなかった(アカウントは残っている)」と「データは消えたがアカウントを消せなかった」では、利用者が次に取る行動が違う。後者はやり直しが要ることを伝えないと、消えたのか残ったのかが分からない
- 成功後の遷移先をA4ではなくA0にしたのはPO判断による。削除した人はもう利用者ではないため、ログインを促す画面より公開トップのほうが自然なため
- **完了メッセージには再登録に招待が要ることまで書く。** 許可リストの該当ドキュメントも削除するため、同じメールアドレスでもそのままでは登録し直せない([auth-login-requirements.md](./auth-login-requirements.md) 3.10・3.11)

### 連携アカウントの管理 †

ソーシャルログイン([auth-login-requirements.md](./auth-login-requirements.md) 3.8)で連携できるログイン方法を、この画面から確認・追加・解除する。

| 表示・操作 | 仕様 |
|---|---|
| ログイン方法の一覧 | 「メールアドレス / パスワード」「Google」を行として表示し、各行に連携状況(連携済み / 未連携)を示す。Google行には連携済みのGoogleアカウントのメールアドレスを併記する |
| 「Googleと連携する」 | 未連携の場合に表示。Googleのサインインポップアップを開き、成功したら現在のアカウントにGoogleを連携する |
| 「連携を解除する」 | 連携済みの場合に表示。Googleは確認ダイアログを挟んでから解除する。メールアドレス / パスワードの解除だけは本人確認(パスワードの再入力)を求める(後述) |

**制約・エラー**

- **最後に残った1つのログイン方法は解除できない**。解除するとアカウントにサインインする手段が無くなるため、ボタンを無効化し理由を併記する(例: Googleのみで作成したアカウントはGoogleの解除不可)
- 連携しようとしたGoogleアカウントが**別のFIRE-FIREアカウントに既に紐付いている**場合(`auth/credential-already-in-use`)は連携できない。画面内にその旨をエラー表示する
- 連携しようとしたGoogleアカウントのメールアドレスが**このアカウントの登録メールアドレスと異なる**場合も連携自体は可能だが、ログイン通知([auth-login-requirements.md](./auth-login-requirements.md) 3.6)の宛先は登録メールアドレスのままである旨を注記する
- 解除・連携のいずれも、成否を画面内のメッセージで伝え、画面遷移はしない

**メールアドレス / パスワードの解除**

パスワード側も同じ条件(最後の1つでなければ解除可)で解除できる。ただし解除するとログイン手段以外も失うため、**確認ダイアログでその旨を明記したうえで、本人確認としてパスワードの再入力を求める**。

- パスワードの再確認を伴う操作 — 2FAの再設定・リカバリーコードの発行/再発行・A5でのリカバリーコード使用 — はパスワードを持たないアカウントでは実行できない([auth-login-requirements.md](./auth-login-requirements.md) 3.3)
- このアプリにはGoogleのみのアカウントへパスワードを設定する導線が無い(同 8章のオープン課題)ため、解除は事実上やり直せない
- したがって解除は「Googleでログインできなくなる」だけでなく「認証アプリを失ったときの復旧手段を手放す」操作でもある。実行前に伝えたうえで、判断そのものはユーザーに委ねる
- **本人確認を求めるのはパスワードの解除だけ**とする。Googleの解除は連携し直せる可逆な操作で、失うものの範囲も違うため、確認ダイアログのみを挟む
- 本人確認の強度は「2FAを再設定する」「リカバリーコードを再発行する」と揃える。いずれもセッションを乗っ取られた状態で実行されると、正規の利用者から復旧手段だけを奪える操作であるため
- 検証と解除はサーバー側でまとめて行う。2FA登録済みのユーザーはクライアントSDKの再認証がパスワードだけでは完了せず確認コードまで要求されるため、パスワードの検証はCloud Functions側でしか行えない(「2FAの再設定」と同じ理由)。検証だけをサーバーに置いて解除をクライアントで行うと、検証を通したことが自己申告になり解除の前提として意味を持たない
- ただしこれはクライアントSDKによる解除を禁止するものではない。Identity Platformにはユーザー更新のブロッキング関数が無く、有効なIDトークンを持つ相手はAPIを直接叩いて解除できる。担保できるのは**このアプリが提供する経路では本人確認を必ず通る**ことまで

> † **連携アカウントの管理は実装済み。** Trelloカード [A8-2] 連携アカウント管理(B10) で実装した。[A8] ソーシャルログイン(Google)対応 ではA1・A4のログイン導線とA8 アカウント連携画面までを対象とし、B10側のUI(一覧・連携・解除)はこのカードで追加した。連携状況はFirestoreではなくFirebase Authの `providerData` から作る(`src/frontend/src/lib/auth/linked-providers.ts`)。パスワード解除の本人確認は [A8-3] パスワード解除に本人確認を挟む(B10) で追加し、解除自体も `unlinkPasswordProvider` callable(`src/backend/src/linked-providers/functions.ts`)へ移した。
