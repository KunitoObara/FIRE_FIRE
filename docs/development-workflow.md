# 開発フロー

Trelloカードを起点に、着手 → 実装 → PR → レビュー対応 → 完了までを進めるための手順書。カードから離れて `develop` を本番へ出すリリース(10章)もここに含める。
5つのスキル([.claude/skills/](../.claude/skills/))がこの文書を正本として動く。IDや判断基準を変えるときはこの文書を直す。

## 1. 全体の流れ

| 段階 | 実行するもの | やること |
|---|---|---|
| 着手 | `/card-start` | 確認中カードのマージ同期 → 着手カード選定 → 要件読込 → **まとめて質問** → **PRの分割要否を決める** → 作業ブランチ作成 |
| 分割 | `/card-split` | 単独でCIを通せる単位へ切る(5章)。実装前に計画するのが既定で、大きくなってからの切り出しは高くつく |
| 実装 | (通常の対話) | 実装 → ローカル検証コマンド一式 |
| PR | `/card-ship` | **差分の大きさを確認** → コミット → push → PR作成 → カードを**確認中**へ移動 |
| レビュー対応 | `/card-review` | CI・レビューの完了待ち → 指摘の分類 → **重大でないものはPOへ確認** → 修正して push(=1往復) |
| マージ | **人間(PO)のみ** | Claudeはマージしない |
| 完了 | 次回の `/card-start` | **そのカードのPRが全部**マージ済みなら**完了**へ移動 |
| リリース | `/release` | `develop` → `main` のPRを作る → マージ後にデプロイ結果を確認する(10章)。カードを起点にしない唯一の工程 |

Claudeが自発的にTrelloの変化を検知することはできない(Webhookを受ける口がない)。
着手はユーザーが `/card-start` を叩くことで始まり、マージ検知は次回の `/card-start` 冒頭でまとめて行う。

完了の表現は**完了リストへの移動のみ**とする。Trelloの「完了としてマーク」は期限日とセットのフラグ(`dueComplete`)で、期限日を持たないカードではUIに現れない。カードに期限日を自動で入れるのは運用上の副作用が大きいため、リスト位置を唯一の完了状態とする。

### スキルが読む範囲

**この文書を毎回まるごと読ませない。** 各スキルは自分の段階に要る章だけを読む。全体を読ませると、その回の判断に関係しない記述で文脈が埋まる。

| スキル | 読む章 |
|---|---|
| `/card-start` | 2章(ボード・ID)・3章(着手時に読むもの)・4章(質問)・5章(ブランチ規約と分割の要否) |
| `/card-split` | 5章 |
| `/card-ship` | 5章(PR規約・分ける目安)・6章(検証とセルフレビュー) |
| `/card-review` | 7章(レビュー対応)・9章(前提と制約) |
| `/release` | 9章(前提と制約)・10章(リリース) |

8章の歯止めは全スキル共通の禁止事項で、実装の詳細は [command-guards.md](./command-guards.md) にある。**歯止めを変えるとき以外は読まなくてよい。**

## 3. 着手時に読むもの

カードの説明文には「画面目的 / 表示項目 / 入力項目 / 主な操作 / 遷移条件」と、HTMLモックのパス・参照ドキュメントのURLが入っている。着手時は次を必ず読む。

1. カード本文とチェックリスト、既存コメント
2. カード本文が参照している `docs/` 配下の要件定義書
3. カード本文に書かれた `src/frontend/docs/html_mock/` のHTMLモック
4. ルートの `CLAUDE.md`、`DESIGN.md`、`src/frontend/docs/CODING_STANDARDS.md`

## 4. 質問のまとめ方

実装に入る前に、不明点を**1回にまとめて**質問する。実装の途中で小出しに聞かない。

質問する / しないの線引き:

- **質問する** — 解釈が割れると成果物が変わるもの。要件定義書とHTMLモックが食い違っている、カードのスコープ境界が曖昧、既存画面の挙動を変える必要がある、要件定義書に書かれていない仕様判断が必要
- **質問しない** — 慣例で決まるもの。ファイル配置、コンポーネント分割、命名、既存パターンの踏襲

判断材料が要件定義書と既存コードから揃うなら、質問せずそのまま実装に入ってよい。

## 5. ブランチ・コミット・PRの規約

既存の運用を踏襲する。

- **作業場所**: メインの作業ツリー。`develop` から直接ブランチを切る(worktreeは使わない)
- **ブランチ名**: `feature/fire-fire-<カードIDを小文字にしたもの>` — 例 `feature/fire-fire-b7`、`feature/fire-fire-a5-2`
  - **PRを分割した場合のスライスは `-part<N>` を付ける**(`feature/fire-fire-b11-part1`)。連番だけを足すと枝番カードのブランチ名(`feature/fire-fire-b11-2` = カード `[B11-2]`)と衝突し、マージ同期が別のカードを完了へ動かしうる
- **コミット/PRタイトル**: `B7 不動産登録・編集画面を実装` — 画面IDを先頭に、体言止めではなく「〜を実装」「〜に対応」
- **コミット本文**: なぜそうしたかを書く。「何を変えたか」はdiffで読めるので、判断の理由と却下した代案を残す
- **マージ方式**: squash merge(PO が実施)

### PR本文のフォーマット

```markdown
Trello: <カードのURL>

## 変更内容

(何を実装したか。参照した要件定義書へのリンクを添える)

## レビューで見てほしい点

(判断が分かれうる箇所、カード範囲外の変更、意図的に見送ったもの)

## 確認したこと

(実行したコマンドと結果)
```

「カード範囲外の変更」を含めた場合は、**必ず**「レビューで見てほしい点」に理由つきで明記する。

### PRの分割

**1つのカードが1つのPRである必要はない。** カードは要件の単位、PRはレビューの単位で、大きさの都合が合わないなら分ける。分割の手順は [`/card-split`](../.claude/skills/card-split/SKILL.md) が担う。

#### なぜ分けるのか

根拠はレビューの精度そのものにある。B11(PR #83、68ファイル・+3,533行)では、**ローカルのテストが緑のまま通ったデータ損失のバグが2件、レビューの往復を重ねて初めて出てきた**。

- 複数タブで開いていると、他方のタブが追加した負債が保存で消える
- 保存した直後にもう一度保存すると、負債が複製され残債の履歴が消える

どちらも自分で書いたテストでは拾えておらず、1往復目には出ず2・3往復目に出た。1回のレビューで差分全体に均等な注意を向けられる量には限りがある、と考えるのが自然な結果だった。

**claude-review が無投稿で終わる問題([B11-6](https://trello.com/c/65XaRqa6))とは分けて考えること。** あれは同じコミットの再実行で結果が変わり、PRの大きさとの相関は取れていない。分割はその対策**ではなく**、上のレビュー精度の話で正当化する。

#### 分ける目安

厳密な閾値ではなく、超えたら分割を検討する線として使う。

| 指標 | 目安 |
|---|---|
| 変更ファイル数 | 20を超えたら検討 |
| テストとロックファイルを除くソースの増減 | 800行を超えたら検討 |
| 触る画面ID | 3つ以上なら検討 |

**ロックファイル(`package-lock.json`)は増減に数えない。** frontend が約14,700行・backend が約6,600行あり、依存を1つ足すだけの変更でも800行を軽く超える。レビューする行はほとんど無いのに「分割を検討」と判定されては、指標として働かない。**変更ファイル数のほうには数える** — 1ファイルは1ファイルで、20の目安を歪めないため。

実績(この指標で測った値): PR #82 は4ファイル・26行で問題なくレビューされた。PR #83 は68ファイル・2,646行で上記のとおり。測り方は [`/card-split`](../.claude/skills/card-split/SKILL.md) B-1 にコマンドで書いてある。

#### 分ける順序

依存の下から上へ切る。**各PRが単独でCIを通せること**が唯一の必須条件で、これを満たせない切り方は採らない。

1. **土台** — `src/types` / `src/schemas` / `src/constants` / `firestore.rules` / リポジトリ。画面から参照されないので単体でCIを通せる
2. **新規画面** — ルート・コンポーネント・その画面のテスト
3. **既存画面への波及** — 1画面につき1PR。B1・B4・B8をまとめない
4. **表記の一括置換・ドキュメント** — 機械的な変更は必ず単独のPRにする。レビュー対象の差分を置換ノイズで埋めないため

#### 型の波及を切る手口

分割が破綻する最大の原因は、型に必須フィールドを足した瞬間に参照側が全部壊れることにある。**新しいフィールドは最初のPRでは任意にしておき、参照側が揃ってから必須に締める。**

- 型は `field?: T`、zodは `.default(...)` か `.optional()`、`firestore.rules` は `hasOnly` に足すだけで `hasAll` には入れない
- 締める変更は最後のPRで行い、そのPRの「レビューで見てほしい点」に「ここで必須化した」と書く

B11の `categoryAxes.debtIds` はこの形にできた(実際、既存ドキュメント向けに `.default([])` を入れてある)。

#### 中間状態の扱い

**「画面として使えない状態が develop に入る」ことは分割を見送る理由にならない。** `develop` の反映先は `fire-fire-dev`(STG)で、本番ではない。土台だけが入った状態は、機能が増えないだけで壊れてはいない。

見送る理由になるのは次のときだけ。

- 単独でCIを通せない
- 既存の画面が壊れる(データが読めなくなる、保存できなくなる)

#### カードとの対応

**カードは分けない。** 分割はレビューの都合であって要件の都合ではないため、1枚のカードに複数のPRがぶら下がる。

そのため、**分割すると決めたら実装に入る前にカードへ計画をコメントする**。1行目の書式は固定で、`/card-start` のマージ同期がこの行を読む。

```
分割計画: 全3本
```

これが無いと、1本目のPRがマージされた時点でカードが完了へ動く。カードは1本目のPRで確認中へ移り、2本目以降はまだPRになっていないため、コメント上は「PRが1本あって、それが済んでいる」状態にしか見えないため。総本数を先に置いておくことでその誤判定を防ぐ。計画を変えたときは新しい `分割計画:` のコメントを足す(最新のものが採られる)。

#### 積み方

**逐次(sequential)を既定とする。** 1本目をマージしてから `develop` を引き直して2本目を切る。

- squash mergeを使っているため、積み上げ(stacked)にすると1本目がsquashされた時点で2本目の履歴が合わなくなり、rebaseかcherry-pickのやり直しが要る
- マージはPOの操作なので、次のPRを出すまで待ちが入る。待てない場合だけ積み上げにし、**PR本文の冒頭に土台のPR番号を明記**して、レビュアーがどこまでを差分として見ればよいか分かるようにする

### セルフレビュー

検証を通したあと、コミットする前に**差分を通しで読み直す**。書いた人としてではなく、初めて読む人として読む。

**「テストが緑」と「正しい」の間には隙間がある。** [B11](https://trello.com/c/gX8pLM3S)(PR #83、68ファイル・+3,533行)では、ローカルのテストが緑のまま通ったデータ損失のバグが2件、レビューの往復を重ねて初めて出た。

- 複数タブで開いていると、他方のタブが追加した負債が保存で消える(2往復目に判明)
- 保存した直後にもう一度保存すると、負債が複製され残債の履歴が消える(3往復目に判明)

どちらも自分で書いたテストでは拾えていない。**思いつかなかったことはテストにも書かれない**ので、テストの緑はこの種の欠陥に対して何も言っていない。以下はその実例から起こした観点で、狙うのはこの隙間である。

| 観点 | 見るもの |
|---|---|
| 同時更新 | 別のタブ・別のセッションが書いた内容を上書きしないか。読んでから書くまでの間に他者が書いた場合どうなるか |
| 二重実行 | 同じ操作を連続で2回実行したときに、複製・履歴の消失が起きないか |
| 削除の波及 | 消したものを参照している側がどうなるか。参照が残ったまま画面が壊れないか |
| 部分失敗 | 途中で失敗したときに中途半端な状態が残らないか。複数の書き込みが揃って成立するか |

**観点ごとに「該当なし」か「確認した内容」を1行書く。** 書くことを強制しないと、読んだつもりのまま通る。書けない観点があるなら、それはまだ読めていない。

見つかった問題は**その場で直す**。レビューに回さない(プロジェクトスキルで見つかったものと同じ扱い)。

**この工程の限界を承知しておくこと。** 書いた本人が同じ文脈で見直す以上、実装時に見えていなかったものは見えないままでありうる。上の2件も、自分では気づけずレビューの往復で出たものである。**自動レビューや [`/card-review`](../.claude/skills/card-review/SKILL.md) の往復を置き換えるものではなく**、明らかな見落としを安く落とすための工程として置いている。ここを取り違えて往復を減らす方向に使うと、B11 で学んだことと逆になる。

## 7. レビュー対応のルール

### 何を「レビュー」とみなすか

1. **claude-review ボットのコメント** — [.github/workflows/claude-review.yml](../.github/workflows/claude-review.yml) が PR の `opened` / `synchronize` で投稿する
2. **CI(ci.yml)の失敗** — `wip-check` / `hooks` / `frontend` / `backend`
3. **PO(人間)のPRコメント**

### 重大でない指摘は、直す前にPOへ確認する

**claude-review の指摘のうち、重大でないものは勝手に直さない。** 何を直すかを指摘ごとにPOへ確認し、選ばれたものだけを直す。**毎ラウンド行う** — ラウンド番号ではなく重大かどうかだけで線を引く。

判定の基準は下の「3往復に達したあとの扱い」と同じものを使う。CIの失敗 / セキュリティ / データ破壊・損失 / 画面が機能しない、に当たるものは**確認せずそのまま直す**。止める理由が無く、確認を挟むと手が遅くなるだけのため。

なぜ確認するのか。**軽微な指摘を自動で3往復ぶん直すと、PRが長引くわりに得るものが小さい。** 1往復目の指摘が実装の欠陥でも、2往復目以降は表現の揺れや「あると安心」の域に入ることがある。直すかどうかはPRを出す側ではなくPOの判断で、そこを自動化すると、直さなくてよいものを直すために往復を1つ消費することになる。

確認するときは、**指摘そのものだけを並べない。** 次を添える。

- その指摘が妥当か、誤検知か(コードと要件定義書で裏を取った結果)
- 重大かどうかの判定と、その根拠
- 直す場合に何をどう変えることになるか

裏取りを省いて生のボット出力の是非を聞くと、判断の材料が無いまま選ばせることになり、確認を挟む意味が無い。

**確認の結果1件も直さなかった回は、往復に数えない。** 修正 push が発生していないため(下記のマーカーの規定と同じ理屈)。

**「直さない」と決まった指摘はバックログへ起票する。** 起票の宛先・ラベル・カード名・本文は下の「起票する新規カード」と同じものを使う。判断としては済んでいても、指摘が黙って消えたように見えないようにするため。起票したらPRにもその旨をコメントする。

**誤検知だけは起票しない。** 直すべきものが無いのにカードだけが残り、バックログが「そもそも問題ではなかったもの」で埋まる。**確認を経て**誤検知のまま見送りと決まったものは、PRコメントで根拠を示して返すだけにする。

**誤検知も確認には出す。** 誤検知という判定自体が外れていることがあり、そのときはPOが直す側を選べる必要があるため。**裏取りの段階では判定までにとどめ、対応は決めない** — 先に却下のコメントを投稿してしまうと、そのあとPOが「直す」を選んだときに投稿済みの内容と食い違う。

**上限に達したあとは確認しない。誤検知も含めて確認しない。** そこから先は重大でない指摘の行き先が決まっており、選ばせるものが無いため — 妥当なものは起票へ、誤検知はPRコメントで返すだけになる(どちらも下記)。

つまり**確認するのは上限に達するまでの、重大でない指摘だけ**である。上限の前後で誤検知の扱いが変わるわけではなく、変わるのは確認を挟むかどうかだけで、**行き先は指摘の分類だけで決まる**。

**一度片付けた指摘を、次のラウンドでもう一度扱わない。** claude-review は毎回**PR全体**をレビューする([claude-review.yml](../.github/workflows/claude-review.yml) のプロンプトは「このPRをレビューしてください」で、ブランチ全体がチェックアウト済み)。コードを直さない限り、見送った指摘は次のラウンドでも同じ趣旨で再投稿される。

- **同じことを何度も確認しない。** POは既に判断している。同じ問いが毎ラウンド飛ぶのは、それ自体が確認を挟む価値を下げる
- **同じ内容のカードを二重に起票しない。** 見送りのたびに起票する以上、放っておくとバックログに同じカードがラウンドの数だけ並ぶ
- 再投稿されたものはPRコメントで「前のラウンドで対応済み(または起票済み)」と、起票してあればそのカードへのリンクを添えて返す

**投稿時刻での絞り込みだけでは足りない。** 再投稿された指摘は新しい `created_at` を持つので、時刻で切ると素通りする。内容が既出かどうかは別に見る必要がある。

**「対応済み」として落とすときだけは、現在のコードを見て確かめる。** 同じ指摘が再投稿される理由は「もう直っているのにボットが古い状態を見ている」だけでなく、「**前回の修正が不十分で、実は直っていない**」こともある。内容の一致だけで落とすと、後者を「対応済み」と返して閉じることになる。テストが緑でも直っていないことがあるのは6章のとおりで、「もう直したはず」は根拠にならない。見送ると決めたものや起票したものの再投稿は、直っていなくて当然なのでコードを見る必要はない。

### 往復の上限

**修正 push 1回 = 1往復。上限3往復。**

- CIの失敗は往復に数えない。グリーンになるまで何度でも直す
- POのコメントは往復に数えない。上限に達したあとでも必ず対応する
- 上限に数えるのは claude-review ボットの指摘への対応だけ

往復回数は、PRへ投稿するコメント内のマーカーで管理する。

```
<!-- review-round:2 -->
レビュー対応 2/3 回目。
```

`/card-review` は開始時に `gh pr view <PR番号> --comments` からこのマーカーの最大値を読み、現在の往復数を判定する。セッションをまたいでも状態が復元できるようにするため。

**マーカーを付けるのは claude-review の指摘に対応した回だけ。** CIの失敗を直しただけの回や、POの指摘に対応しただけの回には付けない(コメントは投稿するが番号を進めない)。上限に数えない対象でマーカーを進めてしまうと、実際には claude-review に3回対応していないのに上限到達と判定され、残りの指摘が誤ってバックログへ切り出される。

### 3往復に達したあとの扱い

残っている指摘を次の基準で振り分ける。

**上限を無視して修正しきるもの(重大)**

- CIが失敗している
- セキュリティ — `firestore.rules` / `storage.rules` の穴、認証・2FAのバイパス、他ユーザーの資産データが読める、秘密情報の漏洩
- データ破壊・損失 — Firestoreの意図しない上書き/削除、CSV取込の部分反映、金額計算の誤り
- 画面が機能しない — カードの主要操作が動かない、遷移しない、クラッシュする、要件を満たしていない

**新規カードとして起票するもの**

上記以外(リファクタ提案、命名、テストの追加、UIの微調整、将来の拡張性の指摘など)。

**ただし誤検知は起票しない。** 直すべきものが無いのにカードだけが残るため、PRコメントで根拠を示して返すだけにする(前掲「重大でない指摘は、直す前にPOへ確認する」)。上限に達したあとに初めて誤検知と判定したものも同じで、確認は挟まない。

つまりここでの振り分けは**3つ**になる。

| 指摘 | 扱い |
|---|---|
| 重大 | 上限を無視して修正しきる |
| 妥当だが重大でない | バックログの末尾へ起票する |
| 誤検知 | 起票しない。PRコメントで根拠を示して返す |

### 起票する新規カード

- **投入先**: バックログの末尾
- **ラベル**: 「詳細設計・実装」「テスト実装」(元カードに合わせる)
- **カード名**: `[<元の画面ID>-<枝番>] <対応内容>` — 例 `[A5-2] 2FA検証セッション期限切れ時に入力を無効化する`
- **本文テンプレート**:

```markdown
(指摘の内容と、なぜ直すべきかを自分の言葉で要約する)

対応: (具体的にどう直すか)

該当: (ファイルパス)

出典: PR #<番号> のレビューコメント <PRのURL>
```

起票したら、元のPRにコメントで「この指摘は別カード <カードURL> に切り出した」と残す。指摘が黙って消えたように見えないようにするため。

## 8. Claudeがやらないこと

- **マージしない**。`gh pr merge` も、`gh api` で `.../pulls/<番号>/merge` を叩くのも同じ。マージはPOの判断
- **force push しない**
- **`develop` / `main` へ直接pushしない**
- **要件定義書とコードの食い違いを無断でどちらかに寄せない**。どちらが正かをユーザーに確認する(`screen-spec-drift-check` と同じ方針)
- **`docs/.env` を読まない・出力しない**

### 設定による裏付け

上のうち機械的に判定できるものには [.claude/settings.json](../.claude/settings.json) で歯止めをかけてある。文書のルールだけに頼らないため。**ただしすべてを塞げているわけではない。**

| 対象 | 判定 |
|---|---|
| `firebase deploy` | 拒否 |
| 再帰的な強制削除(`rm -rf` 系) | 拒否 |
| マージ(`gh pr merge`、`gh api` の `.../merge`、`gh api` の書き込み) | 拒否 |
| `docs/.env`(`.env.example` を除く) | 拒否 |
| force push | 拒否 |
| `git reset --hard` / `git clean -f` 系 | **確認**(作業中の変更を消すため) |

**歯止めは「うっかり実行」を防ぐためのもので、回避しようとする相手を止める仕組みではない。** 既知の抜け道もある(クォート分割・変数展開、`git` のエイリアス等)。この仕組みがあることを理由に、破壊的な操作を注意せず実行してよいことにはならない。最終的な歯止めはこの8章のルールそのもの。

判定のしかた・それぞれの穴・claude-review ジョブでだけ無効にしている理由・回帰テストは [command-guards.md](./command-guards.md) にある。**歯止めを変えるときはそちらを読む**(日々のフローを回すのに読む必要はない)。

禁止対象の語を**引数として含むだけ**のコマンドも拒否されることには、フローの側で当たる。`merge` や `--force` や秘密ファイルのパスに言及する本文は、`gh pr comment --body-file` / `git commit -F` のようにファイル渡しにする。

## 9. 前提と制約

- CI4ジョブ(`wip-check` / `hooks` / `frontend` / `backend`)は `develop`・`main` の必須ステータスチェックで、赤ければマージボタンが押せない。リポジトリを公開するまでは有効にできず「慣例として必須」に留めていたもので、設定内容は [ci-cd-setup.md](./ci-cd-setup.md) 6章にある
- **fork からのPRでは `frontend` が必ず失敗する。** Secretsが渡らないためで、退行ではない
- **fork からのPRでは claude-review は走らずスキップされる。** 同じくSecretsが渡らないが、失敗させても得るものが無いのでジョブの`if`で除いてある。レビューしたい場合はオーナーが `workflow_dispatch` でPR番号を指定して実行する([ci-cd-setup.md](./ci-cd-setup.md) 3章)
- claude-review は**デフォルトブランチ(`develop`)上**のワークフローファイルと一致するときだけ実際に動く。編集しても `develop` に載るまで効かないので、レビューコメントを待つ側は「ボットが動いていない」ケースを空振りせずに判定すること(`gh run list --workflow claude-review.yml --branch <ブランチ>` で実行有無を確認する)
- claude-review は必須チェックではない。コメントを投稿するだけでマージをブロックしない
- **claude-review が自動で走るのは `develop` 宛てのPRだけ。** `develop` → `main` のリリースPRは対象外で、チェック自体が現れない。同じ差分は `develop` へ入る時点でレビュー済みで、2度目に新しい情報が出ないため(トリガーの `branches` で絞ってある)。`main` 宛てのPRをどうしてもレビューしたいときは `workflow_dispatch` で個別に実行する

### デフォルトブランチは `develop`

`main` ではない。**Dependabot はセキュリティ更新のPRをデフォルトブランチに向けて出し、その向き先を変える設定が無いため**である。`dependabot.yml` の `target-branch` はバージョン更新のための設定で、[GitHubのドキュメント](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/configuring-dependabot-security-updates)は「セキュリティ更新にこの設定を使わせたいなら `target-branch` を指定してはならない」としている。指定するとその設定ブロックがセキュリティ更新に適用されなくなるだけで、PRは結局デフォルトブランチに向く。

`main` をデフォルトのままにすると、Dependabot のPRをマージした瞬間に `develop` を通さず本番(`fire-fire-prod`)へデプロイされる。CIは走るので壊れたものは入らないが、STGでの確認を飛ばすことになる。

この変更には副次的な効果がある。

- `gh pr create` とWeb UIの既定のベースが `develop` になる。feature ブランチのPRが欲しいベースそのものなので、`--base` の付け忘れで `main` に向く事故が消える
- 逆に **`develop` → `main` のリリースPRは `--base main` の明示が要る**。本番向けのPRを明示的に作る形になるのは望ましい
- claude-review の検証先もデフォルトブランチなので、`claude-review.yml` の変更が1段早く効くようになった(上の項目を参照)

## 10. リリース(`develop` → `main`)

`develop` に溜まった差分を `main` へ入れて本番(`fire-fire-prod`)へ出す工程。手順は [`/release`](../.claude/skills/release/SKILL.md) が担う。

**章の位置について。** 流れとしては7章のあとに来るが、8章・9章の番号を動かすと `.claude/settings.json` のフックが拒否理由で指している「8章」がずれる。歯止めの設定を文言のためだけに触るのは割に合わないので、末尾に置いてある。

### この工程が他と違うところ

| | feature → `develop` | `develop` → `main` |
|---|---|---|
| CI(4ジョブ) | 走る | 走る |
| claude-review | 走る | **走らない**(9章。同じ差分をレビュー済みのため) |
| マージ後に起きること | `fire-fire-dev`(STG)へデプロイ | **`fire-fire-prod`(本番)へデプロイ** |
| 戻し方 | `develop` を直すPRを出す | **自動ロールバックは無い**([ci-cd-setup.md](./ci-cd-setup.md) 15章) |

`main` への push が [deploy.yml](../.github/workflows/deploy.yml) を起動し、Functions / Firestore / Storage のデプロイと App Hosting のロールアウトが走る。GitHub Environment `production` に承認ルールは設定していないので、**マージした時点でデプロイが始まる**。押し戻す仕組みは無い。

### 単位

**都度出す。ためない。** `develop` に未リリースの差分があれば、そのつどリリースしてよい。差分が小さいほど、本番で問題が出たときにどのカードが原因かの切り分けが早い。

### 手順の要点

1. **STGに出ているか確かめる。** CIはPRにしか走らないので、`develop` が「緑」であることは `develop` への push で走った `deploy.yml` の成功で確かめる。**その成功が `develop` の先端に対するものか**(`headSha` の一致)まで見る。失敗している/古いなら、STGで動いていないものを本番へ入れることになる
2. **未リリースの差分を出す。** `git log --oneline origin/main..origin/develop` で、前回のリリース以降に入ったものを一覧する。1件も無ければリリースするものが無い
3. **`--base main` を明示してPRを作る。** デフォルトブランチが `develop` なので、付け忘れると `develop` 宛てのPRになる(9章)
4. タイトルは `リリース YYYY-MM-DD`。同じ日に2本目を出すときは `リリース YYYY-MM-DD-2` のように連番を足す
5. 本文には**含まれるカード**と、**STGで確認した範囲 / していない範囲**を書く。claude-review が走らない以上、ここが唯一の申し送りになる
6. **マージはPO。** feature のPRと同じ。ただしリリースPRの head は `develop` **ブランチそのもの**なので、待っている間に `develop` へ別のPRが入ると**差分だけが黙って増える**。本文の「含まれるカード」が実態に追いつかなくなるため、2本目を作るのではなく本文を直す
7. **マージしたら `deploy.yml` の結果を見る。** 失敗は GitHub の通知でしか気づけない。デプロイが途中で落ちると、Functions だけ新しくフロントエンドが古い、のような中途半端な状態が本番に残りうる

### リリースブランチを使う場合(例外)

**既定は head が `develop` そのものの直PRである。** それでは困る回だけ、`develop` から切ったリリースブランチを head にする。どちらにするかはPOが決める。

**切る理由になるもの**

- **差分が大きく、PRが開いている間 `develop` を止めたくない。** 直PRの head は `develop` なので、開いている間に入ったマージがそのPRの中身に黙って混ざる(手順の要点6)。ブランチを切れば、出す内容はその時点で固定される

**理由はこれだけである。** 「`main` の『基底が古い』を解くため」は理由にしない — その状態は `main` でも実害が無いことを確認済みで、無くす対象自体が無い(次項)。

**手順**(直PRとの差分だけ)

1. **STGに出ている先端から切る。** 手順の要点1の確認を先に済ませ、`deploy.yml` が成功した `headSha` と一致する `origin/develop` から切る

   ```bash
   git fetch origin
   git switch -c release/YYYY-MM-DD origin/develop
   git push -u origin release/YYYY-MM-DD
   ```

2. ブランチ名は `release/YYYY-MM-DD`。カードの作業ではないので `feature/fire-fire-<カードID>` は使わない(5章)
3. `gh pr create --base main --head release/YYYY-MM-DD`。タイトルと本文の規約は直PRと同じ
4. **デプロイの成功を確かめたら、POがブランチを削除する。** リポジトリの `delete_branch_on_merge` は無効なので、マージしただけでは消えない。`/release` は削除を促すところまでを受け持つ(B節)

**このブランチに新しい変更を積まない。例外は無い。** 直すものが見つかったら `develop` で直してSTGで確認し、**リリースブランチを切り直す。** `deploy.yml` は `develop` と `main` にしか反応しないので、ここに積んだものはSTGで一度も動かないまま本番へ入る。

**デプロイが失敗したときも同じ。** 落ちたリリースブランチを直して出し直すのではなく、`develop` で直してSTGに出てから**別の名前で切り直す**(同じ日なら `release/YYYY-MM-DD-2`)。失敗したブランチは、出した内容を追う手がかりとして次のリリースが成功するまで残し、そのあとPOが消す。

### `main` の「基底が古い」は実害が無い

**`main` でも「Require branches to be up to date before merging」を有効にする**([ci-cd-setup.md](./ci-cd-setup.md) 6章)。`develop` と同じ設定にする。

以前はここで「`main` では無効にする」と決めていた。根拠は「リリースPRをマージすると、そのマージコミットは `main` にだけ残り `develop` へは戻さないため、`develop` が `main` の先端を含まない状態がリリースのたびに再発し(この判断をした 2026-08-16 時点で17件)、有効のままだと毎回それが『基底が古い』でリリースPRのマージボタンを塞ぐはずだ」という見込みだった。**実測ではそうならなかった。** リリースPR #184(`main...release/2026-08-16` は `ahead_by 129 / behind_by 17`)は `mergeStateStatus=CLEAN` のままブロックされずにマージできている。

**理由は「基底が古い」の判定条件そのものにある。** ブロックが働くのは「PRを作ったあとに base が進み、その組み合わせでは壊れる」場合だけで、`behind_by` の絶対値では決まらない。`main` が進むのはリリースPRのマージのときだけで、リリースPRを2本同時に開かない規定(手順の要点6、`/release` の判定表)があるため、あるリリースPRが開いている間に `main` が進むことはない。**base が動かない以上、`behind_by` がどれだけ大きくてもブロックは働かない。** 17件という数字は「マージ内容が食い違っている」ことではなく、`develop → main` のマージPRが残す `Merge pull request #N from develop` というコミットオブジェクトを、後から切り直した `develop` 由来のブランチが(内容は同じでも)持っていない、という構造的な差分で、リリースのたびに1件ずつ増え続ける。**CI4ジョブの必須は外さない。**

**CIとレビューの扱いは直PRと同じ。** `ci.yml` は `main` 宛てのPRで走り(4ジョブとも必須チェック)、`claude-review` は `develop` 宛てだけなので走らない(9章)。`deploy.yml` は `release/*` への push には反応しない。
