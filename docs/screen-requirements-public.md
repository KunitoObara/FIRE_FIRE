# 画面要件定義書:公開画面(A0・A9・A10)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.0節の公開画面(A0・A9・A10)について、画面ごとの要件を詳細化したものである。公開面を持つこと自体の方針は [FIRE-FIRE 要件定義書](./fire-asset-management-requirements.md) 4.15節を参照。

**実装状況: A9・A10は実装済み、A0は未実装。** A9(`/terms`)・A10(`/privacy`)と、3画面が共有する公開用シェル(ヘッダー・フッター・導線)は [screen-spec-drift-check](../.claude/skills/screen-spec-drift-check/SKILL.md) の対象に入っている。A0はルートもコンポーネントもまだ無いため対象外である(実装が入った時点で対象に入る)。

**現在の `/` は開発環境構築の動作確認用のプレースホルダー**(`src/frontend/src/app/(setup-check)/page.tsx`)が応答している。A0の実装でこれを置き換え、`(setup-check)` は `spa-check` ごと削除する(3章)。**そのため、A9・A10のヘッダーのロゴが指す `/` は、A0が入るまでこのプレースホルダーに着地する。**

**フェーズの段には乗らない。** Phase 1〜4が「ダッシュボードに何を載せるか」、Phase 5〜7が「外部への依存の重さ」で分かれているのに対し、この3画面はどちらの軸にも乗らない([要件定義書 7.3](./fire-asset-management-requirements.md#73-サービスの公開面をフェーズ順に乗せない理由))。

## 2. 3画面に共通する扱い

### ログインを要求しない

**この3画面は、未ログインのまま完結する唯一の画面群である。**

A1〜A8も未ログインで到達するが、あちらは「アカウントを作る/ログインする」という認証フローの途中の画面で、行き着く先はB1である。A0・A9・A10はフローに属さない — 訪問者がサービスを知るため、また規約を読むためだけの画面で、そのまま帰ってよい。

- **`AppAccessGuard` の対象外**とする。メール未確認・2FA未登録の状態でも、そのまま表示する(A2・A3へ差し戻さない)
- **Firestoreを一切読まない。** したがって「権限なし」「未ログイン」といった取得失敗の分岐を持たない。他の画面要件が持つ「取得に失敗したときの表示」([不動産管理系画面](./screen-requirements-real-estate.md) 2章)に相当する規定は、この3画面には無い
- 静的に生成できる内容だけで構成する。ログイン状態によって変わるのは次項の導線だけで、それはクライアント側で差し替える

### ログイン中でもリダイレクトしない

**ログイン済みのユーザーが `/` を開いてもB1へ飛ばさない。** 変えるのは**導線だけ**で、「ログイン」「サインアップ」の2つを「ダッシュボードへ」1つに差し替える。

B1へ自動で飛ばすと、ログイン中はA0を見返す手段が無くなる。規約の改定を確認したい、フッターから規約へ入りたい、といった用がログアウトしないと果たせなくなるため。一般的なWEBサービスのトップページと同じ挙動でもある。

- **差し替えるのはヘッダーだけでなく、ページ内のCTA(ヒーロー・下部)も同じである。** ヘッダーだけを直すと、ログイン中のユーザーに画面の真ん中で「サインアップ」を勧め続けることになる。3箇所を同じコンポーネントで作り、置き場所ごとに出し分けの規則を書き分けない
- **判定が確定するまで、どちらの導線も出さない。** 未ログイン用のボタンを描いてから「ダッシュボードへ」に差し替わると、ログイン中のユーザーには一瞬「ログイン」ボタンが見える
- **ページ本体は認証状態の確定を待たずに描画する。** 待たせると、未ログインの訪問者にとっては何も要らない待ち時間になる。導線の部分だけが後から埋まる形にする。**そのため、導線の領域は確定前後で高さが変わらないようにする**(埋まった瞬間に本文が跳ねると、読んでいる最中の位置がずれる)
- A9・A10のヘッダーも同じ扱いにする(この2画面はページ内にCTAを持たない)

### 検索エンジンには出さない(ベータ期間中)

**`noindex` を設定する。** ベータ版・単一ユーザー運用の間に検索流入を集めない。

- **A0だけでなくサイト全体に掛ける。** A0にだけ掛けると、A1 サインアップ画面などが単独でインデックスされうる。トップページが検索に出ないのに登録画面だけが出る状態は、掛けないより悪い
- **外すのは「正式公開」の判断とセットで行う。** 外し忘れを防ぐため、外す条件と手順は3章のオープン課題に残す。A0の実装カードのスコープには入れない
- `noindex` はクロールの禁止(`Disallow`)ではない。ログイン後の画面が守られているのは `firestore.rules` と認証であって、`robots` の設定ではない([要件定義書 5章](./fire-asset-management-requirements.md#5-非機能要件)のセキュリティ)。ここを取り違えて「`robots.txt` に書いたから安全」としない

### 公開リポジトリと同じ制約が掛かる

**A0に載せる画面イメージ・数値はすべてダミーにする。** 開発者本人の資産額が読み取れるスクリーンショットを置かない(ルートの `CLAUDE.md`)。

- 金額は `12,345,678円` のように、明らかに作り物と分かる丸めた値を使う
- 物件名・メールアドレスも他のモックと揃える(`〇〇マンション101号室` / `taro.yamada@example.com`)
- **この制約はモックだけでなく実装にも掛かる。** LPの画像は本番に配信されるため、モックで守って実装で破ると意味が無い

### レイアウト

**A1〜A8の中央寄せ1カラム(`auth-shell`)でも、B1〜B11のアプリシェルでもない、公開用の独自シェルを使う**([DESIGN.md](../DESIGN.md) 5章)。

- 上部にヘッダー(サービス名 + 導線)、下部にフッター、その間に横幅を制限したセクションを縦に積む
- サイドバーは持たない。ログイン後の画面ではないため
- PC・タブレット・モバイルに対応する。モバイル幅ではヘッダーの導線が2つ並ぶだけなので、**ハンバーガーメニューは設けない**(畳む対象がボタン2つしか無い)

## A0. サービストップページ

- **画面目的**: 未ログインの訪問者にFIRE-FIREが何をするサービスかを伝え、ログイン・サインアップへ送り出す

| 区分 | 項目 |
|---|---|
| 表示項目 | サービス名・キャッチコピー、ベータ版であることの表示、できること(機能紹介)、使い方の手順、ベータ版についての注意、コピーライト、利用規約・プライバシーポリシーへのリンク |
| 入力項目 | 無し |
| 主な操作 | 「ログイン」「サインアップ」(ログイン中は「ダッシュボードへ」)、本文中のCTAボタン、フッターのリンク |
| 遷移条件 | 下記「遷移条件」のとおり |

**入力項目を持たない。** 問い合わせフォーム・メール登録フォームの類は置かない。単一ユーザー運用の間、受け口を作っても読む運用が無い(3章)。

### セクション構成

上から次の順に積む。

| # | セクション | 置く内容 |
|---|---|---|
| 1 | ヘッダー(固定) | サービス名(ロゴ)、「ログイン」「サインアップ」 |
| 2 | ヒーロー | ベータ版バッジ、キャッチコピー、1〜2文の説明、CTA(「サインアップ」「ログイン」)、画面イメージ |
| 3 | できること | 主要機能を4つ、アイコン + 見出し + 1〜2文で並べる |
| 4 | 使い方 | 導入から利用開始までを3ステップで示す |
| 5 | ベータ版について | ベータ版の位置付けと、利用者が承知しておくべきこと |
| 6 | 下部CTA | ヒーローと同じ導線をもう一度置く |
| 7 | フッター | コピーライト、利用規約(A9)・プライバシーポリシー(A10)へのリンク |

**「できること」に並べる4つは、実装済みの機能から採る。**

| 見出し | 対応する機能 |
|---|---|
| 資産の推移を1枚で見る | 資産推移グラフ([要件定義書 4.4](./fire-asset-management-requirements.md)) |
| 分類の切り口を自分で決める | 資産分類マスタ(4.3)。総資産・純金融資産・投資性資産などを自分で定義できる点 |
| 不動産と負債まで含めて数える | 不動産の利ざや(4.5)・負債(4.8) |
| FIRE到達予測日が出る | FIRE目標・達成度・到達予測日(4.6) |

- **未実装の機能を載せない。** Phase 5〜7の機能(サブスク・証券口座・マイナポータル連携)は書かない。「近日公開」の予告も置かない — 出さないかもしれないものを載せると、ベータ版であることの説明と衝突する
- **CSV取込を4つの中に入れない。** 取込は手段であって価値ではなく、それは「使い方」の1ステップ目で説明する

**「使い方」の3ステップ**

1. マネーフォワードからCSVをエクスポートする
2. FIRE-FIREに取り込む(B2)
3. ダッシュボードで資産推移・FIRE達成度を見る(B1)

**1ステップ目でマネーフォワードを前提として明記する。** このアプリは他サービスがエクスポートしたものを再構成する道具であって、家計簿そのものではない([要件定義書 1.1](./fire-asset-management-requirements.md))。それを伏せて登録させると、登録した人が最初に詰まる。

### ベータ版であることの明記

**2箇所に置く。** ヒーローのバッジと、専用のセクション(5)である。バッジだけだと読み飛ばされ、セクションだけだと画面を下までスクロールした人にしか届かない。

セクション(5)に書くこと:

- 開発中であり、**仕様・画面が予告なく変わりうる**こと
- **データが失われる可能性がある**こと。取り込んだ元のCSVは各自で保管してほしいこと(アプリは元のCSVファイルを保存しない — [要件定義書 4.2](./fire-asset-management-requirements.md))
- **現在は招待制**で、登録を受け付けられる人数が限られていること
- **投資助言を行うものではない**こと。表示する数値は利用者自身が入力・取り込んだデータに基づく計算結果であること

**サインアップボタンは置く**(カードの要求)。**そのうえで「現在は招待制」を添える。** ボタンを消すと、招待された人が入口を探すことになる。

> **登録そのものを技術的に遮断する仕組みは、この画面のスコープに含まない。** A0が置くのは表示だけで、実際の遮断は認証基盤側で行う — 承認済みのメールアドレスだけがアカウントを作成できるようにする(`beforeUserCreated` による事前承認制。[auth-login-requirements.md](./auth-login-requirements.md) 3.10)。**[X5](https://trello.com/c/5k33KGEY) で実装する**ため、A0の実装時点では遮断が入っていない可能性がある。どちらが先でも成立するが、**A0の公開が先になる場合は、その間だけ誰でも登録できる状態になる**点は承知して出す(コンソール設定で一時的に塞ぐ手もある。同3.10)。

### 遷移条件

- 「サインアップ」押下 → **A1 サインアップ画面**
- 「ログイン」押下 → **A4 ログイン画面**
- 「ダッシュボードへ」押下(ログイン中のみ表示)→ **B1 ダッシュボード画面**
- フッターの「利用規約」→ **A9 利用規約画面**、「プライバシーポリシー」→ **A10 プライバシーポリシー画面**
- ログイン中に開いても**リダイレクトしない**(2章)

### 画面イメージの扱い

ヒーローに置く画面イメージは、**B1 ダッシュボードのダミーデータ版**とする。

- 実データのスクリーンショットを置かない(2章)
- 画像ファイルを貼るのではなく、**HTML/SVGで描いた簡略版**を置いてもよい。画面が変わったときに画像だけが古くなるのを避けられる。モック(`a0-top.html`)はこの形で描いてある
- どちらで実装するかは着手時に決めてよい(要件はどちらも満たす)

**簡略版にする場合も、B1に実在する要素だけで組む。** 縮尺に入らない要素を落とすのはよいが、**B1に無い形を新しく描かない**(数値カードを横に3枚並べる、棒グラフにする、等)。登録した人が最初に見る画面と食い違い、LPが約束したものと違うところに着地させることになる。

| 残すもの | 落としてよいもの |
|---|---|
| サイドバー、分類軸セレクタ、表示期間の切替 | 収支サマリ、負債サマリ、ヘッダーのユーザーメニュー |
| 資産推移(**資産種別の積み上げエリア**と、0の線より下に積む負債の帯)、凡例、横軸の年月 | ツールチップ、負債反映の切替、年月選択のポップオーバー |
| 分類別内訳の円グラフと構成比、差引後の額 | 凡例のリスクレベル(○△◇) |
| FIRE達成度ゲージ、目標資産額・現在資産額・**対象分類名の併記**・到達予測日 | 「目標を設定する」導線 |

- **色は資産分類スロット(`--chart-*`)と負債のハッチングをB1と同じ割り当てで使う**([DESIGN.md](../DESIGN.md) 3章)。LP用に色を作らない
- **数字は1組で辻褄を合わせる。** 資産種別の合計・負債・差引後・構成比・達成率が互いに矛盾しない値にする。ダミーだからと個別に置くと、読んだ人が計算の仕方を誤解する
- **ゲージの対象分類は、分類軸セレクタと同じものに揃える。** B1では両者が別の設定で、[本物のモック](../src/frontend/docs/html_mock/b1-dashboard.html)は**違う軸を指している状態**を示している(セレクタが純金融資産、ゲージが投資性資産)。LPでそれを再現しない — 訪問者に「2つの軸は別の設定」という区別を読ませる前提を置けず、単に数字が食い違って見えるため。揃えたぶん、**現在資産額は円グラフの差引後と同じ額**になり、達成率もその額から出る
  - **ただし対象分類名の併記は落とさない**([screen-requirements-dashboard.md](./screen-requirements-dashboard.md)「FIRE達成度の現在資産額(対象分類)」)。併記が無いと、揃えてあること自体が読み取れない

## A9. 利用規約画面

- **画面目的**: 本サービスの利用条件を掲示する

| 区分 | 項目 |
|---|---|
| 表示項目 | 見出し(利用規約)、制定日・最終改定日、規約本文(条文)、トップページへ戻る導線 |
| 入力項目 | 無し |
| 主な操作 | ヘッダー・フッターの各リンク |
| 遷移条件 | ヘッダーのロゴ → A0、その他はA0のフッターと同じ |

**条文の構成**

| 条 | 内容 |
|---|---|
| 第1条 | 適用 |
| 第2条 | 定義 |
| 第3条 | アカウント登録・アカウントの管理(2FAが必須であること) |
| 第4条 | ベータ版であることの確認(無保証、仕様変更、データ消失の可能性) |
| 第5条 | 本サービスは投資助言ではないこと |
| 第6条 | 禁止事項 |
| 第7条 | 本サービスの提供の停止等 |
| 第8条 | 免責事項 |
| 第9条 | サービス内容の変更・終了 |
| 第10条 | 本規約の変更 |
| 第11条 | 準拠法・裁判管轄 |

- **第5条を独立させる。** 資産額・FIRE到達予測日を数字で出すアプリであり、免責事項の一項目に混ぜると読み落とされる。予測はユーザー自身が入力した想定利回り(B9)と積立額(B8)から計算した結果であって、推奨ではない
- **第4条にデータ消失を明記する。** ベータ版であることの表示(A0)と規約側の記述を揃える。片方だけに書くと、どちらが本当かが読めない

> **条文の文面そのものは雛形であり、公開前に本人が内容を確認する。** このドキュメントが決めるのは「何をどの順で書くか」までである。モック(`a9-terms.html`)に置いてある本文は、構成を確かめるためのドラフトとして扱う。

## A10. プライバシーポリシー画面

- **画面目的**: 取得する情報とその扱いを掲示する

| 区分 | 項目 |
|---|---|
| 表示項目 | 見出し(プライバシーポリシー)、制定日・最終改定日、本文、トップページへ戻る導線 |
| 入力項目 | 無し |
| 主な操作 | ヘッダー・フッターの各リンク |
| 遷移条件 | A9と同じ |

**本文の構成と、実装から来る事実**

| 項 | 内容 | 実装上の根拠 |
|---|---|---|
| 取得する情報 | メールアドレス、Googleアカウントの情報(Googleログイン時)、ログイン日時等、利用者が取り込んだ資産・入出金・不動産・負債のデータ | Firebase Authentication / `users/{uid}` 配下のFirestore |
| **取得しない情報** | **取り込んだCSVファイルそのものを保存しない**(ブラウザ内で解析し、数値だけを保存する) | [要件定義書 4.2](./fire-asset-management-requirements.md)。Firebase Storageに生CSVを置かない |
| 利用目的 | 本サービスの提供、ログイン通知の送信、不正利用の防止 | ログイン通知は [auth-login-requirements.md](./auth-login-requirements.md) 3章 |
| 外部サービスへの提供・委託 | Google(Firebase / Identity Platform)、Resend(ログイン通知メールの送信) | `src/backend/src/login-notification` |
| 保管と削除 | 保管場所、利用者からの削除の求めへの対応。**問い合わせ先が準備中の間は、画面の操作で消せる範囲を併記する**(連絡先の無い宛先へ案内しない) | 各画面の削除操作 |
| Cookie等の利用 | ログイン状態の保持に用いること。広告目的の利用が無いこと | — |
| 安全管理 | 認証・2要素認証を必須とし、データベース側のアクセス制御で本人以外が参照できないようにしていること | `firestore.rules` の `canAccessOwnData()`(TOTP必須)。[auth-login-requirements.md](./auth-login-requirements.md) 3.3 |
| 問い合わせ先 | **準備中である旨のみを書く。** 受信できるアドレスがまだ無いため、アドレスは載せない | **未確定**(3章)。用意は[X4](https://trello.com/c/8wpkp9Gt)、代わりの受け口は[X6](https://trello.com/c/fYjMjcBS) |
| 改定 | 改定の手順 | — |

- **「取得しない情報」を明示する項を置く。** 生のCSVを保存しない設計は、扱う情報が資産データであるだけに、利用者にとって最も知りたい部分である。書かなければ伝わらない
- **外部サービス名を具体的に書く。** 「委託先」とだけ書いて社名を伏せると、どこにデータが渡るかが読めない
- 開発者本人のメールアドレスは書かない(公開リポジトリのため。2章)。**問い合わせ先には取得済みドメインのアドレスを用意する**(3章)。**用意ができるまではアドレスを載せず、準備中である旨だけを書く** — 届かないアドレスを載せると、送った側は届いたつもりで返信を待つことになる

## 3. 今後の検討事項

- **`noindex` を外す条件と手順。** ベータ版から正式公開へ移す判断とセットで決める(2章)。外し忘れると、正式公開後も検索に出ないままになる([X4](https://trello.com/c/8wpkp9Gt))
- **問い合わせ先メールアドレスの用意。** A10に載せる連絡先で、取得済みドメイン(`fire-fire.live`)のアドレスを想定している。ドメインの接続作業と合わせて行う([X4](https://trello.com/c/8wpkp9Gt))。**アドレスの代わりに問い合わせフォームを置く案も出ている**([X6](https://trello.com/c/fYjMjcBS))が、現行のA0は入力項目を持たない方針(A0)なので、フォームを採るならその記述を先に改める
- ~~**登録を実際に制限するか。**~~ **決定済み** — Blocking Functions(`beforeUserCreated`)と許可リストによる事前承認制にする。仕様は [auth-login-requirements.md](./auth-login-requirements.md) 3.10、実装は [X5](https://trello.com/c/5k33KGEY)。A0のスコープには引き続き含めない(画面の表示と、認証基盤側の遮断は別物のため)
- **規約改定時の同意の取り直し。** A1の同意チェックは同意した規約の版を記録していない([screen-requirements-auth.md](./screen-requirements-auth.md) A1)。改定時に再同意を求めるなら、版の記録から要る
- ~~**`(setup-check)/spa-check` の扱い。**~~ **決定済み** — A0の実装で `(setup-check)` を `spa-check` ごと削除する。クライアント遷移の確認は、A0 ⇄ A9・A10 のヘッダー・フッターの導線が実物のSPA遷移になるため役目を果たせている。到達手段の無いルートを本番に配信し続けない
- **ヘルプページ([X2](https://trello.com/c/tgP5d1Ue))との関係。** ヘルプを作るなら、A0のフッターからの導線が要る。A0の実装時点では未着手のため、フッターに枠だけ置くことはしない
