# 画面要件定義書:リスト管理系画面(B12〜B14)

## 1. 位置付け

本ドキュメントは [画面一覧・画面遷移図](./screen-list-and-transitions.md) 2.7節のリスト管理系画面(B12〜B14)について、画面ごとの要件を詳細化したものである。機能全体の方針は [FIRE-FIRE 要件定義書](./fire-asset-management-requirements.md) 4.9〜4.11節を参照。

**実装状況: 3画面とも未実装。** フェーズとしては [同書7章](./fire-asset-management-requirements.md) の **Phase 5** にあたる。ルートもコンポーネントもまだ無いため、[screen-spec-drift-check](../.claude/skills/screen-spec-drift-check/SKILL.md) の対象外である(実装が入った時点で対象に入る)。

## 2. 3画面に共通する扱い

### ダッシュボードには一切反映しない

**この3画面が登録するデータは、B1のどの数字にも効かない。** [B4 資産分類マスタ設定画面](./screen-requirements-dashboard.md#b4-資産分類マスタ設定画面) の集計対象の選択肢にも出さない。

B2〜B4・B5〜B7・B11がいずれも「B1へ数字を供給する画面」であるのに対し、この3画面は自分の中で完結する。理由は画面ごとに違う。

| 画面 | 反映しない理由 |
|---|---|
| B12 サブスク | 実際に払った額は入出金明細CSV(4.2)から来る。登録額を足すと同じ支出を二重に数える |
| B13 金融機関 | 残高を持たない。持てない(口座別の残高を出力するCSVが無い) |
| B14 持ち物 | 資産として計上しないことが要求そのもの(4.11) |

**この性質は画面上でも読み取れるようにする。** 3画面とも、登録した内容がダッシュボードに出ない旨を画面上部の説明文に書く。書かないと「登録したのにB1が変わらない」の答えがどこにも無い(B5が物件について同じ説明を置いているのと同じ扱い)。

### 分類・種別の選択肢は固定でよい

B13の種別・B14の分類は、**コード側に固定の選択肢として持つ**。ユーザーが追加・編集できるマスタデータにはしない。

**[要件定義書 4.3](./fire-asset-management-requirements.md) の「マスタデータとして追加・編集可能にする」は資産分類軸に対する要件であって、あらゆる分類に及ぶものではない。** 分類軸がマスタなのは、それがダッシュボードの集計単位そのものであり、集計の切り口はユーザーごとに違うためである。B13の種別・B14の分類は表示の並び替えと絞り込みにしか使わず、集計には効かない([category-master-extensibility-check](../.claude/skills/category-master-extensibility-check/SKILL.md) がこの2つを指摘した場合、本項が根拠になる)。

- どちらの選択肢にも**「その他」を必ず置く。** 当てはまらないものが出たときに登録できなくなるのを防ぐ
- 選択肢を増やす必要が出たら、コードを変えて増やす。運用中に増える性質のものではない

### 追加・削除と保存(B12・B14)

**B11 負債入力画面と同じ形にする。** 1画面の中でフォームを増減させ、「保存」で一括保存する。

- 「追加」は画面上のフォームを増やすだけ、「削除」も減らすだけで、どちらも保存するまで確定しない。したがって保存前の削除は取り消せる(画面を離れれば元に戻る)。削除ボタン自体には確認を挟まない
- **保存時に、既存の登録を削除する場合のみ確認ダイアログを挟む**([DESIGN.md](../DESIGN.md) 6章)。削除する件数と、どれが消えるのかを名前と金額の組で示す(名前の重複を許すため、名前だけでは同名の2件を区別できない — B11と同じ理由)
  - **ダイアログにダッシュボードへの波及は書かない。** B11・B6の削除ダイアログはそれを書くが、この2画面は前掲のとおりダッシュボードに効かないため、書くと効いているように読める
- 保存はまとめて行い、一部だけ書き込まれた状態を残さない。途中で失敗した場合はその旨を表示し、画面の入力値は保持する
- 保存に成功したら画面に留まり、完了メッセージを表示する(B11と同じ)

**B13だけは形が違う。** 行がCSV取込によっても増えるため、1画面まとめて保存する形にすると、保存の直前に取込で増えた行を黙って消しうる(B11がPR #83で踏んだ「別のタブが追加した負債が保存で消える」と同じ事故)。B13は**行ごとに保存する**(B13「行ごとに保存する」)。

### 件数と文字数の上限

| 対象 | 上限 | 根拠 |
|---|---|---|
| B12 サブスクの登録件数 | 100件 | 一括保存の書き込み件数の歯止め。Firestoreのバッチ上限(500)に対して十分に余裕を取る |
| B14 持ち物の登録件数 | 100件 | 同上 |
| B13 金融機関の登録件数 | 100件 | 行ごとの保存なのでバッチの制約は掛からないが、CSV取込で自動的に増える唯一のリストなので歯止めを置く。列がずれたCSVを取り込んだときに口座名でない値が大量に登録されるのを止める |
| 名前(サービス名・金融機関名・品名) | 60文字 | B7の物件名・B11の項目名と揃える |
| メモ | 200文字 | 一覧の行に収める前提の欄。B3が持つ1,000文字(マネーフォワード側の自由記述をそのまま受ける欄)とは用途が違う |

**上限値は定数と `firestore.rules` の両方に置き、値を揃える**(物件名・分類軸名・負債の項目名と同じ扱い)。件数の上限はルールでは検査できない(ルールはコレクションの件数を数えられない)ため、[要件定義書 8.1](./fire-asset-management-requirements.md#81-クライアントだけが担保している制約) の表に足す。

### 取得・保存に失敗したとき / 読み込み中の表示

[不動産管理系画面](./screen-requirements-real-estate.md) 2章と同じ扱いにする。失敗の理由(未ログイン / Firebaseの設定が読めない / 権限なし / 不明)に応じた文言を表示して遷移せず、読んでいる間はスケルトンを出す。

**解釈できない1件が混じっていた場合は、その1件だけを一覧から落として残りを表示する**(B5・B2の取込履歴と同じ)。1件の不整合で一覧全体を空にしない。

### データの持ち方

| 画面 | コレクション |
|---|---|
| B12 | `users/{uid}/subscriptions/{subscriptionId}` |
| B13 | `users/{uid}/financialInstitutions/{institutionId}` |
| B14 | `users/{uid}/belongings/{belongingId}` |

いずれも1件1ドキュメントで、`firestore.rules` に許可を追加する(既定拒否のままでは読み書きできない)。**履歴は持たない** — B11の残債・B7の時価と違い、過去の値を資産推移グラフへ積む用途が無いため。

## B12. サブスク一覧画面

- **画面目的**: 定期課金しているサービスを手動で登録し、固定費としての大きさを月額換算・年額換算で把握する

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録済みサブスクの入力フォーム(1件=1フォーム)、月額換算の合計、年額換算の合計、登録件数 |
| 入力項目 | サービス名、料金、請求周期(月次/年次)、支払い元、契約開始年月、メモ |
| 主な操作 | 「サブスクを追加」ボタン、各フォームの「削除」ボタン、「保存」ボタン |

**入力項目の補足**

- 必須は**サービス名・料金・請求周期**の3つ。支払い元・契約開始年月・メモは任意
- **料金は請求周期に対する額をそのまま入力する。** 年払いのサービスに月額を入れさせない。年払いの実額を12で割った端数はアプリが引き受ける
- 請求周期は**月次 / 年次の2つだけ**とする。四半期・隔月の契約が出てきたら選択肢を足す(2章「分類・種別の選択肢は固定でよい」)。既定は月次
- **支払い元は [B13 金融機関一覧画面](#b13-金融機関一覧画面) に登録済みの金融機関から選ぶ**(自由入力ではない)。同じ口座名が表記違いで2つ並ぶのを防ぐため
  - **任意にする。** B13が空の状態(まだ取り込んでいない・まだ実装されていない)でもB12を使えるようにする
  - 選んだ金融機関がB13で削除された場合は、**その旨を行に出す**(「支払い元が削除されています」)。行そのものは残し、選び直せるようにする。参照が消えたことを理由に行を消さない
- 契約開始年月は `yyyy-MM`。**当月より後は不可**、下限は1900-01(B11の発生年月・B7の取得年月と同じ)
- 料金は0円以上の整数(円単位)。無料プランに切り替えた契約を0円で残せるようにするため、0を許す

**月額換算・年額換算の出し方**

- **年額換算 = 月次の料金 × 12、または年次の料金そのもの。** 内部では**年額(整数円)に正規化して**扱う
- **月額換算の合計は、年額換算の合計を12で割って出す。** 行ごとの月額換算を足し上げる形は採らない — 年払いのサービスを1件ずつ12で割って丸めてから足すと、合計が「年額合計 ÷ 12」と1円単位で食い違い、画面に2つの月額合計が存在しうる
- 行ごとにも月額換算を出すが、**円未満は切り捨て、「概算」と分かる形で添える**。合計と足し算が合わないことがあるため
- 丸めるのは**表示の直前の1箇所だけ**にする(FIRE達成率・利ざやと同じ方針)

**遷移条件**

- 保存成功 → 画面に留まり完了メッセージを表示する
- バリデーションエラー(必須未入力、料金が数値でない・負の数、契約開始年月が当月より後、文字数超過)→ インラインエラーを表示し、保存しない
- 共通ヘッダー/サイドバーから他の主要画面へ自由に遷移可能

**登録が1件も無いとき**

「登録済みのサブスクがまだありません。」と、フォームを1件追加する導線を表示する(B5の空状態と同じ扱い)。

## B13. 金融機関一覧画面

- **画面目的**: 保有している口座・金融機関を一覧で把握する。入出金明細CSVに現れた口座名から自動で登録され、手動でも追加できる

| 区分 | 項目 |
|---|---|
| 表示項目 | 金融機関の一覧(金融機関名、種別、用途メモ、由来、最後に明細で見た年月)、登録件数 |
| 入力項目 | 金融機関名、種別(銀行/証券/カード/電子マネー/その他)、用途メモ |
| 主な操作 | 「金融機関を追加」ボタン、行の編集、行の削除(手動追加のみ)、「取込済みの明細から取り込む」ボタン |

**残高は表示しない**

**この画面は「どこに口座があるか」だけに答える。** 口座ごとの残高を出す手段が無いためである — 資産残高推移CSVは資産種別ごとの列しか持たず、口座別の残高を出力しない([要件定義書 4.7](./fire-asset-management-requirements.md) がリスクを口座ごとではなく資産種別ごとに設定しているのと同じ制約)。

**手入力で残高を持たせる案は採らない。** 資産残高推移CSVの数字と食い違う二つ目の資産額が生まれ、どちらが正かを画面から判断できなくなる。

**CSV取込による登録**

[B2 CSV取込画面](./screen-requirements-dashboard.md#b2-csv取込画面) で入出金明細CSVを取り込むたびに、そのCSVに現れた `保有金融機関` の値を重複排除してこのリストへ登録する。

- **既に同じ名前で登録されている行は触らない。** 手で設定した種別・用途メモを取込のたびに上書きしない
- **名寄せ・表記ゆれの統合はしない。** CSVの口座名をそのまま持つ。費目名を正規化しないのと同じ理由([入出金明細CSV取込 要件定義書](./transaction-import-requirements.md) 6章)で、機械的に統合すると別の口座を1つに潰しうる。前後の空白だけ落とす(trim)
- **取込が失敗したときは1件も登録しない。** 取込が部分反映しない原則(同書 2.3)に揃える
- 登録の失敗は**取込そのものを失敗させない**。明細は取り込めているのに「取込に失敗しました」と出るほうが実態と合わない。B13側にその旨を出す

**取込済みの明細から取り込む**

B13より前に取り込んだ明細には、上記の自動登録が効かない。そのため、**期間を指定して取込済みの明細を読み直す操作**を画面に置く。

- 読み方は [B3 収支明細一覧画面](./screen-requirements-dashboard.md#b3-収支明細一覧画面) と同じ範囲クエリにし、同じ `TRANSACTION_SCAN_LIMIT` で打ち切る。**打ち切った場合はそのことを画面に出す**(黙って欠けると、リストに無い口座を「取引が無い」と読み違える)
- **全期間を無条件に走査する形は採らない。** 取引は際限なく増えるデータで、全件読みは[同書 8章](./transaction-import-requirements.md)の読み取りの制約に反する
- **何件追加したかを結果として出す。** 0件のときも「新しい口座はありませんでした」と出す。何も起きなかったのか失敗したのか分からない状態を作らない
- 同じ期間で何度実行しても結果は変わる必要がない(冪等)。既にある名前は追加しないため

**行ごとに保存する**

**B12・B14と違い、1画面まとめて保存する形にしない。** 行がCSV取込によっても増えるためである。まとめて保存すると、画面を開いてから保存するまでの間に取込で増えた行を、保存が黙って消しうる(B11がPR #83で踏んだ事故と同じ形)。

- 編集は行の中で行い、行ごとに確定する
- 削除も行ごとに確定し、**確認ダイアログを挟む**(保存を経由しないため、B12・B14のように「保存前なら取り消せる」状態が無い)

**削除できるのは手動追加した行だけ**

**CSV由来の行は削除できない。** 消しても次の取込で同じ名前が再び登録され、消したはずのものが戻るためである。取引が実在する以上、リストに残っているほうが実態と合う。

- CSV由来の行でも**種別・用途メモは編集できる**。編集した内容は取込で上書きされない(前掲)
- 由来(CSV由来 / 手動追加)は行に表示する。削除できる行とできない行が混在するため、できない理由が読み取れるようにする
- **金融機関名はCSV由来の行では編集できない。** 名前を変えると、次の取込で元の名前が別の行として登録され、同じ口座が2行に増える
- 解約した口座の扱いは今後の検討事項とする(後掲)

**最後に明細で見た年月**

CSV取込で登録・確認した際に、その明細の最新の取引年月を記録して表示する。使っていない口座を見分けるための情報で、**絞り込みや並び替えの既定にはしない**(取引が無いこと自体は異常ではない)。手動追加の行では空欄になる。

**遷移条件**

- 行の保存成功・削除成功 → 画面に留まり完了メッセージを表示する
- バリデーションエラー(金融機関名が空、文字数超過、同名の手動追加が既にある)→ インラインエラーを表示し、保存しない
- 共通ヘッダー/サイドバーから他の主要画面へ自由に遷移可能

**金融機関名の重複**

**B12・B14と違い、重複を許さない。** このリストは名前で突き合わせて登録するため(CSV取込・B12の支払い元の選択肢)、同名の行が2つあると、どちらに紐づくのかを決められない。

## B14. 持ち物一覧画面

- **画面目的**: 自動車・PC・スマホなど、資産として計上しない持ち物を記録し、買い替えの時期と費用を見込む

| 区分 | 項目 |
|---|---|
| 表示項目 | 登録済み持ち物の入力フォーム(1件=1フォーム)、登録件数、買い替え予定が近いものの件数 |
| 入力項目 | 品名、分類(自動車/PC・スマホ/家電/その他)、取得年月、取得価格、買い替え予定年月、メモ |
| 主な操作 | 「持ち物を追加」ボタン、各フォームの「削除」ボタン、「保存」ボタン |

**入力項目の補足**

- 必須は**品名と分類**の2つ。取得年月・取得価格・買い替え予定年月・メモは任意
- 取得年月は `yyyy-MM`。**当月より後は不可**、下限は1900-01(B11の発生年月と同じ)
- **買い替え予定年月は当月より後を許す**(むしろそちらが本来の値である)。上限は当月から50年後とし、桁の打ち間違いを止める
- 取得価格は0円以上の整数(円単位)。譲り受けたものを0円で残せるようにするため、0を許す

**取得価格の合計は表示しない**

**登録した持ち物の取得価格を合計して画面に出さない。** 資産として計上しないと決めたもの(4.11)の合計額を大きく出すと、資産額の隣に置いたときに資産のように読まれるためである。

出すのは**買い替え予定が近いものの件数**(当月から12ヶ月以内)とする。この画面の用途は「いつ・いくらの臨時支出が来るか」を見込むことにあり(4.11)、そこに効くのは合計額ではなく時期のほうである。

**評価額の自動計算・減価償却は行わない**

取得価格と取得年月から現在価値を導かない。[要件定義書 4.11](./fire-asset-management-requirements.md) のとおりで、B11の負債が金利・返済期間から残債を導かないのと同じ方針である。**償却曲線を引くと、実際の売却価格とは無関係な数字が資産のように見える。**

売却額を持たせたくなった場合は、自動計算ではなく手入力の欄として足すかを改めて決める(後掲「今後の検討事項」)。

**遷移条件**

- 保存成功 → 画面に留まり完了メッセージを表示する
- バリデーションエラー(必須未入力、取得価格が数値でない・負の数、取得年月が当月より後、買い替え予定年月が範囲外、文字数超過)→ インラインエラーを表示し、保存しない
- 共通ヘッダー/サイドバーから他の主要画面へ自由に遷移可能

**登録が1件も無いとき**

「登録済みの持ち物がまだありません。」と、フォームを1件追加する導線を表示する(B12と同じ)。

## 今後の検討事項

| 項目 | 現状 | 保留の理由 |
|---|---|---|
| B13で解約した口座をどう扱うか | **手段が無い。** CSV由来の行は削除できず、解約したことを示す欄も持たない | 解約後も過去の取引は残るため、リストから消えるのは実態と合わない。「解約済み」の印を付ける形が素直だが、それを付けたあと一覧をどう並べるか(隠すのか、末尾へ送るのか)まで決めないと中途半端になる |
| B12のサブスクを実際の支出と突き合わせる | **突き合わせない。** 登録額と入出金明細は無関係に持つ | 明細の `内容` とサービス名を機械的に結び付ける手掛かりが無い(「Netflix」が「ネットフリックス」で来る)。B13の名寄せをしないのと同じ理由 |
