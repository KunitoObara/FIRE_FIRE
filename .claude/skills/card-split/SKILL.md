# PRの分割

[docs/development-workflow.md](../../../docs/development-workflow.md) 5章「PRの分割」が正本。**先にそこだけ読む**。分ける目安・順序・型の波及の切り方・積み方、そして**なぜ分けるのか**はすべてそこにある。本ファイルは手順だけを持つので、根拠が要る場面では正本を引く。

## どちらのモードか最初に決める

| 状況 | モード |
|---|---|
| これから実装する(`/card-start` の直後) | **A. 計画** — 実装前に切る単位を決める。git操作は不要で、いちばん安い |
| すでにブランチが大きい | **B. 切り出し** — 既存の差分を複数のブランチへ分ける |

Bは常にAより高くつく。**大きくなってから呼ばれた場合でも、次のカードではAで使うようユーザーに伝える。**

---

## モードA: 実装前に計画する

### A-1. カードの範囲を層で分解する

カード本文の「このカードの範囲」を、正本 5章「分ける順序」の4層(土台 / 新規画面 / 既存画面への波及 / 表記・ドキュメント)へ割り当てる。層に収まらない項目が出たら、それは層の切り方が合っていないので**カードの内容に合わせて層を決め直す**(4層は目安であって規則ではない)。

### A-2. 各スライスが単独でCIを通せるか確かめる

これが唯一の必須条件。机上で次を確認する。

- そのスライスだけを `develop` に載せたとき、`npm run typecheck` が通るか
- 既存のテストが壊れないか(型に必須フィールドを足すと、既存のテストのフィクスチャが全部落ちる)
- 既存の画面が壊れないか(データが読めない・保存できない)

通らないものが出たら、正本 5章「型の波及を切る手口」で**新しいフィールドを任意にしてから締める**形に組み替える。組み替えても通らないなら、そのスライスは分けられないので隣とまとめる。

### A-3. 見積もりを出してユーザーに確認する

スライスごとに「何が入るか」「何ファイルくらいか」「単独でCIを通せる理由」を並べ、この分け方でよいかを聞く(`AskUserQuestion`)。**勝手に分けない** — PRが増えればPOのマージ操作もその数だけ増えるため、本人の同意が要る。

分割しない判断になった場合は、その理由をPR本文の「レビューで見てほしい点」に書く、と伝えて終わる。

### A-3b. 分割計画をカードに記録する

同意が取れたら、**実装に入る前に**カードへ計画をコメントする(`mcp__trello__add_comment`)。**1行目の書式は変えない** — `/card-start` のマージ同期がこの行を読んで、カードを完了へ動かしてよいかを判定する。

```
分割計画: 全3本

1. 負債のFirestore層 — 型・スキーマ・rules・リポジトリ
2. B11 負債入力画面
3. B1・B4への波及
```

**これを書かないと、1本目がマージされた時点でカードが完了へ動く。** カードは1本目のPRで確認中へ移り、2本目以降はまだPRになっていないので、コメント上は「PRが1本あって、それが済んでいる」状態にしか見えない。総本数を先に書いておくことでその誤判定を防ぐ。

### A-4. 1本目だけブランチを切って実装に入る

```bash
git checkout develop && git pull
git checkout -b feature/fire-fire-<カードID>-part1
```

**スライスのブランチ名は `-part<N>` を付ける。連番だけを足さない。** 枝番カード(`[B11-2]`)のブランチ名が `feature/fire-fire-b11-2` なので、連番だけだと**実在する別カードのブランチと同名になる**。実際 `[B11-2]`・`[B11-3]` は存在するカードで、B11を3分割していたらスライス2・3のブランチ名がそのまま衝突していた。`/card-start` のマージ同期はカード名からブランチ名を導出するため、衝突すると別のカードを完了へ動かしうる。

2本目以降は1本目がマージされてから切る(逐次が既定)。

## モードB: 既存のブランチを切り出す

### B-1. 現状を測る

正本 5章「分ける目安」の指標をそのまま測る。**`--stat` の出力は使わない** — 末尾のサマリ行が混じって件数が1多く出るうえ、増減の合計にテストが含まれてしまい、「テストを除くソースの増減」という指標とずれる。

```bash
# 変更ファイル数
git diff develop...HEAD --name-only | wc -l

# テストを除く増減の合計
git diff develop...HEAD --numstat -- ':(exclude)*.test.ts' ':(exclude)*.test.tsx' \
  | awk '{ added += $1; deleted += $2 } END { print added + deleted }'
```

**`develop...HEAD`(3点)を使う。`git diff develop`(2点)にしない。** 2点は `develop` の**現在の先端**との差分なので、ブランチを切ったあとに他のPRが `develop` へ入ると、このブランチが触っていない変更まで数に混ざる。`/card-ship` の「1. 変更内容の把握」も3点で測っており、同じ指標は同じ基準で測る。

触る画面IDの数は、差分のパスを**画面IDに読み替えてから**数える。`src/app/(dashboard)/` と `src/components/` 配下は `dashboard` / `debts` / `real-estate` のような**機能名のディレクトリで、画面IDそのものではない**。対応表は [`screen-spec-drift-check`](../screen-spec-drift-check/SKILL.md) が持っているのでそれを引く(同じ表を2箇所に置かない)。`real-estate` のように1つのディレクトリが複数の画面ID(B5・B6・B7)に対応することもあるので、ディレクトリ数をそのまま画面IDの数として数えない。

正本 5章「分ける目安」と突き合わせ、**そもそも分ける必要があるか**を判断する。目安を下回っているなら分けずに終わってよい。その場合はそう報告する。

参考値(この指標で測った実績): PR #82 は4ファイル・26行で目安内。PR #83 は68ファイル・2,646行で超過していた。

### B-2. 差分をファイル単位で層に割り当てる

```bash
git diff develop...HEAD --name-only
```

ここも3点(B-1と同じ理由)。2点だと `develop` 側で後から入った変更を「このブランチ自身の変更」として層に割り当て、B-3でそのまま取り込んでしまう。

各ファイルを A-1 と同じ4層に割り当てる。**1つのファイルが複数の層にまたがる場合**(例: 既存の型定義ファイルに、土台の型と波及先の型の両方を足した)は、次のどちらかにする。

- そのファイルを丸ごと土台側へ寄せる(参照が無ければ単独でCIを通せることが多い)
- 層をまたぐ変更を諦め、そのファイルを含む2層を1本にまとめる

**`git diff` を手で分解して1ファイルの一部だけを切り出す形は避ける。** 切り出し漏れがCIでは検出されず、レビュー対象から静かに落ちる。

### B-2b. 分割計画をカードに記録する

割り当てが決まったら、A-3b と同じ書式でカードへコメントする。モードBでも完了判定の根拠は同じで、これが無いと1本目のマージでカードが完了へ動く。

### B-3. スライスごとにブランチを作る

元のブランチは**消さずに残す**(切り出し元として最後まで参照する)。

```bash
git checkout develop && git pull
git checkout -b feature/fire-fire-<カードID>-part1
git checkout <元のブランチ> -- <このスライスのパス...>
```

`git checkout <branch> -- <path>` は指定したパスだけを取り込む。取り込んだ後、**そのスライス単独で成立するように手で調整する**(参照が未実装の関数を呼んでいる、テストが未実装の画面を触っている、等)。

### B-4. 単独でCIを通す

正本 6章の検証コマンド一式を、そのスライスだけの状態で通す。1つでも落ちたら、B-2 の割り当てが間違っているので戻ってやり直す。**落ちたまま次のスライスへ進まない。**

`firestore.rules` を触ったスライスでは `firebase emulators:exec --only firestore` も走らせる。

### B-5. `/card-ship` でPRを出す

PR本文の「変更内容」の冒頭に、**分割の全体像**を書く。レビュアーが「なぜこれだけしか入っていないのか」を判断できるようにするため。

```markdown
このカードは3本に分けています(docs/development-workflow.md 5章「PRの分割」)。

1. **(このPR)** 負債のFirestore層 — 型・スキーマ・rules・リポジトリ
2. B11 負債入力画面
3. B1・B4への波及

単独でCIを通せる単位で切っており、このPRだけでは画面から負債を登録できません。
反映先は `fire-fire-dev`(STG)で本番ではないため、中間状態が入ること自体は問題になりません。
```

### B-6. 残りのスライスを繰り返す

1本目がマージされたら `develop` を引き直し、2本目のブランチを切って B-3 から繰り返す。

積み上げ(stacked)にする場合は、正本 5章「積み方」に従い**PR本文の冒頭に土台のPR番号を明記**する。squash mergeのため、土台がマージされた時点で rebase かやり直しが要ることも承知のうえで選ぶ。

## Trelloカードの扱い

**カードは分けない。** 分割はレビューの都合であって要件の都合ではないため、1枚のカードに複数のPRがぶら下がる。

- **実装に入る前に、分割計画をカードへコメントする**(A-3b)。総本数が分からないと完了判定ができない
- カードは1本目のPRを出した時点で `/card-ship` が**確認中**へ移す
- 2本目以降のPRのURLも、同じカードにコメントで追記する(`mcp__trello__add_comment`)
- カードが**完了**へ動くのは全部のPRがマージされたあと。判定の手順は `/card-start` §1 に書いてある(分割計画の総本数と、コメントに残ったPRのURLの数・状態を突き合わせる)。1本目がマージされた時点で動かさない
- **計画を変えたとき(スライスを増やす・減らす)は、カードへ新しい `分割計画:` のコメントを足す。** `/card-start` は最新のものを見る

## やらないこと

- **ユーザーの同意なく分けない**(A-3)。PRが増えればPOのマージ操作も増える
- **単独でCIを通せない単位に分けない**。緑にならないPRを並べてもレビューできない
- **`git diff` を手で分解して1ファイルの一部だけを切り出さない**(B-2)
- **元のブランチを消さない**。全部のスライスがマージされるまで切り出し元として要る
