# FIRE達成度・到達予測の計算検証

## なぜこのスキルが必要か

docs/fire-asset-management-requirements.md 4.6は、目標設定に2方式(目標資産額の直接設定/年間支出額からの逆算)を要求し、達成度と到達予測日を算出するとしている。これらは単純に見えて割合と資産成長率の複合計算であり、以下のような間違いが起きやすい。

- 達成度を%表示すべき箇所で比率(0〜1)のまま表示してしまう
- 年率と月率、%と比率(4 と 0.04)を取り違える
- 4%ルールなど「年間支出額→必要資産額」の逆算で、掛けるべきところを割ってしまう
- 目標に届かないケースで到達予測日がinfinity/NaN/過去日付になる

## 要件の正本

**算出方式は [docs/screen-requirements-fire-goal.md](../../../docs/screen-requirements-fire-goal.md) の「到達予測日の算出」節が正本。** このスキルは実装がそこに一致しているかを見るもので、**方式そのものをここで決めない**。正本と違う実装を見つけたら、どちらが正かをユーザーに確認する(勝手にどちらかへ寄せない)。

正本が決めている要点を、検証の観点として抜き出す。

| 決め事 | 検証で見るもの |
|---|---|
| 起点は当月、月単位で進める | 日単位の刻みや、起点が資産残高の最終日になっていないか |
| 月次成長率は `(1 + 年率 ÷ 100) ^ (1/12)` | 年1回の複利や単利になっていないか。年率をそのまま月に掛けていないか |
| 積立額には利回りを掛けない | 積立分が複利で育っていないか |
| 想定利回り未設定の資産種別は年率0%(除外しない) | 除外して予測の初月が現在資産額とずれていないか |
| 物件・負債は全期間据え置き | 残債が時間で減っていないか(要件定義書 4.8「自動計算は行わない」に反する) |
| 既定(総資産)ではCSV合計と内訳の差額を年率0%で据え置く | **予測の初月が現在資産額と一致するか**(これが一致しないのは上記のどれかが崩れている印) |
| 打ち切りは600ヶ月(50年) | 上限が無く終わらない経路が無いか |

## 実装の場所

| | パス |
|---|---|
| 達成度・到達予測 | `src/frontend/src/lib/dashboard/fire-progress.ts` |
| 目標設定(直接指定 / 年間支出からの逆算) | `src/frontend/src/lib/fire-goal/` |
| 想定利回り・リスクの前提(B9) | `src/frontend/src/lib/assumptions/` |

**到達予測は B8 と B9 の両方の設定に依存する。** 利回り(B9)を変えたときと積立額(B8)を変えたときの両方で予測日が動くこと、前提が未設定のときにどう振る舞うかまで検証の対象に含める。計算関数だけを単体で見ると、前提の受け渡しでの取り違え(年率と月率、%と比率)が素通りする。

## 検証手順

1. 変更対象の計算関数を特定する(達成度計算、到達予測日計算、年間支出額からの目標資産額逆算)。
2. 既知の入力に対して手計算で期待値を出し、それと実装の出力を比較する。例:
   - 目標3,000万円・現在1,500万円 → 達成度50%
   - 年間支出300万円・4%ルール → 必要資産額7,500万円(300万 ÷ 0.04)
   - 現在1,000万円・年率6%・積立0円・目標2,000万円 → 約11年11ヶ月後(`ln(2) ÷ ln(1.06 ^ (1/12))` ≒ 142.7ヶ月なので143ヶ月目)
   - 現在0円・年率0%・積立10万円・目標1,200万円 → ちょうど120ヶ月目
3. 境界値を確認する。正本の「結果の区別」の3状態が、それぞれ意図した条件で出ることまで見る。
   - **達成済み** — 現在資産額が目標以上。過去日付や0ヶ月を出していないか
   - **到達見込みなし** — 利回りが全て未設定かつ積立0以下、または積立のマイナスが伸びを上回る。無限ループやNaNにならず明示的にこの状態を返すか
   - **資産残高が未取込** — 現在資産額0円から予測が始まり、積立額があれば到達月が求まるか。「算出できません」で止めていないか(正本「『前提が足りない』を4つ目の状態にしない」)
   - 打ち切りのちょうど境界(600ヶ月目に到達する入力)で、到達側と見込みなし側のどちらへ倒れるか
4. **予測の初月が現在資産額と一致するか**を必ず確かめる。B1のゲージが出す現在資産額と予測の出発点が違うと、同じカードの中で2つの現在額が並ぶ。既定(総資産)の場合が最も崩れやすい。
5. 表示層(ゲージ・到達予測日の文言)で、計算結果の単位(円、%、日付)が正しく反映されているか確認する。
6. **確かめたケースはユニットテストとして残す。** vitest は導入済みで(`npm run test`)、対象の各ファイルには既に `*.test.ts` がある。手計算の結果をレポートするだけで終わらせない — 次に計算を触ったときに壊れたことが分からないため。既存のテストと重複するケースは足さない。

## 出力

各テストケースについて「期待値/実際の値/一致するか」を一覧で示し、不一致があれば原因箇所を指摘する。正本と実装が食い違っている場合は、どちらを直すべきかを決めずにユーザーへ確認する。
